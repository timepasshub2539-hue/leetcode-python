Stone Game — 🟡 Intermediate (2/3) — LeetCode Daily Python Solution (the interval trick)

💰 Greedy

Introduction

Every coding interview eventually circles back to a handful of problem shapes, and "two players alternately picking from either end of an array" is one of the most recognizable ones. Stone Game is the canonical version of this family, and interviewers love it because it tests three separate skills at once: can you recognize optimal substructure in a game, can you translate that into a correctly-ordered DP table, and can you notice when a problem's specific constraints let you skip the DP entirely.

This is also a great problem for building intuition about interval DP — a DP style where the state isn't "the first i items" but "the slice from index i to index j." That pattern shows up again and again: burst balloons, palindrome partitioning, matrix chain multiplication, and predicting-the-winner-style game problems. Once you've internalized how to fill an interval DP table correctly, a whole category of "hard" problems stops being hard.

Problem Overview

You're given a row of piles of stones, each pile holding some positive number of stones. There's an even number of piles, and the total number of stones across all piles is odd — which guarantees the game can never end in a tie.

Alice and Bob take turns removing piles, but only from the ends of the row — either the leftmost pile or the rightmost pile, never from the middle. Alice always moves first. Each player keeps the stones they pick up, and both play optimally, meaning each is always trying to maximize their own final stone count relative to the other.

The question: assuming perfect play from both sides, does Alice end up with more stones than Bob?

Example

Take the piles [5, 3, 4, 5].

Alice moves first and can only take the 5 on the far left or the 5 on the far right. Whatever she leaves behind becomes Bob's problem, and Bob will also play to maximize his own advantage.

Working this out by hand: no matter how the game unfolds from here, Alice can always end up ahead by exactly one stone. We'll prove this rigorously with the DP table below, and the numbers will match.

Intuition

The instinct most people have is to simulate the game: "if Alice takes left, then Bob's options are these two, and if Alice takes right, then Bob's options are those two..." That's a real algorithm, but it's exponential — every turn branches into two more branches.

The key realization that turns this into a tractable DP problem: since the total number of stones is fixed and known in advance, Alice doesn't need to track her absolute stone count. She only needs to maximize the gap between her total and Bob's total. If that gap comes out positive, she wins — the exact number doesn't matter.

This reframing is what makes the recursion clean. At any point in the game, the "state" isn't about whose stones are whose — it's just: given a slice of the row from index i to index j, what's the best score-gap the player whose turn it is can force?

And here's the part that makes it solvable bottom-up rather than top-down: whichever pile you take (left or right), your opponent then plays optimally on whatever's left. Their best result works against you, so you subtract it. Compare "take left minus opponent's best reply" against "take right minus opponent's best reply," and keep the larger one.

Because every larger slice depends on smaller slices being solved first, you can't fill this table row by row — you have to fill it by increasing slice length, starting with single piles and working outward until you reach the full row.

Brute Force Solution

Idea: Recursively simulate every possible sequence of moves. At each turn, try taking the left pile and taking the right pile, recurse on both, and pick whichever gives the current player the better outcome.

Algorithm: 1. Base case: an empty slice yields a gap of 0. 2. Recursive case: best(i, j) = max(piles[i] - best(i+1, j), piles[j] - best(i, j-1)) 3. Alice wins if best(0, n-1) > 0.

Advantages: Obviously correct, easy to reason about, mirrors how you'd explain the game to a five-year-old.

Disadvantages: Recomputes the same subproblems over and over. The number of distinct (i, j) calls is polynomial, but without memoization the raw recursion tree branches exponentially.

Time complexity: O(2ⁿ) without memoization. Space complexity: O(n) for the recursion stack.

Optimal Solution

The recursive structure above is sound — the only problem is redundant recomputation. Since best(i, j) only depends on best(i+1, j) and best(i, j-1), both strictly smaller slices, we can compute every slice exactly once by filling a table in order of increasing length.

Picture a 2D grid where cell (i, j) represents "the best gap the current player can force on piles i through j":

Slice length What's filled
1 dp[i][i] = piles[i] — taking your only option
2 Compare the two piles, subtract nothing (opponent has no choice either)
3, 4, ... n Each depends on two already-solved smaller slices

Because a length-k slice always depends only on length-(k-1) slices, sweeping by length guarantees every value you read has already been computed.

Python Code

def stone_game(piles: list[int]) -> bool:
    """Return True if Alice wins with optimal play from both sides."""
    n = len(piles)
    # dp[i][j] = best score gap the current player can force on piles[i..j]
    dp = [[0] * n for _ in range(n)]

    # Base case: a single pile — take it, gap equals its value
    for i in range(n):
        dp[i][i] = piles[i]

    # Fill by increasing slice length so smaller slices are ready first
    for length in range(2, n + 1):
        for i in range(n - length + 1):
            j = i + length - 1
            take_left = piles[i] - dp[i + 1][j]
            take_right = piles[j] - dp[i][j - 1]
            dp[i][j] = max(take_left, take_right)

    return dp[0][n - 1] > 0

Code Walkthrough

  • dp = [[0] * n for _ in range(n)] builds an n×n table, all zeros — using a list comprehension so each row is a genuinely separate list (never [[0]*n]*n, which would alias every row to the same list).
  • The base-case loop handles slices of length 1: if it's just one pile, the best gap you can force is that pile's own value, since your opponent gets nothing from this slice.
  • The outer loop for length in range(2, n + 1) sweeps slice sizes from 2 up to the full row. Using n + 1 (not n) is essential — otherwise the loop stops one slice short and never computes the full-row answer.
  • The inner loop for i in range(n - length + 1) picks every valid starting index for a slice of this length, and j = i + length - 1 marks where it ends.
  • take_left and take_right implement the recurrence: take a pile, then subtract whatever gap the opponent can force on what's left.
  • dp[i][j] = max(take_left, take_right) keeps the better of the two choices.
  • The final answer, dp[0][n-1] > 0, asks: on the full row, can the first player (Alice) force a positive gap?

Dry Run

Piles: [5, 3, 4, 5], indices 0, 1, 2, 3.

Length 1 (base case): dp[0][0]=5, dp[1][1]=3, dp[2][2]=4, dp[3][3]=5

Length 2: - dp[0][1]: max(5 − dp[1][1], 3 − dp[0][0]) = max(5−3, 3−5) = max(2, −2) = 2 - dp[1][2]: max(3 − dp[2][2], 4 − dp[1][1]) = max(3−4, 4−3) = max(−1, 1) = 1 - dp[2][3]: max(4 − dp[3][3], 5 − dp[2][2]) = max(4−5, 5−4) = max(−1, 1) = 1

Length 3: - dp[0][2]: max(5 − dp[1][2], 4 − dp[0][1]) = max(5−1, 4−2) = max(4, 2) = 4 - dp[1][3]: max(3 − dp[2][3], 5 − dp[1][2]) = max(3−1, 5−1) = max(2, 4) = 4

Length 4 (full row): - dp[0][3]: max(5 − dp[1][3], 5 − dp[0][2]) = max(5−4, 5−4) = max(1, 1) = 1

dp[0][3] = 1 > 0 → Alice wins by exactly one stone, matching the expected result.

Complexity Analysis

Time: O(n²). There are O(n²) distinct (i, j) slices, and each is computed in O(1) work using two already-solved smaller slices.

Space: O(n²). The table stores one entry per (i, j) pair.

These bounds are tight because the recurrence genuinely needs every slice's value available before computing larger slices — there's no way to avoid materializing the full table without changing the approach entirely (which is exactly what the shortcut below does).

Alternative Solutions

The parity shortcut (O(1)): Because the problem guarantees an even number of piles and an odd total, Alice can always force herself into taking either every even-indexed pile or every odd-indexed pile — her choice. Here's why: on her first move she picks left or right, which commits Bob to leaving her the "other parity" option on his turn, and Alice can always steer the game to preserve her chosen parity group all the way through. Since one of "sum of even-indexed piles" and "sum of odd-indexed piles" must be strictly larger (the total is odd, so they can't tie), Alice picks whichever group is bigger and wins, guaranteed — without playing a single simulated move.

def stone_game_fast(piles: list[int]) -> bool:
    # ponytail-style shortcut: even pile count + odd total => Alice always wins
    return True

This only works because of this problem's exact constraints. Change the rules — as in Stone Game II or III, where you can take more than one pile per turn — and the parity argument collapses; you're back to needing the DP.

Approach Time Space When to use
Brute force recursion O(2ⁿ) O(n) Never in production, only to build intuition
Interval DP O(n²) O(n²) When the reasoning needs to generalize to harder variants
Parity trick O(1) O(1) Only under these exact constraints

Edge Cases

  • Two piles: The table collapses to a single comparison — Alice takes the bigger pile, and the odd total guarantees they're never equal, so there's no ambiguity.
  • Maximum size (500 piles): The table has 250,000 cells — trivial for O(n²) time and space, still runs in milliseconds.
  • All piles equal except one: The odd-total constraint means piles can never all be equal, so there's always a decisive winner.
  • Minimum pile values (all piles = 1): Degenerates to "whoever takes more piles wins" — since Alice always gets the ceiling of n/2 piles under optimal play here, she wins.
  • Odd pile count: Can't happen per the problem's constraints, so the base case never needs to handle a leftover single element mid-recursion incorrectly.

Common Mistakes

  1. Filling the table in row-major order (for i in range(n): for j in range(n)) instead of by increasing slice length — this reads dp[i+1][j] or dp[i][j-1] before those cells are populated, silently returning zeros.
  2. Tracking raw stone totals instead of the score gap — this breaks the subtraction step, since you need "my gain minus opponent's best subsequent gap," not two independent running totals.
  3. Using range(2, n) instead of range(2, n + 1) for the length loop — this silently stops one slice short and never computes the answer for the full row, so you get a wrong answer for the sub-problem instead of the real one.
  4. Aliasing rows with [[0] * n] * n — this makes every row the same list object, so writing to one cell corrupts every row.
  5. Forgetting the base case entirely and trying to compute length-2 slices directly, which produces incorrect results because dp[i+1][j] for a single-pile slice was never initialized.

Interview Questions

  • How would this change if players could take from a pile, not just remove it whole?
  • What if more than two players took turns?
  • Can you solve this in O(n) space instead of O(n²)?
  • What breaks if you can take one, two, or three piles from either end (Stone Game II/III)?
  • Can you prove the parity argument formally, not just observe it empirically?

Key Takeaways

  • Reframe "who ends up with more" as "maximize the score gap" — this collapses two running totals into one number worth optimizing.
  • Interval DP problems must be filled in order of increasing slice length, not row by row, because larger slices depend on smaller ones being ready.
  • Recognizing a problem's exact constraints can turn an O(n²) DP into an O(1) check — but that shortcut is fragile and breaks the moment the rules shift.

📇 Flashcards

Two piles, alternating optimal turns — what pattern applies?

Interval DP: define best score-gap over a subarray, recurse on shrinking [i,j] window.

Time complexity of the Stone Game DP?

O(n^2) — one state per (i,j) pair, each computed in O(1) from smaller subarrays.

Space complexity, and how to shrink it?

O(n^2) for the full table; collapsible to O(n) with rolling 1D array since each row only needs the row below.

Common bug when coding the gap-DP transition?

Forgetting the gap represents current player's advantage, so next player's best gap gets subtracted, not added.

Stone Game gap-DP vs classic knapsack DP — key difference?

Knapsack tracks max value alone; gap-DP tracks relative advantage between two adversarial players each turn.

Interview follow-up: what if piles could be uneven or player skips a turn?

Breaks the simple two-ended shrink; state must expand to track whose turn and remaining piles explicitly.
