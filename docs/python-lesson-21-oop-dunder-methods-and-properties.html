Lesson 21: Why Does print(obj) Show Garbage?

General

Introduction

If you've ever printed a custom Python object and gotten back something like <__main__.Point object at 0x7f8b2c0a3d90>, you've run into one of the first genuinely confusing moments in learning object-oriented Python. It's not a bug. It's Python telling you, honestly, that it has no idea how you want this object represented — because you never told it.

This matters more than it looks like it should. Interviewers care about it because it tests whether you understand what's happening underneath Python's syntax, not just whether you can write a for loop. Every time you use print(), ==, len(), or + on a built-in type, you're relying on a contract that type honors. When you write your own classes, nothing honors that contract unless you write it yourself. Understanding dunder methods is the difference between writing classes that feel bolted-on and classes that feel like they belong in the language.

This lesson also covers two decorators, @property and @classmethod, that solve a related problem: how do you expose computed values and alternate ways of building objects without cluttering your API with extra method calls and awkward constructors? Together, these tools are what separate a class that "works" from a class that reads like it was designed.

Problem Overview

Suppose you're modeling a Point with x and y coordinates. Out of the box, Python gives you almost nothing useful:

  • print(point) shows a memory address instead of coordinates.
  • point1 == point2 returns False even when the coordinates match, because Python is comparing object identity, not value.
  • len(point) fails outright — Python has no idea what "length" means for a point.
  • point1 + point2 fails too, because + is undefined for objects Python doesn't recognize.

None of this is a limitation of Python. It's a design choice: Python doesn't guess what equality, length, or addition should mean for your custom type. Instead, it exposes a set of hooks — dunder methods — that you implement to opt in to that behavior. The task is to learn which hook maps to which built-in behavior, and then use @property and @classmethod to make the resulting class feel clean to use.

Example

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p1 = Point(3, 4)
p2 = Point(3, 4)

print(p1)          # <__main__.Point object at 0x...>
print(p1 == p2)     # False

print(p1) shows a memory address because Python falls back to the default object representation when no __repr__ is defined. p1 == p2 is False because the default __eq__ checks whether p1 and p2 are the same object in memory — they're not, even though their coordinates match. Once we add __repr__ and __eq__, both of these start behaving the way most developers expect on first contact with the class.

Intuition

The mental model that unlocks all of this is simple: built-in syntax is sugar for method calls. print(obj) doesn't have special knowledge of your class — it calls repr(obj), which calls obj.__repr__(). a == b calls a.__eq__(b). len(obj) calls obj.__len__(). a + b calls a.__add__(b).

An experienced engineer doesn't memorize this list — they internalize the pattern: whenever I use an operator or a built-in function on an object, Python is looking for a specifically named method on that object's class. If the method exists, Python calls it. If it doesn't, Python either falls back to a default (as with __repr__) or raises an error (as with __add__).

This reframes the whole problem. You're not implementing "printing" or "equality" — you're implementing a method with a name Python already knows to look for. Once that clicks, extending any custom class to support any built-in behavior stops being a lookup task and becomes a design decision: does this object's notion of equality make sense as coordinate comparison, or as something else?

Brute Force Solution

Idea: Write ordinary named methods — describe(), equals(other), size(), add(other) — and call them explicitly instead of relying on operators.

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def describe(self):
        return f"Point({self.x}, {self.y})"

    def equals(self, other):
        return self.x == other.x and self.y == other.y

    def add(self, other):
        return Point(self.x + other.x, self.y + other.y)

Advantages: Works immediately, no special knowledge of Python's data model required.

Disadvantages: The object doesn't compose with the rest of the language. print(p1) still shows garbage unless you remember to call p1.describe(). p1 == p2 still returns False. Anyone using your class has to learn your custom method names instead of relying on Python conventions they already know. It also breaks interoperability — code that generically calls len() or + on objects (sorting, aggregation, generic algorithms) simply won't work with your type.

Complexity: Each operation is O(1) for Point, same as the dunder version — the cost here isn't runtime, it's usability and integration.

Optimal Solution

Implement the dunder methods that correspond to the behavior you want, so built-in syntax "just works."

Syntax Calls Purpose
print(obj) / str(obj) __str__ (falls back to __repr__) Human-readable / debug string
repr(obj) __repr__ Unambiguous debug representation
a == b __eq__ Value-based equality
len(obj) __len__ Size/count
a + b __add__ Combination
obj[i] __getitem__ Indexing

The order matters: define __repr__ first, since Python uses it as the fallback for str() when __str__ is missing. Then layer in __eq__, __len__, and __add__ only for the behaviors that make sense for your type — not every class needs all of them.

For computed, read-only-feeling attributes (like a circle's area from its radius), use @property instead of a plain method — this lets callers write circle.area instead of circle.get_area(), while the value is still computed on demand. Pairing a property with a setter lets you validate input at the point of assignment, catching bad data immediately instead of letting it corrupt state three calls later. And for alternate ways to construct an object (e.g., building a Point from a tuple), use @classmethod, which receives the class (cls) instead of an instance (self), so it can build and return a new object without touching __init__'s signature.

Python Code

import math


class Point:
    """A 2D point that behaves like a native Python type."""

    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Point({self.x}, {self.y})"

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented
        return self.x == other.x and self.y == other.y

    def __add__(self, other):
        if not isinstance(other, Point):
            return NotImplemented
        return Point(self.x + other.x, self.y + other.y)

    @property
    def magnitude(self):
        """Distance from the origin, computed fresh each access."""
        return math.hypot(self.x, self.y)

    @classmethod
    def origin(cls):
        """Alternate constructor: build a Point at (0, 0)."""
        return cls(0, 0)

    @classmethod
    def from_tuple(cls, coords):
        """Alternate constructor: build a Point from an (x, y) tuple."""
        x, y = coords
        return cls(x, y)


class Circle:
    """A circle with a validated radius and a computed area."""

    def __init__(self, radius):
        self.radius = radius  # goes through the setter below

    @property
    def radius(self):
        return self._radius

    @radius.setter
    def radius(self, value):
        if value < 0:
            raise ValueError("radius cannot be negative")
        self._radius = value

    @property
    def area(self):
        return math.pi * self._radius ** 2

Code Walkthrough

  • __repr__ returns a string that mirrors how you'd construct the object — this is the debug view, aimed at you, the programmer.
  • __eq__ first checks isinstance(other, Point) and returns NotImplemented (not False) if the comparison doesn't make sense — this lets Python fall back gracefully instead of asserting a wrong answer.
  • __add__ follows the same defensive pattern, then returns a new Point rather than mutating either operand, matching how + behaves on numbers and strings.
  • magnitude is a @property, so p.magnitude reads like an attribute but recomputes math.hypot(self.x, self.y) every time it's accessed — no stale cached value to worry about.
  • origin and from_tuple are @classmethods. They receive cls, the class itself, so they can build and return instances without hardcoding Point(...) — this matters if Point is ever subclassed, since cls will resolve to the subclass.
  • In Circle, radius is implemented as a property with a setter. __init__ assigns self.radius = radius, which routes through the setter and validates the value before it's stored in self._radius.
  • area is a read-only property (no setter), since it's derived entirely from radius and should never be set directly.

Dry Run

p1 = Point(3, 4)
p2 = Point(3, 4)
p3 = p1 + p2

print(p1)          # Point(3, 4)        -> __repr__ used
print(p1 == p2)     # True               -> __eq__ compares x and y
print(p3)          # Point(6, 8)        -> __add__ built a new Point
print(p1.magnitude) # 5.0                -> sqrt(3**2 + 4**2)

c = Circle(5)
print(c.area)       # 78.53981633974483 -> computed from radius

c.radius = -1        # raises ValueError, caught before it's stored

p1 == p2 walks into __eq__, checks isinstance, then compares 3 == 3 and 4 == 4, returning True. p1 + p2 walks into __add__, builds Point(3+3, 4+4), and returns Point(6, 8). c.radius = -1 walks into the setter, hits the if value < 0 guard, and raises before self._radius is ever touched — the invalid value never enters the object's state.

Complexity Analysis

Every dunder method here (__repr__, __eq__, __add__) does a fixed, constant amount of work — comparing or combining a small, fixed number of attributes — so each is O(1) time, O(1) space. This holds regardless of how many Point objects exist, since none of these methods touch a collection. The magnitude property is also O(1), since math.hypot operates on two scalars. These are correct complexity claims because none of the operations scale with input size — they scale with the number of attributes on the class, which is fixed at class-definition time.

Alternative Solutions

For classes with many fields, @dataclass (from the dataclasses module) generates __init__, __repr__, and __eq__ automatically based on field annotations:

from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

This gives you correct __repr__ and __eq__ for free, and is the right choice when your class is mostly a data container. It's worth knowing dunder methods by hand anyway, because @dataclass doesn't generate __add__, __len__, or custom validation logic — for anything beyond straightforward field storage, you're back to implementing the hooks yourself.

Edge Cases

  • Comparing to a different type: p1 == "not a point" should return False, not raise — handled by the isinstance check returning NotImplemented.
  • Adding incompatible types: p1 + 5 should fail clearly, not silently produce garbage — same NotImplemented pattern.
  • Radius of exactly 0: should be valid (a degenerate circle), so the setter check must be < 0, not <= 0.
  • Missing __str__: confirm that str(obj) and print(obj) correctly fall back to __repr__ when __str__ isn't defined.
  • Mutating after construction: setting circle.radius after creation should go through the same validation as __init__, since both route through the property setter.

Common Mistakes

  1. Defining __str__ but not __repr__ — debugging tools (like the interactive shell and repr() in containers) still show the ugly default.
  2. Forgetting isinstance checks in __eq__, causing crashes or wrong results when compared against unrelated types.
  3. Returning False instead of NotImplemented from __eq__ for unsupported types, which breaks Python's ability to try the other object's __eq__ as a fallback.
  4. Mutating self inside __add__ instead of returning a new object, which silently breaks code that expects + to be non-destructive.
  5. Skipping validation in a property setter early in a project "to add later," which lets invalid state slip in and surface as a bug far from where it was created.
  6. Using @staticmethod when @classmethod was needed, especially for alternate constructors — a staticmethod factory hardcodes the class name and breaks with subclassing.

Key Takeaways

Python's built-in behavior — printing, comparing, measuring length, adding — is not magic; it's a dispatch table of dunder methods your class can opt into. __repr__ should be the first one you write, since everything else falls back to it. @property lets you expose computed or validated values through plain attribute syntax, and @classmethod gives you alternate, readable ways to construct objects. Once you understand this map, any class you write can feel as native as Python's own built-in types.

📇 Flashcards

When == doesn't work right for custom objects, what's the fix?

Define __eq__; default is identity comparison, so equal-looking objects compare False without it.

Time complexity of calling len(obj) via __len__?

O(1) if you store a count/length attribute; O(n) if __len__ recomputes by scanning.

Space cost of adding dunder methods to a class?

O(1) extra — dunders are just methods, no per-instance overhead beyond normal attributes.

Common bug with @property setters?

Forgetting to store to a differently-named private attr (e.g. self._x), causing infinite recursion calling the setter itself.

__repr__ vs __str__: when is each used?

__repr__ is the fallback for both and meant for debugging/unambiguous repr; __str__ is user-facing display text.

Interview follow-up: why prefer @classmethod over __init__ overloading?

classmethod gives named alternate constructors (e.g. from_string) without cluttering __init__ with conditional logic.
