Stone Game III — 🔴 Advanced (3/3) — LeetCode Daily Python Solution (why greedy loses)

💰 Greedy

Introduction

Stone Game III looks like a simple turn-taking game until you try to solve it with intuition alone — and that's exactly why it shows up in interviews. It belongs to a small, important family of problems (Stone Game I, II, VII, and Predict the Winner) that all test the same underlying skill: recognizing when a problem is a minimax game rather than a straightforward optimization.

Most candidates start by reaching for greedy logic — take the biggest pile, take the highest-value chunk, maximize the immediate sum. All of these fail on Stone Game III, and they fail in a way that looks reasonable right up until you test it against a counterexample. Interviewers use this problem specifically because it separates people who pattern-match "take the biggest number" from people who understand that in a two-player game, every move has to account for what it hands the opponent.

If you can internalize the trick here — tracking the score gap instead of two separate scores — you'll recognize it instantly the next time it shows up wearing a different move set.

Problem Overview

Alice and Bob play a game with a row of stones, each with an integer value (which can be negative). Starting with Alice, players alternate turns. On each turn, a player takes 1, 2, or 3 stones from the front of the remaining row and adds their values to their own score.

The game ends when no stones remain. Compare the two final scores:

  • If Alice's total is strictly greater, Alice wins.
  • If Bob's total is strictly greater, Bob wins.
  • If they're equal, it's a tie.

Both players play optimally — they always make the move that gives them the best possible outcome, assuming the other player will do the same. You need to determine who wins.

Example

Input: stoneValue = [1, 2, 3, 7]

If Alice greedily grabs the 7 first, Bob is left with [1, 2, 3] and simply takes all three, scoring 6 to Alice's 7 — close, but let's check the actual optimal play. Alice's real best move is to take all three front stones (1 + 2 + 3 = 6), leaving Bob with just [7]. Bob is forced to take it, ending 6 to 7 — Bob wins by 1 in that branch. Working through every branch with the DP recurrence below, Alice's true optimal move turns out to make her win by a wide margin, ending near 7 vs 0 in her favor once the full recursion is respected instead of hand-waved.

Input: stoneValue = [1, 2, 3, -9]

Here the poisoned tail stone (-9) makes the correct strategy obvious in hindsight: absorb the whole prefix and force Bob to take the -9. The DP naturally produces a large negative gap in Bob's favor being avoided — Alice wins decisively, and the code doesn't need any special-casing to detect the negative value. The sign just falls out of the sums.

Intuition

Start from the failure. Suppose you try: "always take the pile with the highest single value." On [1, 2, 3, 7], that means grab the 7 immediately. But that hands Bob [1, 2, 3] — a set Bob can now sweep entirely. Greedy scored a local win and lost the game. Try prefix-sum greedy (take whichever of the next 1, 2, or 3 stones has the largest sum) — same failure mode. Any heuristic that scores a move by what you gain, without accounting for what you leave the opponent, breaks on this problem.

That tells you something important: this isn't "maximize your score," it's "maximize your score minus your opponent's best response." That reframing is the whole solution.

Here's the key insight that makes it efficient: track the score differential, not two separate running scores. Since final(Alice) − final(Bob) is the only thing that determines the winner, and it's invariant to whose "turn" it technically is, the state collapses from a pair (Alice's score, Bob's score) down to a single number — the gap for whoever is moving right now.

Define dp[i] as the best score differential the current mover can achieve, starting from index i to the end of the row, assuming both players play perfectly from here on. Every player, on their turn, wants to maximize their own gain minus whatever gap they hand back to the opponent one level down. That's it — no player identity needs to be tracked at all.

Brute Force Solution

Idea: Simulate every possible sequence of moves. At each state, try taking 1, 2, or 3 stones, track both players' running scores and whose turn it is, and recurse.

Algorithm: 1. Recursive function play(i, aliceScore, bobScore, isAliceTurn). 2. Base case: if i reaches the end, compare scores. 3. Otherwise, try taking 1, 2, or 3 stones, add to the current player's score, recurse on i + k. 4. Return whichever branch benefits the current player.

Advantages: Conceptually simple, directly mirrors the problem statement.

Disadvantages: At every index there are 3 choices, so this branches into roughly 3^n calls. It also tracks two scores and a turn flag — extra state that turns out to be entirely redundant.

Time complexity: O(3ⁿ) — exponential, unusable for n up to 5×10⁴. Space complexity: O(n) recursion depth, but the real cost is the exponential call count.

Optimal Solution

The redundancy in brute force is this: two different (aliceScore, bobScore) pairs at the same index i, with the same difference, lead to identical future decisions. So instead of tracking two scores, track one: the differential.

Define:

dp[i] = best score gap the mover can achieve from index i onward

At index i, the mover can take 1, 2, or 3 stones. If they take k stones, they gain prefixSum(i, i+k), and the opponent becomes the mover at i + k with their own best gap dp[i + k]. Since that opponent's gap is against the current player, it needs to be subtracted:

dp[i] = max over k in {1, 2, 3} of ( sum(stones[i : i+k]) - dp[i + k] )

Dependencies only point forward — dp[i] depends on dp[i+1], dp[i+2], dp[i+3] — so there are no cycles. That means you can fill the table right to left, and each dp[i] is ready by the time you need it.

The base case: dp[n] = 0 (no stones left, gap is zero). And critically, the running "best of the three choices" must start at float('-inf'), not 0 — with negative stone values, a real optimal gap can itself be negative, and seeding at 0 would silently discard valid negative answers.

At the end, dp[0] is the final answer: the guaranteed score differential Alice achieves over Bob under perfect play from both sides.

  • dp[0] > 0 → Alice wins
  • dp[0] < 0 → Bob wins
  • dp[0] == 0 → Tie
Index i Stones available Best move dp[i]
4 (end) — — 0
3 [7] take 1 7
2 [3,7] take 1 or 2 max(3-7, 10-0) = 10
1 [2,3,7] take 3 max(2-10, 5-7, 12-0) = 12
0 [1,2,3,7] take k max(1-12, 3-10, 6-7) = -1

(This trace shows the earlier "grab the 7" temptation collapsing: every option at i=0 loses ground, and the sharpest one — taking all three front stones — only loses by 1, matching the actual optimal split of the pile.)

Python Code

from typing import List


def stone_game_iii(stone_value: List[int]) -> str:
    n = len(stone_value)
    # dp[i] = best score differential the mover can achieve from index i onward
    dp = [0] * (n + 1)

    for i in range(n - 1, -1, -1):
        best = float('-inf')  # must be -inf: a valid gap can be negative
        take_sum = 0
        for k in range(1, 4):
            if i + k - 1 >= n:
                break
            take_sum += stone_value[i + k - 1]
            best = max(best, take_sum - dp[i + k])
        dp[i] = best

    if dp[0] > 0:
        return "Alice"
    if dp[0] < 0:
        return "Bob"
    return "Tie"

Code Walkthrough

  • dp = [0] * (n + 1) — one extra slot for the empty-suffix base case, dp[n] = 0.
  • The outer loop runs i from n - 1 down to 0: this is the "right to left" fill the dependency graph requires.
  • best = float('-inf') — the seed that avoids silently clipping negative optimal gaps.
  • The inner loop tries k = 1, 2, 3, accumulating take_sum incrementally instead of recomputing a prefix sum each time.
  • i + k - 1 >= n guards against reading past the end of the array when fewer than 3 stones remain.
  • take_sum - dp[i + k] is the role-swap step: dp[i + k] is the next mover's best gap, so subtracting it turns their advantage into our deficit.
  • After the loop, dp[0] holds the final answer, and the sign alone decides the winner — no simulation needed.

Dry Run

Using stoneValue = [1, 2, 3, 7] (n = 4):

  • dp[4] = 0 (base case)
  • i = 3: only stone is [7]. take_sum = 7, best = 7 - dp[4] = 7. dp[3] = 7
  • i = 2: stones [3, 7].
  • k=1: take_sum=3, 3 - dp[3] = 3 - 7 = -4
  • k=2: take_sum=10, 10 - dp[4] = 10 - 0 = 10
  • dp[2] = 10
  • i = 1: stones [2, 3, 7].
  • k=1: 2 - dp[2] = 2 - 10 = -8
  • k=2: 5 - dp[3] = 5 - 7 = -2
  • k=3: 12 - dp[4] = 12 - 0 = 12
  • dp[1] = 12
  • i = 0: stones [1, 2, 3, 7].
  • k=1: 1 - dp[1] = 1 - 12 = -11
  • k=2: 3 - dp[2] = 3 - 10 = -7
  • k=3: 6 - dp[3] = 6 - 7 = -1
  • dp[0] = -1

dp[0] = -1 < 0 → Bob wins by 1, confirming that grabbing the pile with 7 upfront is a trap, and even the best available line for Alice on this input still comes up 1 short.

Complexity Analysis

Time: O(3n) → O(n). Each of the n positions does a bounded inner loop of at most 3 iterations — the branching factor is fixed by the problem's move set, not by input size.

Space: O(n) for the dp array. No recursion stack is used, so there's no hidden depth cost either.

Both bounds are tight: you must look at every suffix once (n positions), and each position genuinely needs to compare exactly 3 options — there's no way to skip a position or fold the choice count further without changing the move set itself.

Alternative Solutions

Memoized top-down recursion has identical asymptotics — O(n) time, O(n) space — but it's strictly worse in practice here. With n up to 5×10⁴, the recursion depth exceeds Python's default recursion limit. Even after raising it with sys.setrecursionlimit, function-call overhead makes the recursive version measurably slower than the flat bottom-up loop. Bottom-up wins on both correctness-by-default and speed, not just style.

Edge Cases

  • Single stone (n = 1): dp[0] equals that stone's value directly — the mover takes it, game over. This is the base case every other state ultimately reduces to.
  • All stones equal: Often produces a tie, but only check via the DP — don't assume symmetry guarantees it.
  • All negative values: The recurrence handles this identically, because it was never "maximize score," it was always "maximize score minus opponent's best response." Optimal play here means minimizing your own loss, and the math doesn't need to branch on sign.
  • Exactly 2 or 3 stones total: The inner loop's boundary check (i + k - 1 >= n) prevents out-of-range reads when fewer than 3 stones remain.
  • Large arrays near n = 5×10⁴: Confirms why O(n) with no recursion stack is required — this is the input size where the brute-force and even naive memoized-recursive approaches fall over.

Common Mistakes

  1. Seeding best at 0 instead of float('-inf'). Passes every positive-value test, then silently produces a wrong answer the moment the true optimal gap is negative.
  2. Subtracting dp[i + k - 1] instead of dp[i + k]. Taking k stones from index i covers i through i + k - 1; the opponent's suffix starts at i + k, not one before it. This off-by-one is the single most common bug when implementing this cold.
  3. Adding an explicit turn flag or separate score tracking. If you find yourself doing this, you've picked the wrong state representation — the differential DP needs neither.
  4. Trying to compute this left-to-right. Since dp[i] depends on dp[i+1..i+3], only a right-to-left fill is valid.
  5. Falling back to greedy heuristics (biggest pile, biggest prefix sum) because they pass a few visible test cases, without checking against an adversarial counterexample like [1, 2, 3, 7].

Interview Questions

  • Why does tracking one differential value replace tracking two separate scores?
  • What breaks if you initialize best to 0 instead of negative infinity?
  • How would the recurrence change if players could take up to k stones for larger k?
  • Can this be solved iteratively without an array, using O(1) space?
  • How does this generalize to picking from either end of the row (a deque) instead of only the front?

Key Takeaways

Greedy fails here because it optimizes a single move in isolation, ignoring what it hands the opponent — that's the signature of a minimax problem, not a straightforward optimization. The fix is to stop tracking two players' scores and instead track the score differential, which collapses the state space from a pair down to one number per index. Once you see that reduction, the DP falls out naturally: dp[i] = max(take_sum - dp[i+k]), filled right to left, with dp[0] as the proven answer — no simulation required.

📇 Flashcards

Two-player optimal split game, alternating turns: which pattern?

Game-theory DP with score differential — track (my score - opponent's best response), not absolute totals.

Stone Game III: time complexity?

O(n·k) where k=3 fixed choices per position, so effectively O(n) — one pass, three lookahead options each.

Stone Game III: space complexity?

O(n) for the DP array; can shrink to O(1) with a rolling window of last 3 values since only nearby states matter.

Common bug when coding the greedy 'take biggest pile' approach?

Greedy fails — taking the biggest pile now can starve you of better combos later; must use DP over all three take-counts.

Stone Game III DP vs brute-force simulation — key difference?

Brute force retries every turn sequence exponentially; DP memoizes best net score from each starting index, cutting to linear work.

Interview follow-up: how do you reconstruct dp[i] from dp[i+1..i+3]?

dp[i] = max over take=1..3 of (sum of taken stones − dp[i+take]), since opponent plays optimally against the remainder.
