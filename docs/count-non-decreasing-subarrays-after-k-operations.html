8. Introduction: Why This Problem Matters

Welcome to another session of Fun with Learning Technology. Today, we are tackling a classic "trick" question that appears in high-stakes technical interviews and competitive programming circles: LeetCode 3420 – Count Non-Decreasing Subarrays After K Operations.

At first glance, this problem seems straightforward: given an array and a budget of K increments, count how many continuous slices (subarrays) can be transformed into a non-decreasing sequence. It sounds like a perfect candidate for a brute-force approach. You might think, "Just check every subarray, calculate the cost to fix it, and see if it fits in K."

However, experienced engineers know that "obvious" is often where performance fails. With an input size of up to 100,000 elements, a naive O(N²) or even slightly slower approach will time out instantly. Interviewers use problems like this not just to test if you know Python syntax, but to gauge your ability to:

  • Identify hidden inefficiencies in naive solutions.
  • Transform data structures (like flipping the array logic).
  • Maintain state incrementally rather than recomputing from scratch.
  • Combine sliding windows with monotonic stacks for constant-time updates.

By the end of this article, you will understand exactly why the naive approach fails, how to flip the problem perspective, and how to implement a robust O(N) solution that scales effortlessly. Let's dive into the intuition before we write a single line of code.

9. Problem Overview

Here is the core challenge restated in plain English:

You are given an array of integers nums and an integer k. Your goal is to count the number of contiguous subarrays that can be made non-decreasing (sorted in ascending order) using at most k total operations.

An "operation" consists of increasing any single element within a specific subarray by 1. Crucially, these operations are local: fixing a subarray does not affect the budget or state for the next subarray we check.

Key Constraints to Note: * Non-Decreasing: For a slice nums[i...j], it must satisfy nums[x] <= nums[x+1] for all valid x. * Budget: The sum of all increments across the entire subarray cannot exceed k. * Scale: The array length n can be up to 100,000. Values can go up to 1 billion. k is also large (up to 1 billion).

This means we absolutely cannot iterate through every subarray and sort/rearrange them individually. We need a linear-time scan.

11. Intuition: The "Flip" Strategy

If you try to simulate this directly from left to right, you face a wall: how do you efficiently know the minimum value required to make a window sorted?

Here is the senior engineer's insight: Don't fix small numbers by raising them; instead, think about fixing the landscape by lowering the requirements.

Imagine scanning from right to left. If we look at an element nums[i], for the subarray ending at i to be non-decreasing, nums[i] must be greater than or equal to the maximum value of everything to its right after we've made adjustments.

Wait, that's confusing. Let's simplify the mental model. Instead of raising every small number to match the big one, let's view the cost as a "gap" that needs filling.

The Stack Trick: Think of the array as a landscape. We want to ensure that as we walk from left to right, the numbers never dip below the previous peak. If a new number is smaller than our current running maximum, it creates a "drop" or a "negative cost."

To handle this efficiently, we use a Monotonic Stack. This stack doesn't just store numbers; it stores pairs of (value, count). * We maintain a stack where values are strictly decreasing from bottom to top (or increasing, depending on perspective). * When we encounter a new number that is larger than the top of our stack, we "merge" groups. Why? Because if we have a block of 5s and then a 6, the cost logic changes for the entire block of 5s relative to future smaller numbers.

The Core Logic: We maintain a Sliding Window [left, right]. We track a running cost. As we expand right: 1. If the current number is smaller than our local maximum (which is tracked by the stack structure), it adds to our cost. 2. If the cost exceeds k, we must shrink the window from the left (left) until cost <= k.

By using a stack, we group identical values together. This allows us to update the total cost in O(1) time when shifting boundaries, rather than iterating through every element. We are effectively calculating "how much do I need to raise this block of numbers to match the next higher number?"

12. Brute Force Solution: The Trap

Before we reveal the optimal method, let's see what happens if we ignore complexity constraints.

The Idea: Iterate through every possible starting index i. Inside that loop, iterate through every ending index j. For each subarray nums[i...j]: 1. Find the maximum value in nums[i...j]. 2. Calculate the cost: Sum of (max_value - current_element) for all elements. 3. Check if cost <= k.

Algorithm:

def count_brute_force(nums, k):
    n = len(nums)
    count = 0

    # Iterate over all subarrays
    for i in range(n):
        current_max = nums[i]
        cost = 0

        for j in range(i, n):
            # Update max as we extend the window
            if nums[j] > current_max:
                current_max = nums[j]

            # Add cost to make this element equal to current_max
            diff = current_max - nums[j]
            cost += diff

            # Check budget
            if cost <= k:
                count += 1
            else:
                break # Optimization: if one element makes it too expensive, larger windows will too

    return count

Complexity Analysis: * Time Complexity: O(N²). We have nested loops. Inside, we do constant work (updating max and adding diff), but the nesting dominates. With N=100,000, N² is 10 billion operations. This will crash a standard interview runtime. * Space Complexity: O(1).

Verdict: While easy to write, this is unacceptable for production or interviews with large inputs. It wastes CPU cycles by recalculating costs and re-scanning ranges repeatedly.
