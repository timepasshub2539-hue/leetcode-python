Minimum Number of Pushes to Type Word II — 🔴 Advanced (3/3) — LeetCode Daily Python Solution (i // 8 + 1 solves it)

General

Introduction

Every phone keypad you've ever typed on made an assumption: that the letters belong on the keys they're on. T9 put "abc" on 2, "def" on 3, and so on, and nobody questioned it because it matched the alphabet. But what if you were handed a blank keypad and told: put any letters on any key, in any order you want — just minimize the total number of button presses for a specific word?

That's the real question behind Minimum Number of Pushes to Type Word II, and it's a fantastic interview problem because it looks like a simulation exercise but is actually an optimization problem wearing a disguise. Interviewers use it to test whether you can recognize a classic algorithmic shape — greedy assignment via an exchange argument — underneath an unfamiliar phone-keypad wrapper. If you've studied Huffman coding or interval scheduling, this problem will feel oddly familiar once you strip away the keypad story. If you haven't, it's one of the cleanest introductions to that reasoning pattern you'll find.

This is Part 3 of a three-part series on the Minimum Pushes problems, and it's the one where the "obvious" fixed-keypad approach falls apart and you have to actually prove your algorithm is optimal, not just correct.

Problem Overview

You're given a string word made of lowercase English letters. You get to design a keypad with 8 usable keys (numbered 2 through 9). Every letter of the alphabet that appears in word must be assigned to exactly one key, and each key can hold any number of letters — but the letters on a key are ordered, because pressing a key multiple times cycles through its letters.

  • The 1st letter on a key costs 1 press.
  • The 2nd letter on that same key costs 2 presses.
  • The 3rd letter costs 3 presses, and so on.

To type word, you press the buttons for each character in order, and the total press count is your score. You choose the entire key layout before typing. The goal: design the layout (i.e., decide which letters go on which keys, and in what order within each key) so that typing word costs the fewest total presses.

Note what's absent from the rules: there's no requirement to preserve alphabetical order, no requirement to match real T9, and no limit on how many letters can sit on one key. The only real constraints are 8 keys and 26 possible letters.

Example

Take word = "abcde".

Each letter appears once. There are only 5 distinct letters and 8 keys available, so every letter can get its own key, occupying the "1st letter" (1-press) slot on that key. Total cost: 5.

Now take word = "aabbccddeefghij".

Count the letters: a and b and c and d each appear twice, and e appears twice as well, then f, g, h, i, j appear once each. That's 10 distinct letters, more than 8 keys, so at least two letters must double up on a single key — meaning at least one letter lands in a 2-press slot instead of a 1-press slot.

Which letter should absorb that penalty? Obviously not one of the letters appearing twice — you'd pay that 2-press cost every time it shows up. You want the least frequent letters sharing keys, because a 1-extra-press penalty on a rare letter costs less overall than the same penalty on a frequent one. That's the entire intuition of this problem in one sentence.

Intuition

Here's how an experienced engineer approaches this once they see through the phone-keypad framing.

Strip away the story and you're left with two lists: - A list of weights: how often each distinct letter appears in word. - A list of costs: how many presses a "slot" requires, determined only by its rank when you line up all 26 possible slots (8 keys × up to however many rungs you need) from cheapest to most expensive.

You're free to match any weight to any cost slot, and you want to minimize the sum of weight × cost across all letters. That's it — that's the whole problem, once you see it this way.

This is a textbook case for the rearrangement inequality (the same principle behind Huffman coding and priority scheduling): to minimize a sum of products between two sequences, pair the largest values in one sequence with the smallest values in the other. Concretely: pair your highest-frequency letters with your cheapest slots.

Why is this provably correct, not just plausible? Suppose you have an optimal assignment where some letter with a higher frequency sits in a more expensive slot than a letter with a lower frequency. Swap them. The change in total cost is:

(freq_i - freq_j) * (cost_j - cost_i)

If freq_i > freq_j and cost_i > cost_j, this quantity is strictly negative — the swap always helps (or, in the case of a tie, doesn't hurt). That means any assignment that isn't sorted by frequency can be strictly improved, so the sorted assignment must be optimal. This is the classic exchange argument, the same proof structure used to justify greedy correctness in interval scheduling and Huffman coding.

One subtlety worth noting: ties don't matter. If two letters have equal frequency, swapping their slots changes the total cost by exactly zero, so any tie-breaking rule works.

And the cost structure itself has a clean closed form. With 8 keys, the cheapest 8 slots (across all keys) cost 1 press, the next 8 cost 2 presses, the next 8 cost 3 presses, and so on. If you rank all letters from most frequent (rank 0) to least frequent, the cost of the letter at rank i is:

cost(i) = i // 8 + 1

That single line is the greedy assignment, expressed as a formula. No heap, no simulation of individual keys — just rank and divide.

Brute Force Solution

Idea: Try every possible way of partitioning the distinct letters into groups of at most... well, actually there's no upper bound per key, so the "brute force" here is really trying every possible bijection between letters and cost-ranks, then computing total cost for each and taking the minimum.

Algorithm: 1. Count frequency of each distinct letter. 2. Generate every permutation of the frequency list. 3. For each permutation, assign costs 1, 1, ..., 1 (8 times), 2, 2, ..., 2 (8 times), etc., in that fixed cost order, and multiply by the permuted frequencies. 4. Take the minimum total across all permutations.

Advantages: Guaranteed correct, no need to reason about why greedy works.

Disadvantages: With up to 26 distinct letters, that's up to 26! permutations — completely infeasible. It also does a huge amount of redundant work re-deriving something the exchange argument already proves in one paragraph.

Time complexity: O(26!) — astronomically bad. Space complexity: O(26) per permutation, but the permutation count dominates everything.

Nobody would actually write this, but it's worth stating explicitly so the greedy solution's savings are obvious by contrast.

Optimal Solution

The optimal approach follows directly from the exchange argument above:

  1. Count how often each letter appears in word. Only the frequencies matter — which specific letter had which count is irrelevant, because the exchange argument only cares about relative order among weights.
  2. Sort those frequencies in descending order.
  3. Walk through the sorted list. The letter at index i (0-indexed, after sorting descending) costs i // 8 + 1 presses per occurrence.
  4. Sum frequency * cost across all distinct letters.
Rank (0-indexed) Key slot Cost per press
0–7 1st letter on each of the 8 keys 1
8–15 2nd letter on each of the 8 keys 2
16–23 3rd letter on each of the 8 keys 3
24–25 4th letter on 2 of the keys 4

This table is exactly what i // 8 + 1 computes — no key simulation needed, because the cost only depends on an index, not on which physical key you're tracking.

Worked trace: for a word with 9 distinct letters sorted descending by frequency, letters at ranks 0–7 each cost 1 (they fill all 8 keys' first slot), and the 9th letter, at rank 8, is the first to spill into the second slot — cost 2. This is also the smallest example where the greedy answer diverges from "just use real T9," since T9's fixed layout has no reason to put your most frequent letter first.

Python Code

from collections import Counter


def minimum_pushes(word: str) -> int:
    """Return the fewest total keypad presses to type `word`."""
    frequencies = sorted(Counter(word).values(), reverse=True)

    total_pushes = 0
    for rank, freq in enumerate(frequencies):
        cost_per_press = rank // 8 + 1
        total_pushes += cost_per_press * freq

    return total_pushes

Code Walkthrough

  • Counter(word) builds a frequency map of every distinct letter in word in a single O(n) pass.
  • .values() discards the letters themselves — only the multiset of frequencies matters, per the exchange argument.
  • sorted(..., reverse=True) orders frequencies from highest to lowest, which is exactly the pairing the exchange argument requires: highest weight paired with cheapest cost.
  • enumerate(frequencies) gives each frequency its rank in the sorted order — rank 0 is the most frequent letter.
  • rank // 8 + 1 converts a rank directly into a press cost, using integer division to bucket every 8 consecutive ranks into the same cost tier.
  • total_pushes += cost_per_press * freq accumulates weight × cost, which is the quantity the exchange argument proves is minimized by this exact pairing.

Complexity Analysis

  • Counting frequencies: O(n), where n is the length of word.
  • Sorting: at most 26 distinct letters, so this is O(26 log 26), a constant — effectively O(1).
  • Final pass: O(26) at most, also constant.

Total time: O(n). The alphabet cap of 26 is what makes the assignment step trivial — cost per letter is bounded by ⌈26 / 8⌉ = 4, so there's no asymptotic tension to exploit, only the ranking logic itself.

Space: O(26) for the frequency counter and sorted list — constant relative to input size.

These bounds are correct, not just "fast enough": the counting step can't be faster than O(n) because you must read every character at least once, and the sorting step is bounded by the alphabet size, not by n, so it never grows with the input.

Alternative Solutions

A bucket sort by frequency (frequencies range up to n, so O(n) buckets) can replace the comparison sort, dropping even the O(26 log 26) constant. It's not asymptotically better here, though — the alphabet is already bounded by a small constant, so there's nothing to win. It would only matter for a much larger symbol set, like Unicode-scale alphabets, where 26 stops being "small."

A heap-based approach is sometimes the instinct, especially if you're used to problems with incremental top-k queries or a changing weight set. But the weight set here is static and bounded by 26, so a single sort dominates any heap-based streaming approach. Reaching for a heap — or worse, a general assignment-problem solver like the Hungarian algorithm — misses that the cost structure is separable and monotonic in rank, which is exactly what makes plain sorting provably optimal.

Edge Cases

  • Empty word: no letters to count, frequency list is empty, total cost is 0.
  • All letters distinct, count ≤ 8: every letter lands in a 1-press slot regardless of order — the formula degrades gracefully to cost 1 without any special-casing.
  • Exactly 8 distinct letters vs. 9 distinct letters: this is the actual discontinuity boundary. At 8 letters, everyone pays 1 press. At 9, one letter spills to 2 presses. A buggy off-by-one would surface exactly here.
  • Single repeated letter ("aaaa"): one distinct letter, cost 1 per press, total equals the string length.
  • Maximum distinct letters (all 26 present): ranks 24 and 25 hit cost 4, the maximum possible cost per press in this problem.

Common Mistakes

  1. Assuming a fixed T9 layout is required. The problem lets you design the keypad — using real T9 order gives a feasible but generally suboptimal answer.
  2. Sorting ascending instead of descending. This inverts the pairing and gives the worst possible cost, not the best.
  3. Off-by-one in the cost formula, especially at the rank-7/rank-8 boundary. Rank 7 (the 8th letter) still floor-divides to 0, so its cost is 0 + 1 = 1. Rank 8 is the first to become 1 + 1 = 2.
  4. Reaching for a heap or the Hungarian algorithm out of habit. Both work, but both are asymptotic overkill for a static, small, bounded weight set — a strong interview signal is recognizing when the general tool is unnecessary.
  5. Forgetting to discard the letter identities. Tracking which specific letter maps to which key is unnecessary work — only the frequency multiset matters.

Interview Questions

  • "Why is the greedy sort provably optimal, not just a good heuristic?" — be ready to reproduce the exchange argument by hand.
  • "What changes if there are k keys instead of 8, or m letters in the alphabet instead of 26?" — the formula generalizes to cost(rank) = rank // k + 1, with max cost ⌈m / k⌉.
  • "What if each key had a hard limit on how many letters it could hold?" — this breaks the simple greedy and turns the problem into a genuine bin-packing-flavored assignment, no longer solvable by a single sort.
  • "What if press cost per rank were non-linear instead of rank // k + 1?" — as long as cost is non-decreasing in rank, the greedy-by-weight pairing and exchange argument still hold; only the closed form for cost changes.
  • "Construct a word where the fixed T9 layout diverges arbitrarily from the optimal answer." — a good self-check that you understand why T9 is just one arbitrary point in the same search space.

Key Takeaways

This problem rewards recognizing structure over memorizing a technique. Once you see it as "minimize sum of weight × cost over a free bijection," the exchange argument tells you the answer is greedy before you write a single line of code. The alphabet cap of 26 is what keeps the assignment step trivial, and the closed-form rank // 8 + 1 collapses the entire keypad simulation into one arithmetic expression. The real skill being tested isn't sorting — it's knowing when a general-purpose tool (a heap, an assignment solver) is unnecessary because the problem's structure already guarantees a simpler algorithm works.

📇 Flashcards

Word has 5 distinct letters and 5 total pushes needed — why is greedy digit-count assignment optimal?

Sort letters by frequency descending, assign 8 keys×3 slots by round-robin; most frequent letters get fewest pushes, minimizing total sum.

Time complexity of the T9-style push-minimization solution?

O(n log n) for sorting letter frequencies, where n is word length (at most 26 distinct letters).

Space complexity of this frequency-count + greedy assignment approach?

O(1) to O(26) — fixed-size frequency array/map, independent of input length.

Common bug when computing pushes per letter in this problem?

Off-by-one: push count is (index // 8) + 1, not index // 8 — forgetting the +1 undercounts every key press.

How does this greedy-by-frequency pattern compare to Huffman coding?

Same core idea — frequent items get cheaper (shorter) codes — but here cost buckets are fixed-size (3 per key) instead of a variable-depth tree.

Interview follow-up: why does key layout (8 keys, 3 letters each) not matter, only counts?

Because any bijection of letters to slots gives the same cost sum; only how many letters share each push-count tier matters.
