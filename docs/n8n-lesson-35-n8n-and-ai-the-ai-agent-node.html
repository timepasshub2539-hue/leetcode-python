n8n Lesson 35: It Forgot After 3 Messages. Here's the Fix

General

Introduction

Every "AI agent" demo you've seen — the one where someone types a sentence into a chat box and a calendar event moves, an email goes out, or a ticket gets created — is built from the same three parts. No exceptions. Once you can name those three parts and know exactly what each one does, you stop treating the n8n AI Agent node as a black box and start treating it as a wiring diagram you control.

This matters for more than just n8n users. The pattern — a reasoning model, a set of callable tools, and a memory store — is the exact same pattern behind LangChain agents, OpenAI's function calling, and every "AI assistant" product shipping right now. If you're a developer who wants to understand agentic systems, or you're prepping for interviews where "design an AI agent" shows up as a system design question, this is the mental model to have before you touch any framework.

The reason this is worth a full breakdown rather than a quick tip is that the failure modes are subtle. An agent that "forgets after three messages" doesn't look like a bug — it looks like the AI being dumb. An agent that "ignores your tool" doesn't look like a config error — it looks like the model being unreliable. Both are fixable in about thirty seconds once you know where to look.

Problem Overview

Here's the situation in plain terms: you drop a single LLM node into a workflow and send it a message. It replies in text. Ask it to check your calendar, and it answers confidently — and wrong — because it has no way to actually look at your calendar. It's a text predictor with no hands and no notepad.

Separately, even if you fix the "no hands" problem by giving it a tool, a second issue shows up a few messages later: you mention your flight time once, and two messages later the agent has no idea what you're talking about. It isn't being forgetful in a human sense — it's stateless. Every execution is a fresh start unless something explicitly carries context forward.

So the real problem is: how do you take a stateless, text-only model and turn it into something that can act in the real world and hold a coherent conversation? The answer in n8n is three attachable nodes wired into one AI Agent node: a chat model, one or more tools, and a memory node.

Example

Say you're automating flight-rescheduling requests through a chat interface.

Message 1: "My flight is at 3pm today." Agent: "Got it, I'll remember that."

Message 2: "What's the weather like?" Agent: (calls a weather tool) "Clear skies, 72°F."

Message 3: "Can you reschedule it to tomorrow?"

Without a memory node, the agent at message 3 has no idea what "it" refers to — the flight was mentioned two turns ago and nothing carried it forward. It will either hallucinate a flight, ask you to repeat yourself, or fail the tool call outright.

With a Window Buffer Memory node attached and set to retain, say, 10 prior turns, message 3 works correctly: the agent re-reads the buffered conversation, finds "flight at 3pm" from message 1, and calls the calendar tool with the right event identified.

That's the entire bug and the entire fix, in one example.

Intuition

Here's how an engineer actually arrives at this architecture, rather than memorizing it.

Start from the constraint: an LLM is a function. Text in, text out. It has no side effects, no access to your systems, and no memory between calls — each API call is independent. If you accept that constraint fully, three gaps become obvious:

  1. It can't do anything, only describe things. To close this gap, you need some mechanism where the model's text output can trigger a real action, and the result of that action can be fed back in. That's a tool — a function the model can request be called, with a description good enough for the model to know when to request it.

  2. It can't remember past calls. Each invocation is isolated. To make a conversation feel continuous, something outside the model has to store prior turns and re-inject them into every new call. That's memory — not a property of the model, but an external buffer that gets prepended to context.

  3. Something has to orchestrate the loop. The model decides it needs a tool, the system runs the tool, the result goes back to the model, the model decides what's next. This loop — read request, maybe call tool, read result, maybe call another tool, finally answer — is what the "agent" actually is. It's not a smarter model; it's a control loop wrapped around a plain model.

Once you see it this way, the n8n AI Agent node is just a UI for this control loop, and the three plug-in slots (model, tool, memory) map directly onto the three gaps above. You're not learning n8n-specific magic — you're learning the generic shape of every LLM agent.

One subtlety worth internalizing early: a tool's output comes back to the agent through the reasoning loop in the same execution, not through memory. Memory only governs what persists across separate messages. People commonly attach a Simple Memory node expecting it to help the agent use tool results — it doesn't need to, because that data is already in-flight. Memory's job is purely cross-turn continuity.

Brute Force Solution

The "brute force" here is the naive first attempt most people make: a single LLM node, no tools, no memory, and a system prompt that just says "you are a helpful assistant that manages calendars."

Idea: Trust the model to answer from its own knowledge and pretend it has access to live data.

Algorithm: 1. Receive user message. 2. Send it to the LLM with a system prompt describing its role. 3. Return the LLM's text response.

Advantages: - Trivial to build — one node, one prompt. - Fast, cheap, no external calls. - Fine for pure Q&A with no real-world grounding needed.

Disadvantages: - Cannot perform real actions — it can only generate plausible-sounding text, including confident fabrications about calendar events that don't exist. - No continuity — every message is answered in isolation, so follow-ups referencing earlier context silently fail. - Looks correct in a demo with one message, then breaks immediately in any real multi-turn, action-requiring conversation.

Complexity: O(1) per call in terms of orchestration — there's no loop, no state. That simplicity is exactly why it's insufficient: there's nothing to maintain state or branch on tool results.

Optimal Solution

The optimal structure is the three-node wiring, assembled in dependency order:

┌─────────────────┐
│   Chat Model      │  → gives the agent a brain (e.g., Claude)
│   (reasoning)      │
└────────┬─────────┘
         │
┌────────▼─────────┐
│   AI Agent Node    │  → owns the loop: call model → maybe call tool → repeat → answer
└───┬──────────┬────┘
    │          │
┌───▼───┐  ┌───▼────────┐
│ Tool(s) │  │  Memory     │  → hands to act          → notepad to remember
│(Calendar)│  │(Window Buf) │
└─────────┘  └────────────┘

Step 1 — Attach the chat model. This is the only piece required for the agent to respond at all, even with zero tools or memory attached. Pick your provider (Claude, in this case), select the credential and model, and wire it into the agent's model input. Without this, nothing downstream works.

Step 2 — Attach a tool. Take an action node (Calendar, in this case) and switch it into tool mode rather than leaving it as a direct workflow action. The description field on that tool is not documentation — it's the only signal the model uses to decide when the tool is relevant. A vague description causes two failure patterns in practice: the agent ignores the tool entirely, or, with more than one tool attached, it grabs the wrong one. Write the description the way you'd explain the tool's purpose to a new teammate in one sentence.

Step 3 — Attach memory. A Window Buffer Memory node holds the last N conversation turns and feeds them back into every new model call. The size of N is a tuning knob, not a correctness parameter: too small and context like "my flight is at 3pm" falls out of the window after a few turns; too large and every call drags unnecessary tokens (and cost) along for the ride. Ten or so turns is a reasonable default for short, task-focused conversations.

The resulting execution, per message: the agent reads the request → decides if a tool is needed → if yes, calls it and reads the result → decides if another tool is needed or if it's ready to answer → returns a final answer, with the full exchange appended to memory for the next turn.

Python Code

n8n is low-code, but the underlying control loop is just a few lines of Python if you were wiring it yourself — useful to see once, because it demystifies what the node is doing internally.

from dataclasses import dataclass, field


@dataclass
class Memory:
    """Fixed-size window buffer of (role, content) turns."""
    max_turns: int = 10
    turns: list = field(default_factory=list)

    def add(self, role: str, content: str) -> None:
        self.turns.append((role, content))
        self.turns = self.turns[-self.max_turns:]

    def as_context(self) -> list:
        return [{"role": role, "content": content} for role, content in self.turns]


def run_agent(user_message: str, memory: Memory, tools: dict, call_model) -> str:
    """
    One agent turn: reasoning loop over model calls and tool calls.
    `call_model` is a function(messages, tools) -> model response.
    `tools` maps tool name -> callable.
    """
    memory.add("user", user_message)
    messages = memory.as_context()

    while True:
        response = call_model(messages, tools=list(tools.keys()))

        if response.get("tool_call") is None:
            memory.add("assistant", response["text"])
            return response["text"]

        tool_name = response["tool_call"]["name"]
        tool_args = response["tool_call"]["args"]
        tool_result = tools[tool_name](**tool_args)

        # Tool result feeds back into THIS execution's loop, not into memory directly.
        messages.append({"role": "assistant", "content": f"called {tool_name}"})
        messages.append({"role": "tool", "content": str(tool_result)})

Code Walkthrough

  • Memory is the Window Buffer Memory node in code form: a fixed-size list of turns, with add trimming to max_turns so old context ages out instead of growing unbounded.
  • as_context is what gets prepended to every new model call — this is literally how "remembering the flight time two messages later" works. Nothing fancier than re-sending recent history.
  • run_agent is the AI Agent node's control loop. It adds the new user message to memory, then enters a loop: ask the model, check if it requested a tool, and if so, run that tool and feed the result back in as additional context within the same loop — not through memory. The loop only exits when the model returns plain text instead of a tool call.
  • tools is a dict of name → function, standing in for attaching a Calendar node (or any node) in tool mode. The model picks a name; your code (or n8n) executes the matching function.
  • Note what's not in this code: there's no special handling for "remembering the tool result." That's the point the transcript makes — tool output is already live in messages for this turn. Memory's job starts and ends at carrying conversation turns across separate calls to run_agent.

Dry Run

Using the flight example, with max_turns=10:

Turn 1: user_message = "My flight is at 3pm today." - memory.add("user", ...) → turns = [("user", "My flight is at 3pm today.")] - Model sees this, has no tool to call, responds "Got it." - memory.add("assistant", "Got it.") → turns now has 2 entries.

Turn 2: user_message = "What's the weather like?" - memory.as_context() returns both prior turns plus this one. - Model requests weather_tool(). Loop executes it, result ("Clear, 72°F") appended to messages for this turn only. - Model responds "Clear skies, 72°F." Memory now has 4 entries.

Turn 3: user_message = "Can you reschedule it to tomorrow?" - memory.as_context() includes turn 1 — "My flight is at 3pm today." is still inside the 10-turn window. - Model resolves "it" to the flight, requests calendar_tool(event="flight", new_time="tomorrow"). - Loop executes it, gets a confirmation, model responds with the reschedule confirmation.

Without the memory buffer, turn 3's messages would contain only the current message, "it" would have no referent, and the model would either ask for clarification or guess wrong.

Complexity Analysis

  • Time: Each agent turn costs O(k) model calls, where k is the number of tool calls needed before a final answer (typically 1–3 in practice). Each call's cost scales with context length, which is bounded by max_turns — so time per turn is O(max_turns + k).
  • Space: Memory storage is O(max_turns), since the buffer is capped and old turns are evicted. This is why windowing matters — unbounded memory would make space (and per-call cost) grow linearly with conversation length forever.
  • Why these are correct: the cap on max_turns is a deliberate trade, not an oversight — it bounds both token cost and latency at the price of a hard recall limit. For short task-oriented conversations (the common case for automation agents), this trade is correct; for long-running conversations needing full recall, you'd swap the window buffer for a retrieval-based memory (see below).

Alternative Solutions

  • Summarization memory instead of a raw window: instead of storing the last N turns verbatim, periodically summarize older turns into a condensed note. This trades some fidelity for a much longer effective memory span at the same token cost — useful if conversations regularly run past 10–15 turns.
  • Vector-store / retrieval memory: store all turns, embed them, and retrieve only the ones relevant to the current message. This scales to arbitrarily long conversations but adds latency (an embedding + search step) and complexity that's overkill for most short automation workflows.
  • No memory, full context replay: send the entire conversation history every time. Simple, but cost grows unbounded with conversation length — the window buffer exists specifically to avoid this.

For the flight-rescheduling use case, the window buffer is the right call: conversations are short, and the added complexity of retrieval memory buys nothing.

Edge Cases

  • Empty input — an agent invoked with no message or empty string should short-circuit rather than call the model; otherwise you're burning a model call on nothing.
  • Tool returns an error — if the Calendar API fails, the agent needs that failure surfaced as a tool result (not silently swallowed), so the model can inform the user rather than hallucinate success.
  • Multiple tools with overlapping purposes — two tools with similar descriptions (e.g., "Calendar" and "Scheduler") will cause the model to pick inconsistently; descriptions must be distinct enough to disambiguate.
  • Memory window exactly at the boundary — information mentioned exactly max_turns turns ago will be evicted on the next turn; if a workflow regularly needs longer recall, the window size is undersized for that workflow, not a bug in the mechanism.
  • Concurrent sessions sharing one memory node — if the memory isn't keyed per conversation/session ID, two different users' conversations will bleed into each other's context.

Common Mistakes

  1. Attaching Simple Memory and expecting it to carry tool results within a turn — it doesn't need to; that's already handled by the in-execution reasoning loop.
  2. Leaving a tool's description vague or generic ("handles calendar stuff") — the model has nothing else to go on when deciding relevance, and will misfire with multiple tools attached.
  3. Setting the memory window too large "to be safe" — it inflates token cost and latency on every single call for no benefit in short conversations.
  4. Forgetting the chat model node entirely and wondering why the agent doesn't respond at all — the model is the one truly mandatory piece; tools and memory are optional add-ons on top of it.
  5. Assuming the agent "understood" something after one tool call without testing a multi-turn follow-up — memory bugs only show up two or three messages later, so single-message testing hides them completely.

Interview Questions

  • "How would you design memory for a conversational agent that needs to scale to thousands of concurrent users?" (keying memory per session, eviction policy, storage backend)
  • "What's the difference between a tool result and conversational memory, and why does that distinction matter?"
  • "How do you prevent an agent from calling the wrong tool when several are available?" (description quality, tool naming, possibly a routing step before the agent)
  • "What happens to cost and latency as conversation length grows, and how do you bound it?"
  • "Design a fallback for when a tool call fails mid-conversation — what should the agent do?"

  • Function-calling / Tool-use design in any LLM SDK (OpenAI, Anthropic) — the exact same model-decides-when-to-call-a-function pattern underlying the n8n tool node.

Key Takeaways

An AI agent is not a smarter model — it's a plain model wrapped in three attachments: a chat model to reason, tools to act on the real world, and memory to stay coherent across turns. Tool results flow back into the model within the same execution; memory's only job is carrying context across separate messages. Get the tool description specific and the memory window sized to the conversation length you actually expect, and this exact three-part wiring handles any agent you build next — just swap the model, the tool, or both.

n8n AI Agent node: what three things does it wire together?

LLM (brain), tools (hands), and memory (notepad) — combined into one agentic automation node.

Why can't a plain LLM node take real actions?

It can only generate text/talk; it has no way to call an external action — needs a tool connected to actually do something.

Who decides which tool to call and when, in an AI Agent setup?

The model decides; n8n just executes whatever action the model chooses to call.

Common bug: agent 'forgot' something said 3 messages ago. Cause?

No memory node wired in — without it, each run has no conversation history, so context is lost between messages.

Setting up an AI Agent node: what's step one vs step two?

Step one: wire in a model (the LLM connection). Step two: add tool(s) the model can call to act.

AI Agent node vs plain LLM/Chat node — key difference?

Plain LLM only replies with text; AI Agent can reason, pick a tool, call it, and use memory for context across turns.
