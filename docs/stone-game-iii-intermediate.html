Stone Game III — 🟡 Intermediate (2/3) — LeetCode Daily Python Solution (the trick nobody sees)

General

Introduction

Every so often a LeetCode problem shows up wearing a costume — it looks like a game, it talks like a game, but underneath it's a completely standard dynamic programming problem waiting for the right lens. Stone Game III is one of those. It gets asked in interviews not because the final code is long (it isn't — about ten lines) but because it tests whether you can resist the obvious wrong idea: simulating both players' scores separately.

If you've solved single-player DP problems before — climbing stairs, house robber, coin change — you already have every tool you need here. What's missing is a mental trick that collapses a two-player adversarial game into the same one-array, one-loop shape you already know. Once you see it, you'll recognize the pattern instantly in Stone Game II, Predict the Winner, and a handful of other "two players take turns" interview questions.

Problem Overview

You're given a row of stones, each with a point value (values can be negative). Alice and Bob take turns removing stones from the front of the row — Alice goes first. On each turn, a player must take exactly 1, 2, or 3 stones, and the sum of what they take is added to their own score.

Both players play optimally — meaning each one always makes the move that maximizes their own final advantage, not just their next move's value. After all stones are gone, compare the two scores: whoever has more points wins. If the scores are equal, it's a tie.

The row can contain up to 50,000 stones, which immediately rules out any brute-force or exponential recursive approach — you need something that runs in linear time.

Example

Take the row [1, 2, 3, 7].

The tempting move is for Alice to grab the three biggest values she can reach — take 1, 2, 3 in her first turn, banking 6 points. But that leaves the entire remaining row — just the 7 — for Bob. Bob wins 7 to 6.

Alice taking more stones actually cost her the game. That's the whole trap this problem is built around: point totals don't scale with stone count, especially once you allow negative values into the row.

Now compare with [1, 2, 3, 6]. Play it out by hand: no matter what Alice opens with, she can't force a win — her best outcome is a tie.

And with [1, 2, 3, -9], Alice's best move is grabbing all three positive piles up front (1+2+3=6), leaving Bob stuck with -9. Alice wins by a wide margin.

Same rules, three different outcomes — because the right move depends on the shape of the remaining row, not on greedily grabbing whatever's biggest right now.

Intuition

The naive way to approach this is to simulate the actual game: recurse on "what if I take 1 stone," "what if I take 2," "what if I take 3," and at each step track Alice's score and Bob's score as two separate running totals. That's exactly what most people write first — it mirrors the problem statement almost word for word. It also runs into two problems immediately: it's exponential (three branches at every stone), and juggling two score variables makes the code messy and error-prone.

Here's the reframe that fixes both problems at once. The only thing that determines who wins is the difference between the two scores — not their individual values. So instead of tracking Alice's score and Bond's score, track a single number: the best lead the current player can build over the other player, assuming both play perfectly from this point onward.

Call this dp[i] — the best score gap achievable by whoever is about to move, starting from index i in the row. The beauty of this framing is that it doesn't need to know whether "whoever is about to move" is Alice or Bob. The same recurrence works for both, because from the perspective of "the player whose turn it is," the game always looks identical: take some stones, then let your opponent play optimally against what's left.

This is the Score Gap trick. It turns a two-player adversarial game into an ordinary single-player optimization problem — the same shape as any other 1D DP problem, just with one twist in the recurrence.

Brute Force Solution

Idea: Recursively simulate every possible sequence of moves. At each turn, try taking 1, 2, or 3 stones, track each player's score independently, and recurse into the remaining row for the other player.

Algorithm: 1. Define a recursive function that takes the current index and whose turn it is. 2. Try all three possible take counts, recursing after each. 3. Compare Alice's final score to Bob's final score.

Advantages: Directly mirrors the problem statement; easy to reason about correctness for tiny inputs.

Disadvantages: Branches three ways at every stone with no memoization, giving roughly O(3^n) time. Completely unusable once the row has more than a few dozen stones, let alone 50,000.

Complexity: O(3^n) time, O(n) space (recursion stack).

Optimal Solution

We fill a DP array from the back of the row toward the front, because dp[i] depends on dp[i+1], dp[i+2], and dp[i+3] — states that lie further along the row. That means the last stone's outcome has to be known before we can compute anything about the stones before it.

Setup: dp has n + 1 slots — one per stone, plus one extra slot at index n representing the empty row, which is worth 0 (nobody left to take anything, gap is zero).

Recurrence: For each index i, walking backward from n - 1 to 0:

dp[i] = max over k in {1, 2, 3} of:
    (sum of stones[i .. i+k-1]) - dp[i + k]

Read it like this: whatever the current player takes gets added straight to their advantage. Then, because the opponent gets to play the rest of the row optimally, their best gap gets subtracted — it works against us, since every point they gain is a point off our lead.

Index Stones taken Running sum Subtract dp[i+k] Candidate gap
i 1 stone stones[i] dp[i+1] sum − dp[i+1]
i 2 stones +stones[i+1] dp[i+2] sum − dp[i+2]
i 3 stones +stones[i+2] dp[i+3] sum − dp[i+3]

dp[i] takes the best (maximum) of those three candidates.

Final answer: dp[0] is Alice's best possible lead over Bob across the entire row, since she moves first.

  • dp[0] > 0 → Alice wins
  • dp[0] < 0 → Bob wins
  • dp[0] == 0 → tie

Python Code

from typing import List


def stone_game_iii(stone_values: List[int]) -> str:
    n = len(stone_values)
    # dp[i] = best score gap the player to move can achieve from index i onward
    # dp[n] = 0: empty row, no gap to fight over
    dp = [0] * (n + 1)

    for i in range(n - 1, -1, -1):
        best = float("-inf")
        running_take = 0
        for k in range(1, 4):  # take 1, 2, or 3 stones
            if i + k - 1 >= n:
                break
            running_take += stone_values[i + k - 1]
            best = max(best, running_take - dp[i + k])
        dp[i] = best

    if dp[0] > 0:
        return "Alice"
    if dp[0] < 0:
        return "Bob"
    return "Tie"

Code Walkthrough

  • dp = [0] * (n + 1) — one slot per stone plus the empty-row sentinel at index n, which stays 0.
  • for i in range(n - 1, -1, -1) — the backward loop. Every dp[i] depends on positions ahead of i, so those must already be filled before we compute dp[i].
  • running_take — accumulates the value of the stones taken in this candidate move (1, then 2, then 3 stones) without recomputing a sum from scratch each time.
  • if i + k - 1 >= n: break — guards against reading past the end of the row when fewer than 3 stones remain.
  • best - dp[i + k] — the core of the trick: what you gained minus what your opponent can gain afterward.
  • dp[i] = best — store the best achievable gap for whoever is to move from index i.
  • The final if/elif/else on dp[0] reads the sign straight into the winner.

Dry Run

Row: [1, 2, 3, 7], so n = 4.

  • dp[4] = 0 (empty row)
  • dp[3]: only option is taking the 1 stone at index 3 → 7 - dp[4] = 7 - 0 = 7. dp[3] = 7
  • dp[2]: take 1 (value 3) → 3 - dp[3] = 3 - 7 = -4. Take 2 (3+7=10) → 10 - dp[4] = 10. Best = 10. dp[2] = 10
  • dp[1]: take 1 (2) → 2 - dp[2] = 2 - 10 = -8. Take 2 (2+3=5) → 5 - dp[3] = 5 - 7 = -2. Take 3 (2+3+7=12) → 12 - dp[4] = 12. Best = 12. dp[1] = 12
  • dp[0]: take 1 (1) → 1 - dp[1] = 1 - 12 = -11. Take 2 (1+2=3) → 3 - dp[2] = 3 - 10 = -7. Take 3 (1+2+3=6) → 6 - dp[3] = 6 - 7 = -1. Best = -1. dp[0] = -1

dp[0] = -1 is negative, so Bob wins — matching what we saw by hand: Alice grabs 6 points, Bob takes the 7, Bob wins by 1.

Complexity Analysis

  • Time: O(n) — the outer loop runs once per stone, and the inner loop is capped at 3 iterations regardless of n, so the total work is linear.
  • Space: O(n) — one DP array of size n + 1. This can be trimmed to O(1) with a sliding window of the last 3 values, but O(n) is already comfortably fast enough for the 50,000-stone constraint and much easier to read.

Both bounds are correct because every dp[i] is computed exactly once and only reads values that are already finalized (indices i+1 through i+3), so there's no redundant recomputation anywhere in the loop.

Alternative Solutions

Top-down recursion with memoization is a reasonable alternative: recurse from index i, cache the result in a dictionary or array, and let Python handle the backward dependency implicitly through the call stack. It reads a bit closer to the plain English rules of the game, since you're not manually reasoning about fill order.

The tradeoff is recursion depth. With rows up to 50,000 stones, a naive recursive solution risks hitting Python's recursion limit, and function call overhead makes it noticeably slower than the iterative version in practice. For this specific problem, the bottom-up loop is the one to ship — it has the same time and space complexity with none of the recursion-limit risk.

Edge Cases

  • Single stone (n = 1): Alice takes it, no computation needed — dp[0] correctly resolves to stones[0] - dp[1] = stones[0].
  • All negative values: The DP still finds the ending that loses the least; there's no assumption anywhere that values are positive.
  • Exact tie: If both players' optimal play lands on equal scores, dp[0] comes out to exactly 0, and the code correctly returns a tie rather than defaulting to either player.
  • Empty row handled implicitly: dp[n] = 0 is what makes the very first backward step correct — skipping this slot is a common bug (see below).
  • Large input (n = 50,000): Because this is a single backward loop with no recursion, it scales safely to the full constraint with no stack risk.

Common Mistakes

  1. Tracking Alice's and Bob's scores separately. This forces you to maintain two arrays or two variables for a game that only ever cares about their difference — unnecessary complexity that also makes memoization harder to reason about.
  2. Sizing the DP array to exactly n instead of n + 1. Forgetting the extra slot for the empty row breaks the very first backward step, since dp[n] needs to exist and equal 0.
  3. Assuming taking more stones is always better. This breaks the moment a large value sits just out of reach, or a negative value shows up in the row you're about to hand your opponent.
  4. Filling the DP array left to right. Since dp[i] depends on dp[i+1], dp[i+2], dp[i+3], filling forward reads uninitialized future states.
  5. Forgetting to bounds-check when fewer than 3 stones remain. Without the i + k - 1 >= n guard, the loop reads past the end of the stones list near the tail of the row.

Interview Questions

  • Why does subtracting dp[i+k] correctly model an adversarial opponent, rather than just adding their best score?
  • How would you reduce the space complexity from O(n) to O(1)?
  • What changes if a player can take between 1 and k stones instead of a fixed 1–3?
  • How would you also return the actual sequence of moves, not just the winner?
  • Why is top-down recursion with memoization risky here, and how would you convert it to iterative form generically?

Key Takeaways

Stone Game III isn't hard because the code is long — it's ten lines. It's hard because the obvious first instinct (simulate both scores) is exponential and messy, while the right instinct (track just the gap) turns it into ordinary single-player DP. Fill backward, one number per index, best lead achievable from taking 1, 2, or 3 stones. Read the sign at dp[0] and you already know the winner. Score Gap DP — once you see it here, you'll spot it in the next game-theory DP problem immediately.

📇 Flashcards

Stone Game III: what pattern do you reach for?

DP with lookahead — dp[i] = max score current player can force from pile i onward, trying take 1/2/3.

Time complexity of the Stone Game III DP?

O(n) — one pass right-to-left, constant work (3 choices) per index.

Space complexity, and how to cut it further?

O(n) for the dp array; can drop to O(1) with a 3-slot rolling window since dp[i] only needs the next 3 values.

Trickiest bug when coding this DP?

Storing raw pile sum instead of score DIFFERENCE (current player's edge); forgetting the difference flips sign each recursive call.

Stone Game III vs simple 'take biggest pile' greedy?

Greedy fails — taking the biggest pile ignores what it hands the opponent next; DP evaluates all 3 take-counts against optimal opponent play.

Interview follow-up: why 1/2/3 stones, not simulate every full game?

Simulating every turn sequence is exponential; DP collapses it to one state per starting index since only 3 next-moves matter.
