Predict the Winner — 🟡 Intermediate (2/3) — LeetCode Daily Python Solution (the trick nobody sees)

General

Introduction

Predict the Winner shows up on interview lists because it looks nothing like a "standard" DP problem until you find the right lens. On the surface it's a two-player game — pick from either end of an array, both play optimally, does Player 1 come out ahead? That framing tempts most people into simulating the entire game: tracking Player 1's score, Player 2's score, and every possible sequence of moves. It technically works, and it technically explodes.

What interviewers are actually testing here is whether you can spot a state reduction. Two running totals sound necessary until you realize the only thing that matters is the gap between them. That single insight — collapsing two tracked values into one — is a pattern that shows up constantly in game-theory DP problems, and once you've internalized it here, you'll recognize it everywhere else it hides.

Problem Overview

You're given an array of non-negative integers. Two players alternate turns, Player 1 going first. On each turn, a player removes either the leftmost or the rightmost number from the array and adds it to their own score. This continues until the array is empty. Both players play optimally — meaning each one always makes the move that maximizes their own final score, assuming the other player will do the same.

The question isn't "who wins by more" or "play out the game." It's a yes/no question: can Player 1 guarantee a final score that is greater than or equal to Player 2's? A tie counts as Player 1 winning — that detail matters more than it seems, and it's a common place solutions quietly go wrong.

Example

Take nums = [1, 5, 2].

Player 1's options are 1 (left) or 2 (right). Suppose Player 1 grabs 2. Now the array is [1, 5], and Player 2 plays optimally — they take 5, leaving Player 1 stuck with 1. Final score: Player 1 has 2 + 1 = 3, Player 2 has 5. Player 1 loses.

Try the other first move: Player 1 grabs 1. Array becomes [5, 2]. Player 2 takes 5, Player 1 is left with 2. Final score: Player 1 has 3, Player 2 has 5. Still a loss.

Either way, Player 1 loses — grabbing the "bigger" number first doesn't save you, because it hands your opponent a better follow-up position. That's the core tension the algorithm has to capture: a move's value depends on what it lets the opponent do next, not just what it gives you now.

Intuition

The natural first instinct is to simulate: write a recursive function where each player tries both ends, recurses on the smaller subarray, and tracks their own running score against the opponent's. This is a classic minimax — two sides, one resource, each optimizing for themselves while accounting for the other's optimal response.

The problem is that tracking two separate scores means your recursive state has to somehow encode "whose turn is it and what has each side accumulated so far," which balloons quickly. But here's the reframe: you don't actually care about either player's absolute score. You only care whether Player 1's score minus Player 2's score is zero or positive.

So define diff(i, j) as the best score difference the current player (whoever's turn it is on subarray nums[i..j]) can force over their opponent, playing both optimally. If the current player takes the left end, they gain nums[i], but now it's the opponent's turn on nums[i+1..j], and whatever difference the opponent forces there works against the current player. So the net contribution of taking the left is nums[i] - diff(i+1, j). Same logic for taking the right: nums[j] - diff(i, j-1). The current player picks whichever is larger, because they're optimizing for themselves too.

One number — the difference — now fully represents a two-player game. If diff(0, n-1) >= 0, Player 1 can force at least a tie, and the tie counts as a win.

Brute Force Solution

Idea: Recursively compute diff(i, j) for every subarray by trying both ends.

Algorithm: 1. Base case: if i == j, return nums[i] — no choice with one element. 2. Otherwise, return max(nums[i] - diff(i+1, j), nums[j] - diff(i, j-1)). 3. Player 1 wins if diff(0, n-1) >= 0.

Advantages: Directly mirrors the game logic — easy to reason about and verify against the problem statement.

Disadvantages: The same (i, j) range gets recomputed repeatedly from different call paths (overlapping subproblems), so runtime grows exponentially.

Complexity: Time O(2ⁿ), space O(n) for the recursion stack.

Optimal Solution

The recursion above has two things that scream "dynamic programming": overlapping subproblems (the same diff(i, j) gets asked for repeatedly) and optimal substructure (the best answer for a range depends only on the best answers for smaller ranges inside it). That means we can fill a table once and never recompute anything.

Build a 2D table dp where dp[i][j] holds diff(i, j). Fill it in order of increasing subarray length, since every cell depends only on smaller subarrays:

Step What's filled Depends on
Length 1 dp[i][i] = nums[i] Nothing — base case
Length 2 dp[i][i+1] Two length-1 cells
Length k dp[i][i+k-1] dp[i+1][j] and dp[i][j-1]
Length n dp[0][n-1] Final answer

Once the table is fully built, dp[0][n-1] is the best score difference Player 1 can force over the whole array. If it's zero or positive, Player 1 wins.

Python Code

def predict_the_winner(nums: list[int]) -> bool:
    n = len(nums)
    if n <= 1:
        return True

    # dp[i][j] = best score difference the current player can force
    # over their opponent on the subarray nums[i:j+1]
    dp = [[0] * n for _ in range(n)]

    # Base case: single-element subarrays have no choice
    for i in range(n):
        dp[i][i] = nums[i]

    # Fill by increasing subarray length
    for length in range(2, n + 1):
        for i in range(n - length + 1):
            j = i + length - 1
            take_left = nums[i] - dp[i + 1][j]
            take_right = nums[j] - dp[i][j - 1]
            dp[i][j] = max(take_left, take_right)

    return dp[0][n - 1] >= 0

Code Walkthrough

  • n <= 1: a single-element array is a trivial win — Player 1 takes the only number, Player 2 gets nothing.
  • dp = [[0] * n for _ in range(n)]: a full n x n table, though only the upper triangle (i <= j) is ever used.
  • The first loop fills the diagonal — every length-1 subarray's best difference is just that element, since there's no decision to make.
  • The nested loop grows the window length from 2 up to n, and for each starting index i, computes the ending index j.
  • take_left and take_right mirror the recurrence exactly: gain the picked value, then subtract whatever difference the opponent can force on the remaining subarray.
  • dp[i][j] = max(...): the current player always picks the better of the two options, because they're playing optimally too.
  • The final check, dp[0][n-1] >= 0, answers the actual question — can Player 1 force a tie or better.

Dry Run

Using nums = [1, 5, 233, 7]:

Length 1 (diagonal): dp[0][0]=1, dp[1][1]=5, dp[2][2]=233, dp[3][3]=7.

Length 2: - dp[0][1] = max(1-5, 5-1) = 4 - dp[1][2] = max(5-233, 233-5) = 228 - dp[2][3] = max(233-7, 7-233) = 226

Length 3: - dp[0][2] = max(1-228, 233-4) = 229 - dp[1][3] = max(5-226, 7-228) = -221

Length 4: - dp[0][3] = max(nums[0]-dp[1][3], nums[3]-dp[0][2]) = max(1-(-221), 7-229) = max(222, -222) = 222

dp[0][3] = 222 >= 0, so predict_the_winner([1, 5, 233, 7]) returns True.

Complexity Analysis

Time: O(n²) — the table has O(n²) cells and each is filled in constant time.

Space: O(n²) for the table. This is correct and unavoidable in the bottom-up version because every cell can be referenced by a longer subarray later, so nothing can be discarded early.

Alternative Solutions

You can implement the exact same recurrence top-down, using recursion plus a cache (functools.lru_cache or a manual dictionary/2D array):

from functools import lru_cache

def predict_the_winner(nums: list[int]) -> bool:
    @lru_cache(maxsize=None)
    def diff(i, j):
        if i == j:
            return nums[i]
        return max(nums[i] - diff(i + 1, j), nums[j] - diff(i, j - 1))

    return diff(0, len(nums) - 1) >= 0

This is arguably easier to read since it mirrors the recursive definition directly. For the problem's constraint (n up to 20), both approaches perform identically in practice. The bottom-up table is the safer default because it sidesteps Python's recursion limit entirely — a non-issue at n=20, but a habit worth keeping for problems where input size isn't guaranteed small.

Edge Cases

  • Single-element array: returns True trivially — Player 1 takes the only number.
  • All zeros: every diff comes out to 0, which still satisfies >= 0, still a win for Player 1.
  • All equal values: same result — any tie-producing configuration still returns True.
  • Two elements: reduces to a direct comparison, max(nums[0]-nums[1], nums[1]-nums[0]) >= 0, which is always true since one of those is non-negative.
  • Large values: Python integers don't overflow, so there's no need to worry about the input constraint's upper bound.

Common Mistakes

  1. Checking for strictly greater than instead of greater-or-equal — forgetting the problem explicitly counts a tie as a Player 1 win.
  2. Greedily picking the larger end value without accounting for what it leaves the opponent — this is exactly the trap in [1, 5, 2].
  3. Subtracting the wrong subrange — using diff(i, j-1) when taking the left end, or diff(i+1, j) when taking the right, which silently flips whose turn is being modeled.
  4. Filling the table in the wrong order — iterating i and j directly instead of by increasing subarray length, which reads uninitialized cells.
  5. Tracking two separate running scores instead of the difference — not wrong, just needlessly complex, and much easier to get backwards.

Interview Questions

  • Can you extend this to more than two players, or a non-alternating turn order?
  • What happens if a player can take from more than just the two ends — say, any of the first three elements?
  • Can you reduce the space complexity from O(n²) to O(n) using rolling arrays? (Yes — since each row only depends on the row below it and itself, you can compress it, though the diagonal-fill order takes care.)
  • How would you modify this if the scoring weight for each number depended on which turn it was taken on?
  • Why does the top-down and bottom-up version have the same time complexity despite different execution orders?

Key Takeaways

The real lesson isn't the specific recurrence — it's the reduction. Whenever a problem asks you to track two competing quantities that only matter relative to each other, check if collapsing them into a single difference simplifies the state. Combined with recognizing overlapping subproblems in the naive recursion, that's the whole path from an exponential brute force to a clean O(n²) interval DP.

📇 Flashcards

Two-player alternating game on an array — what pattern applies?

Game theory DP: compute score difference (current − opponent) via dp[i][j] = max of choosing either end minus opponent's best.

Time complexity for Predict the Winner DP?

O(n²) — filling an n×n table over subarray ranges [i,j].

Space complexity, and how to cut it?

O(n²) for the table; reducible to O(n) with a 1D rolling array since dp[i] only needs the previous row.

Common bug when defining dp[i][j] in this problem?

Mixing up 'max score for player 1' vs 'score difference'; must track relative advantage, not absolute score, or recursion breaks.

Predict the Winner vs Stone Game — key difference?

Same DP shape; Stone Game guarantees first player wins with even piles, Predict the Winner requires proving it generally via diff >= 0.

Interview follow-up: how to handle very large n efficiently?

Use the O(n) space rolling-array optimization; recursion with memoization also works but risks stack depth on large n.
