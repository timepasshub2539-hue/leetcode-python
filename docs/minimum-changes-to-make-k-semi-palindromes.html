2911. Minimum Changes to Make K Semi-palindromes

General ✓ Runtime tested

Introduction

Every so often LeetCode throws out a problem that looks like a palindrome question on the surface but is actually testing something else entirely: your ability to combine two separate algorithmic ideas into one clean solution. 2911. Minimum Changes to Make K Semi-Palindromes is exactly that kind of problem. It borrows the "cost to make a substring a palindrome" idea that shows up constantly in interview prep, bends the definition of palindrome into something unfamiliar, and then wraps the whole thing in a partition DP.

Interviewers like this problem for a specific reason: it rewards engineers who can decompose a hard problem into two independent, well-understood pieces — a cost function and a partitioning DP — rather than trying to solve everything in one pass. If you've ever worked through "Palindrome Partitioning II" or similar splitting problems, this is the natural next step up in difficulty. Learning it sharpens a pattern you'll reuse constantly: precompute a cost table over all substrings, then run a DP over partition points on top of it.

Problem Overview

You're given a string s and an integer k. Your job is to split s into exactly k contiguous pieces. Each piece doesn't need to already be anything special — but you're allowed to change individual characters in it until it becomes what the problem calls a semi-palindrome.

A semi-palindrome is defined relative to some divisor d that is strictly less than the string's length and evenly divides it. Once you pick d, you don't slice the string into blocks of size d. Instead, you group characters by their index modulo d — every index that lands in the same residue class joins the same group. Each of those groups, read on its own, must be a palindrome.

Your goal: choose the split points and, for each resulting piece, the number of character changes needed to make it a valid semi-palindrome for the best possible d, such that the total number of changes across all k pieces is as small as possible.

Example

Take s = "abaacaba". Group by index mod 2 (so d = 2):

  • Group starting at index 0: positions 0, 2, 4, 6 → a, a, c, b
  • Group starting at index 1: positions 1, 3, 5, 7 → b, a, a, a

Wait — check with the actual string a-b-a-a-c-a-b-a. Indices 0..7: a(0) b(1) a(2) a(3) c(4) a(5) b(6) a(7).

  • mod 2 == 0: indices 0,2,4,6 → a, a, c, b
  • mod 2 == 1: indices 1,3,5,7 → b, a, a, a

Neither group is a palindrome as written here, which is exactly why cost matters — you compute how many swaps-via-change it takes to make each group read the same forwards and backwards, by comparing each character to its mirror across the group's center. For a group like b, a, a, a, the first and last characters (b and a) don't match, so that's one change. The middle two (a, a) already match. That's a cost of 1 for this group at this d.

You'd repeat this for every valid divisor of the substring's length and keep whichever d gives the lowest total — that's the "cost" of turning that one substring into a semi-palindrome.

Intuition

The instinct that trips most people up first is treating d like a chunk size — "split the string into blocks of length d." That's wrong, and it's wrong in a way that's easy to miss because nearly every other string-partitioning problem does mean contiguous blocks. Here, d is a stride. You're grouping indices that are congruent modulo d, so index 0 pairs with index d, which pairs with index 2d, and so on, all living in the same group. That's the "interleaving" that makes a semi-palindrome genuinely different from a regular one.

Once you internalize that d is a residue-class grouping rather than a slice width, the rest of the intuition falls into place in two separate layers:

  1. Local layer — cost of one piece. For any single substring, try every valid divisor d of its length (where d is strictly less than the length), build the d interleaved groups, and count mismatches against each group's own reverse. Keep the cheapest d. This gives you one number: the minimum changes to make that exact substring a semi-palindrome.
  2. Global layer — where to cut. Once every substring has a known cost, the problem becomes "pick k - 1 cut points in the string to minimize the sum of the costs of the resulting k pieces." That's a textbook partition DP, the same shape as palindrome partitioning problems, just fed by a different cost function.

The key insight that makes the combination efficient: each substring's cost is fixed — it doesn't depend on what the other pieces look like. So you never need to recompute it inside the DP. Compute it once per substring, store it in a table, and let the DP only worry about where to cut.

Brute Force Solution

Idea: Try every way to split the string into k contiguous non-empty pieces, and for each piece, try every valid divisor d to find its true minimum semi-palindrome cost, then sum.

Algorithm: 1. Enumerate every combination of k - 1 cut points among n - 1 possible gaps. 2. For each resulting set of k pieces, compute the real cost of each piece by checking every divisor (not skipping any, not caching anything). 3. Sum the costs for that split and track the global minimum across all splits.

Advantages: Trivial to reason about correctness — it's a literal transcription of the problem statement.

Disadvantages: The number of ways to place k - 1 cuts among n - 1 gaps is combinatorial, and if you don't cache substring costs, the same substring's cost often gets recomputed many times across different splits. A naive version that always assumes d = 1 (as the earlier walkthrough in the source material shows with "cac") can also silently produce wrong-but-plausible-looking answers, since d = 1 happens to be correct on some substrings by luck, not by rule.

Time complexity: Exponential in the number of cut combinations, multiplied by the cost of recomputing each piece's cost from scratch — far too slow once n approaches 200.

Space complexity: Low if done recursively without memoization, but that's precisely what makes it slow.

Optimal Solution

The optimal approach separates the problem into exactly the two layers the intuition section described.

Step 1 — Build a cost table. For every pair of indices (i, j) with i <= j, compute cost[i][j]: the minimum number of changes needed to turn s[i..j] into a semi-palindrome. A single character costs 0 automatically. For longer substrings, loop over every d from 1 to length−1, skip any d that doesn't evenly divide the length, build each of the d interleaved groups, count character mismatches against each group's own reverse, and keep the smallest total across all valid d.

Substring length Valid divisors d tried
1 none (cost is 0)
4 1, 2
6 1, 2, 3
8 1, 2, 4

Step 2 — Partition DP on top. Define dp[i][kk] as the minimum total changes to split the first i characters of s into exactly kk pieces. The base case is dp[0][0] = 0 — zero characters, zero pieces, zero cost. Everything else starts at infinity. Transition: for every earlier cut point j, dp[i][kk] = min(dp[i][kk], dp[j][kk-1] + cost[j][i-1]) — finish kk - 1 pieces up to j, then pay for one more piece spanning from j to i - 1. The final answer lives at dp[n][k].

This is the same "precompute, then partition" shape used in many palindrome-partitioning problems — the only thing that changed is what "cost of a piece" means.

Python Code

class Solution:
    def minimumChanges(self, s: str, k: int) -> int:
        n = len(s)

        def cost(i: int, j: int) -> int:
            """Minimum changes to make s[i..j] a semi-palindrome."""
            m = j - i + 1
            if m == 1:
                return 0

            best = m  # worst case: change every character
            for d in range(1, m):
                if m % d != 0:
                    continue
                total = 0
                for r in range(d):
                    group = s[i + r:j + 1:d]
                    half = len(group) // 2
                    for a in range(half):
                        if group[a] != group[-(a + 1)]:
                            total += 1
                best = min(best, total)
            return best

        # Precompute cost of every substring once.
        cost_table = [[0] * n for _ in range(n)]
        for i in range(n):
            for j in range(i, n):
                cost_table[i][j] = cost(i, j)

        INF = float("inf")
        dp = [[INF] * (k + 1) for _ in range(n + 1)]
        dp[0][0] = 0

        for i in range(1, n + 1):
            for kk in range(1, k + 1):
                for j in range(kk - 1, i):
                    if dp[j][kk - 1] == INF:
                        continue
                    dp[i][kk] = min(dp[i][kk], dp[j][kk - 1] + cost_table[j][i - 1])

        return dp[n][k]

Code Walkthrough

  • cost(i, j) operates on inclusive indices and returns 0 immediately for single characters — there's nothing to compare.
  • best = m sets a worst-case ceiling: changing every character in the piece, used only if nothing better is found.
  • The d loop only considers divisors that evenly split m, since every other d can't form complete groups.
  • s[i + r:j + 1:d] is the line that actually does the interleaving — starting at offset r from the piece's start, stepping by d, it pulls out exactly the characters that belong to that residue class.
  • The mismatch count compares each character in the group to its mirror from the other end, using group[-(a + 1)] instead of building a separate reversed string.
  • cost_table is filled once, for every (i, j) pair, before the DP ever runs — that's the precomputation that keeps the overall algorithm fast.
  • The dp table is (n + 1) x (k + 1), with dp[0][0] = 0 as the only reachable zero-cost state at the start.
  • The triple loop tries every prefix length i, every piece count kk, and every earlier cut point j, and only updates dp[i][kk] when the predecessor state dp[j][kk - 1] is actually reachable.

Dry Run

Using s = "abaacaba" (length 8) conceptually with k = 2:

  1. The cost table is built first — every substring from length 1 to 8 gets its best divisor cost computed and stored.
  2. The DP then considers every single cut point j between 1 and 7, pairing dp[j][1] (cost of making the first piece a semi-palindrome) with cost_table[j][7] (cost of making everything after j a semi-palindrome).
  3. dp[8][2] ends up holding the minimum over all of those combinations — the cheapest way to split the full string into exactly two semi-palindromic pieces.

The important thing to see is that no substring's cost is ever recalculated mid-DP — every lookup is a table read, not a fresh computation.

Complexity Analysis

Time: There are roughly n² substrings. Computing the cost of one substring of length m involves checking its divisors and, for each, scanning its characters — bounded by O(m log m) in practice, which collectively makes the cost table O(n³) in the worst case. With n capped at 200, that's a few million operations — fast. The DP itself is O(n² * k), and since k <= n / 2, this term is smaller than the cost table construction. Overall: O(n³).

Space: The cost table is O(n²), and the DP table is O(n * k), so total space is O(n²).

Why it's correct: The cost table captures the true minimum cost for every possible piece independent of context, so the DP's job reduces to pure combinatorial optimization over cut points — no information is lost by separating the two layers, because a piece's optimal semi-palindrome cost never depends on where its neighbors are cut.

Alternative Solutions

A memoized top-down recursion (dp(i, kk) as a function with @lru_cache instead of an explicit table) is functionally identical and sometimes easier to write correctly on a first pass, since you don't need to carefully order the loops. It costs a bit more overhead per call but can be more intuitive while debugging the recurrence. For this problem's input size, both approaches run comfortably within limits, so the choice is mostly about personal preference for iterative versus recursive DP.

Edge Cases

  • Piece of length 1: Automatically costs 0 — there's no palindrome violation possible with a single character, so d loops are skipped entirely.
  • k equal to its maximum (n / 2): Forces every piece toward the smallest possible size, so many pieces will end up length 1 or 2 — the algorithm handles this without special-casing because the DP naturally explores all valid cut placements.
  • String with no repeated characters: Every semi-palindrome piece longer than 1 will likely cost close to its worst case, since there's nothing to pair up — the cost function still works correctly, just returns higher numbers.
  • All identical characters: Every divisor and every piece size costs 0, since any group of identical characters is already a palindrome.
  • k = 1: The DP degenerates to a single lookup: the cost of the entire string as one semi-palindrome piece, cost_table[0][n-1].

Common Mistakes

  1. Treating d as a chunk size instead of a stride. Slicing the string into contiguous blocks of size d instead of grouping by index modulo d produces a completely different — and wrong — definition of semi-palindrome.
  2. Defaulting to d = 1 to save time. It occasionally produces the right cost by coincidence, but on most substrings a smaller divisor that groups matching characters together will beat it.
  3. Recomputing substring cost inside the DP loop. This throws away the entire point of precomputing a cost table and reintroduces massive redundant work.
  4. Forgetting that d must be strictly less than the substring's length. Allowing d equal to the length degenerates the "groups" into single characters each, which trivially costs 0 and silently breaks the whole cost calculation.
  5. Off-by-one errors in the DP's inclusive/exclusive indexing. Mixing up whether cost_table[j][i-1] or cost_table[j][i] represents the piece from j to i-1 is one of the easiest ways to get a DP that looks reasonable but returns consistently wrong answers.

Interview Questions

  • Can a substring of any length be split into a valid semi-palindrome for any d? (No — the substring's length must be evenly divisible by d, or the groups can't be formed at all.)
  • Why precompute every substring's cost instead of recalculating it inside the DP? (The same substring range is reused across many different partitions, so computing it once avoids redundant work.)
  • How would the solution change if pieces had to be of equal length? (The DP's cut-point search would collapse to checking only cuts spaced evenly, removing most of the outer loop's freedom.)
  • Could this be solved with a greedy approach instead of DP? (No — the cheapest split overall doesn't always come from greedily minimizing each individual piece's cost, since piece boundaries interact.)

Key Takeaways

The hardest part of this problem isn't the DP — it's correctly understanding what a semi-palindrome actually is, specifically that d defines an interleaved grouping by index modulo d, not a contiguous block size. Once that's clear, the problem splits cleanly into two independent, well-understood pieces: a cost function per substring, and a partition DP over cut points. That "precompute local cost, then DP the global split" pattern generalizes to a huge number of string-partitioning problems, which makes this one worth internalizing beyond just this specific LeetCode number.

Pattern name/tell: 'split string into k parts, minimize cost per part'?

Partition DP — define dp[i][k] = min cost of splitting first i chars into k valid parts.

Time complexity for Minimum Changes to Make K Semi-palindromes?

O(n^2 log n) roughly: O(n^2) substring costs (each costs O(sqrt(len)) divisors) plus O(n*k*n) DP transitions.

Space complexity used by the DP + cost table?

O(n^2) for the precomputed cost[i][j] table, plus O(n*k) for the DP array.

Trickiest edge case when computing a substring's semi-palindrome cost?

Must try every divisor d of length (not just d=1 or len/2) and take the minimum mismatch cost across groups mod d.

Semi-palindrome vs regular palindrome — key difference?

Semi-palindrome only requires each residue-class subsequence (indices same mod d) to be a palindrome, not the whole string.

Interview follow-up: why can't greedy picking equal-size parts work?

Optimal split sizes vary per segment; only DP over all split points guarantees the true minimum total cost.
