Python Lesson 24: One functools Line Fixes Your Broken Decorator

General

Introduction

Every developer eventually writes the same five lines of code in three different places. Maybe it's logging, maybe it's timing, maybe it's a permission check. You copy it, paste it, and tell yourself you'll refactor it later. Later rarely comes, and now that logic lives in ten places instead of one.

Decorators solve exactly this problem, and they show up constantly in real Python code: @staticmethod, @app.route, @lru_cache, @property, @pytest.fixture. If you've written Python for more than a week, you've used decorators without necessarily knowing what they do underneath the @ symbol.

They also show up constantly in interviews, not always as a dedicated question, but as a signal. When an interviewer asks you to add logging, caching, or retry logic to an existing function without modifying it, they're testing whether you understand this pattern. Knowing decorators cold means you don't fumble that moment.

This lesson builds a decorator completely from scratch, no shortcuts, so the @ syntax stops being magic and becomes something you could have invented yourself.

Problem Overview

Here's the situation: you have several unrelated functions, and every one of them needs the same extra behavior wrapped around it. In our case, that behavior is timing, how long a function takes to run.

The naive approach is to paste timing code inside every function that needs it. That works until you need to change how the timing is formatted, or add a fourth function, or a tenth. At that point you're maintaining the same logic in multiple places, and any inconsistency between them is a bug waiting to happen.

The goal is to write the timing behavior exactly once, and attach it to any function, existing or future, without modifying that function's actual code. That's the job a decorator does.

To get there, we need two ideas most Python developers use but rarely stop to name: functions as values, and closures.

Example

Imagine three functions in a project: one processes a file, one queries a database, and one sends an email. All three currently have manual timing code pasted inside them:

import time

def process_file(path):
    start = time.time()
    # ... actual work ...
    print(f"Took {time.time() - start:.4f}s")

def query_database(query):
    start = time.time()
    # ... actual work ...
    print(f"Took {time.time() - start:.4f}s")

def send_email(to, subject):
    start = time.time()
    # ... actual work ...
    print(f"Took {time.time() - start:.4f}s")

By the end of this lesson, all three functions will look like this instead:

@timer
def send_email(to, subject):
    # ... actual work ...

One line, @timer, and the timing behavior is attached without touching the body of send_email at all.

Intuition

The first mental shift is realizing that a function in Python isn't a special, fixed block of code. It's a value, exactly like an integer or a string. That means you can:

  • store it in a variable,
  • pass it as an argument to another function,
  • return it from a function.

That third point is the one that makes decorators possible. If a function can return another function, you can write a function whose entire job is to take a function in and hand back an improved version of it.

The second piece is closures. Normally, when a function finishes running, its local variables disappear. But if that function defines and returns an inner function, and that inner function references one of those local variables, Python keeps the variable alive. The inner function carries it around like a private backpack, even after the outer function has already finished.

def make_multiplier(n):
    def multiplier(x):
        return x * n
    return multiplier

double = make_multiplier(2)
triple = make_multiplier(3)

print(double(5))  # 10
print(triple(5))  # 15

make_multiplier finishes executing the moment it returns. But double still remembers n = 2, and triple still remembers n = 3, forever. That's a closure: a function bundled together with the environment it was created in.

Once you see that, a decorator is a small logical leap. It's a function that:

  1. takes another function in as an argument,
  2. defines a wrapper function around it (a closure that remembers the original function),
  3. returns that wrapper.

The wrapper can run code before calling the original function, after it, or both, all without changing a single line inside the original.

Brute Force Solution

The "brute force" version of solving this problem is what we started with: paste the timing code into every function that needs it.

Idea: manually duplicate the cross-cutting logic inside every function body.

Algorithm: 1. Record the start time at the top of the function. 2. Run the function's actual logic. 3. Compute and print the elapsed time before returning.

Advantages: - No new concepts required, easy to write. - Explicit, nothing hidden.

Disadvantages: - Violates DRY; the same code exists in N places. - Changing the timing format means editing N functions. - Easy to forget when adding a new function, timing silently disappears from the new one. - Mixes unrelated concerns (business logic and timing) inside the same function body.

Time complexity: unaffected, the timing code itself is O(1) overhead per call. Space complexity: O(1), but the maintenance cost scales linearly with the number of functions, which is the real problem here.

Optimal Solution

The optimal solution centralizes the timing logic in exactly one place: a decorator function.

Here's the structure, step by step:

  1. timer(func) is the decorator. It receives the real function, func, as its argument.
  2. Inside timer, we define wrapper(*args, **kwargs), a closure that remembers func.
  3. wrapper starts a clock, calls func with whatever arguments it was given, prints the elapsed time, and returns whatever func returned.
  4. timer returns wrapper instead of func.
Step What happens
timer(send_email) is called func is now send_email
wrapper is defined It closes over func, remembering send_email
timer returns wrapper send_email (the name) now points at wrapper
send_email(...) is called Actually calls wrapper(...), which times and calls the real send_email

The @timer syntax above a function definition is not new behavior, it's shorthand. Writing:

@timer
def send_email(to, subject):
    ...

is exactly equivalent to writing:

def send_email(to, subject):
    ...

send_email = timer(send_email)

The @ symbol just performs that reassignment automatically, right after the function is defined.

Python Code

import functools
import time


def timer(func):
    """Log how long `func` takes to run."""
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper


@timer
def send_email(to, subject):
    """Send an email to `to` with the given `subject`."""
    time.sleep(0.1)  # simulate network latency
    print(f"Email sent to {to}")

Code Walkthrough

  • def timer(func): — the decorator itself. It accepts one argument: the function being decorated.
  • def wrapper(*args, **kwargs): — the inner closure. *args, **kwargs let it accept any combination of positional and keyword arguments, so timer works on any function signature, not just one specific one.
  • start = time.perf_counter() — perf_counter is preferred over time.time() for measuring elapsed durations because it's monotonic and higher-resolution.
  • result = func(*args, **kwargs) — this is the closure at work. wrapper still has access to func, the original function, even though timer already finished executing.
  • elapsed = time.perf_counter() - start — compute the duration after the real work is done.
  • return result — critical: the wrapper must return whatever the original function returned, otherwise every decorated function silently starts returning None.
  • return wrapper — timer hands back the closure, not the original function.
  • @functools.wraps(func) — placed directly above wrapper's definition, this copies func.__name__, func.__doc__, and other metadata onto wrapper. Without it, send_email.__name__ would print "wrapper" and help(send_email) would show wrapper's (empty) docstring instead of the real one.

Dry Run

Call send_email("a@b.com", "Hi"):

  1. Because of the decorator, this is really calling wrapper("a@b.com", "Hi").
  2. start is recorded.
  3. func(*args, **kwargs) runs the real send_email body: sleeps 0.1s, prints "Email sent to a@b.com".
  4. result is None (the real function has no explicit return).
  5. elapsed is computed, roughly 0.1 seconds.
  6. wrapper prints "send_email took 0.1002s".
  7. wrapper returns result, which is None.
  8. Because of functools.wraps, send_email.__name__ is still "send_email", and send_email.__doc__ is still "Send an email to...".

Complexity Analysis

  • Time complexity: O(1) overhead added per call, on top of whatever the wrapped function's own complexity is. The decorator doesn't change the algorithmic complexity of the underlying function; it just adds a constant amount of work (a couple of timer reads and a print).
  • Space complexity: O(1) additional space per decorated function, the closure stores one reference (func), regardless of how large the function's own state is.
  • These are correct because the wrapper does a fixed, small amount of extra work regardless of input size, it never scales with the arguments passed to the decorated function.

Alternative Solutions

A common alternative is a class-based decorator, where __call__ replaces the closure:

class Timer:
    def __init__(self, func):
        functools.update_wrapper(self, func)
        self.func = func

    def __call__(self, *args, **kwargs):
        start = time.perf_counter()
        result = self.func(*args, **kwargs)
        print(f"{self.func.__name__} took {time.perf_counter() - start:.4f}s")
        return result

This works identically but stores state on self instead of in a closure. It's worth knowing for interviews, but for a stateless decorator like this one, the closure-based function version is simpler and more idiomatic. Class-based decorators tend to earn their complexity when you need to track state across many calls (like a call counter) in a way that reads more naturally as object attributes.

Edge Cases

  • Function with no arguments: *args, **kwargs handles this fine, they're just empty.
  • Function that raises an exception: as written, wrapper will let the exception propagate up, since func(*args, **kwargs) isn't wrapped in a try block. This means no timing is printed if the function fails, worth deciding deliberately depending on requirements.
  • Function that returns None: already handled correctly, wrapper returns whatever func returns, including None.
  • Decorating a method on a class: works, since self just becomes the first positional argument captured by *args.
  • Stacking multiple decorators: each decorator wraps the result of the one below it, order matters, and functools.wraps at every layer keeps __name__ accurate at each level.

Common Mistakes

  1. Forgetting to return the result inside wrapper, silently turning every decorated function into one that always returns None.
  2. Forgetting functools.wraps, causing __name__ and __doc__ to point at wrapper instead of the real function, which breaks tooling, documentation generators, and debugging.
  3. Not accepting *args, **kwargs, which makes the decorator only work on functions with one specific signature.
  4. Confusing decorator execution time with call time. The decorator (timer(func)) runs once, at definition time. The wrapper runs every time the decorated function is called. Mixing these up leads to confusion about when side effects happen.
  5. Forgetting decorators execute top-to-bottom, bottom-up when stacked. @a @b on top of def f means f = a(b(f)), not b(a(f)).

Key Takeaways

  • Functions in Python are values: they can be stored, passed, and returned like any other object.
  • A closure is a function that remembers variables from the scope it was created in, even after that scope has finished executing.
  • A decorator is a function that takes a function in, wraps it in a closure, and returns the wrapper.
  • The @ syntax is shorthand for func = decorator(func), nothing more.
  • functools.wraps preserves the original function's identity (__name__, __doc__), and skipping it is one of the most common, most avoidable mistakes in Python.
  • Decorators you already use daily, @staticmethod, @app.route, @lru_cache, are all built on this exact pattern.

📇 Flashcards

What's the tell that you need a decorator here?

Want to add behavior (logging, timing, caching, auth) around a function without touching its body — wrap it, don't rewrite it.

What does a closure add to time/space cost?

O(1) time to call; O(k) extra space per closure for the k free variables captured in the enclosing scope.

How does a closure 'remember' a value after its enclosing function returns?

The inner function keeps a reference to the enclosing scope's variable via __closure__ cells, not a copy — scope stays alive as long as needed.

Trickiest bug when writing a decorator from scratch?

Forgetting *args/**kwargs on the wrapper, or losing the original function's __name__/__doc__ — breaks introspection and tools like help().

@my_decorator vs my_decorator(func) — what's the difference?

None functionally; @ is pure syntax sugar that reassigns func = my_decorator(func) at definition time.

Why does functools.wraps matter, and what does it fix?

Without it, wrapper shadows func's metadata (name, docstring, signature); functools.wraps(func) copies that onto the wrapper.
