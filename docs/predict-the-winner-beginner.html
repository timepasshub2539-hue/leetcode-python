Predict the Winner — 🟢 Beginner (1/3) — LeetCode Daily Python Solution (the trick nobody sees)

General

Introduction

"Predict the Winner" looks like a toy problem — two players picking numbers off the ends of an array — but it's one of the most common gateways into a whole family of interview questions built around the minimax pattern. Variants of this exact setup show up on LeetCode as Stone Game, Stone Game II, and Stone Game III, and the underlying idea — two players competing optimally over shared resources — comes up constantly in interview conversations about game theory, competitive optimization, and interval DP.

What makes this problem worth your time isn't the game itself. It's the reframing trick at its core: instead of tracking two players' scores separately, you track a single number — their difference. That one idea is what turns a seemingly two-dimensional bookkeeping problem into a clean, single-value recurrence. Once you've internalized it here, you'll recognize the same shape instantly in a dozen other interval DP problems.

Problem Overview

You're given an array of numbers. Two players take turns removing a number from either end of the array — never from the middle — and add it to their own running total. Player 1 always moves first. Both players play optimally, meaning each one always tries to maximize their own final score, assuming the other player is doing the same.

Your job: determine whether Player 1 can end the game with a score greater than or equal to Player 2's. Note that detail carefully — a tie counts as a win for Player 1, not a loss. That single rule trips up more people than the DP itself.

Example

Take nums = [1, 5, 2].

The correct answer is false — no matter how cleverly Player 1 plays, they cannot come out ahead.

Now take nums = [1, 5, 233, 7]. Here the answer is true. Player 1 can force a final score of 234 against Player 2's 12, a difference of 222 in Player 1's favor.

And a small trick case: nums = [2, 2]. Both players inevitably end up with 2 points each. The scores tie — and because ties go to Player 1, the correct answer is true.

Intuition

The instinct most people reach for first is greedy: on every turn, just grab the bigger of the two end values. Watch what happens on [1, 5, 2]:

  • Player 1 compares 1 and 2, greedily takes 2. Remaining: [1, 5].
  • Player 2 compares 1 and 5, greedily takes 5. Remaining: [1].
  • Player 1 is forced to take 1.

Final scores: Player 1 has 2 + 1 = 3, Player 2 has 5. Player 1 loses. Greedy fails because taking the biggest number right now can hand your opponent an even better position on the next move. Optimal play requires thinking ahead about what your choice leaves behind for the opponent.

This is where the score-gap trick comes in. Instead of tracking player1_score and player2_score as two separate numbers, track only player1_score - player2_score. If that value ends at zero or above, Player 1 wins. This collapses a two-player bookkeeping problem into a single running number — the score gap.

Define diff(i, j) as: the best possible score gap achievable by whichever player is about to move, considering only the subarray from index i to j.

On your turn, you have two choices:

  • Take nums[i]. The opponent now plays optimally on the slice (i+1, j), and their best result is diff(i+1, j) — but from your perspective, their gain works against you, so you subtract it: nums[i] - diff(i+1, j).
  • Take nums[j]. Symmetrically: nums[j] - diff(i, j-1).

You pick whichever is larger:

diff(i, j) = max(nums[i] - diff(i+1, j), nums[j] - diff(i, j-1))

If i == j, there's only one number left, so diff(i, j) = nums[i].

The final answer is diff(0, n-1) >= 0.

Brute Force Solution

Idea: Directly recurse on diff(i, j) with no caching — recompute everything from scratch every time.

Algorithm: Same recurrence as above, called recursively without storing results.

Advantages: Simple to write, easy to reason about, correct.

Disadvantages: The same (i, j) pair gets recomputed repeatedly from different call paths. This blows up exponentially — around a million redundant calls by the time the array reaches ~20 elements.

Complexity: Time O(2ⁿ), Space O(n) for the call stack.

Optimal Solution

The fix is to notice that diff(i, j) always returns the same value for the same (i, j) pair, since it depends only on the subarray, not on how you got there. That's a textbook signal for memoization or tabulation.

Top-down (memoization): Cache each (i, j) result in a dictionary the first time it's computed, and reuse it on every subsequent call.

Bottom-up (tabulation): Build a 2D table dp where dp[i][j] means the same thing as diff(i, j). Fill it by subarray length:

Step What's filled
Length 1 dp[i][i] = nums[i] for every i (base case)
Length 2 dp[i][i+1] built from two length-1 cells
Length 3 dp[i][i+2] built from two length-2 cells
... ...
Length n dp[0][n-1] — the final answer

Every cell only needs two already-computed cells from a shorter subarray, so by the time you reach the full array, the answer is ready.

Python Code

from functools import lru_cache


def predict_winner_recursive(nums: list[int]) -> bool:
    """Top-down: recursion + memoization."""
    @lru_cache(maxsize=None)
    def diff(i: int, j: int) -> int:
        if i == j:
            return nums[i]
        take_left = nums[i] - diff(i + 1, j)
        take_right = nums[j] - diff(i, j - 1)
        return max(take_left, take_right)

    return diff(0, len(nums) - 1) >= 0


def predict_winner_dp(nums: list[int]) -> bool:
    """Bottom-up: tabulation."""
    n = len(nums)
    dp = [[0] * n for _ in range(n)]

    for i in range(n):
        dp[i][i] = nums[i]

    for length in range(2, n + 1):
        for i in range(n - length + 1):
            j = i + length - 1
            dp[i][j] = max(nums[i] - dp[i + 1][j], nums[j] - dp[i][j - 1])

    return dp[0][n - 1] >= 0


if __name__ == "__main__":
    assert predict_winner_dp([1, 5, 2]) is False
    assert predict_winner_dp([1, 5, 233, 7]) is True
    assert predict_winner_dp([2, 2]) is True
    assert predict_winner_dp([1]) is True
    assert predict_winner_recursive([1, 5, 2]) is False
    print("all tests passed")

Code Walkthrough

  • lru_cache(maxsize=None) gives the recursive version memoization for free — no manual dictionary needed.
  • diff(i, j) base case: a single remaining number must be taken as-is.
  • take_left / take_right compute both choices using the recurrence: your gain minus the opponent's best response on what's left.
  • dp[i][i] = nums[i] seeds every length-1 subarray before the main loop runs.
  • The outer loop walks through increasing subarray lengths; the inner loop slides that length across all valid starting positions i, deriving j from i + length - 1.
  • dp[0][n-1] holds the final score gap for the whole array once the table is complete.

Dry Run

Using nums = [1, 5, 2]:

  • dp[0][0] = 1, dp[1][1] = 5, dp[2][2] = 2
  • dp[0][1] (covers [1, 5]): max(1 - dp[1][1], 5 - dp[0][0]) = max(1 - 5, 5 - 1) = max(-4, 4) = 4
  • dp[1][2] (covers [5, 2]): max(5 - dp[2][2], 2 - dp[1][1]) = max(5 - 2, 2 - 5) = max(3, -3) = 3
  • dp[0][2] (covers [1, 5, 2]): max(1 - dp[1][2], 2 - dp[0][1]) = max(1 - 3, 2 - 4) = max(-2, -2) = -2

The final gap is -2, which is negative, so predict_winner_dp([1, 5, 2]) returns False — matching expectations.

Complexity Analysis

There are roughly n² distinct (i, j) pairs, and each cell takes constant time to compute once its two dependencies are filled in. That gives:

  • Time: O(n²)
  • Space: O(n²) for the table (or O(n) for the call stack in the recursive version, plus O(n²) for the memo cache)

Both are correct because every cell is computed exactly once and reused, eliminating the exponential blowup from the brute-force version.

Alternative Solutions

If memory is a concern, note that computing dp[i][j] for a given length only needs values from the length just below it — you never need the full grid. Keeping just a single 1D array and updating it in place brings space down to O(n) while keeping time at O(n²).

Edge Cases

  • Single element ([x]): Player 1 takes it and automatically wins — diff returns nums[0] directly.
  • Two equal elements ([2, 2]): Score gap is exactly 0. Since ties favor Player 1, this must return True — a common source of off-by-one logic errors.
  • All identical values: Every arrangement produces a gap of 0, always True.
  • Empty array: Not a valid input per constraints, but defensively should return True (no game, no loss).
  • Very large arrays: Confirms whether your solution actually needs the O(n) space optimization instead of O(n²).

Common Mistakes

  1. Using > 0 instead of >= 0 when checking the final gap — this incorrectly returns False on ties.
  2. Tracking Player 1's and Player 2's scores as two separate running totals instead of collapsing them into one gap value — adds unnecessary bookkeeping and complexity.
  3. Forgetting the base case i == j, causing index-out-of-range errors when the recursion reaches a single element.
  4. Implementing the brute-force recursive version without memoization and being surprised it times out on larger inputs.
  5. Filling the DP table in the wrong order (e.g., by row instead of by increasing subarray length), which reads uncomputed cells.

Key Takeaways

Greedy fails on this problem because the best move right now isn't always the best move overall. The score-gap trick — tracking one number instead of two — is what makes the recurrence tractable, and building it bottom-up from single-element subarrays to the full array gets you a clean O(n²) solution. Watch for the tie-breaking rule; it's the single detail most likely to cost you a wrong answer in an interview setting.

📇 Flashcards

What pattern fits 'Predict the Winner' style array games?

Interval DP / game-theory DP: each player picks an end, maximize your score minus opponent's optimal play.

Time complexity of the naive top-down solution?

O(n²) states (i,j) each O(1) work after memoization, so O(n²) total.

Space complexity of the memoized solution?

O(n²) for the memo table plus O(n) recursion stack depth.

Trickiest bug when framing this as one recursive score?

Forgetting to negate the opponent's optimal result — score(i,j) = max(a[i]-score(i+1,j), a[j]-score(i,j-1)).

Predict the Winner vs Stone Game — key difference?

Stone Game guarantees first player always wins with even length; Predict the Winner needs the actual score-difference check, no shortcut.

Interview follow-up: reduce space to O(n)?

Since dp[i][j] only depends on row i+1 and same row j-1, iterate bottom-up with a 1D array reused across rows.
