Predict the Winner — 🟢 Beginner (1/3) — LeetCode Daily Python Solution

General

Introduction

"Predict the Winner" shows up constantly in interview prep lists, and it's not because the problem itself is exciting — it's because of what it teaches. On the surface it looks like a simulation problem: two players, an array, alternating turns. Most people's first instinct is to write a function that tries every possible sequence of moves and see who ends up ahead. That instinct is correct as a starting point and wrong as an ending point, and the gap between those two is exactly what interviewers are testing.

This problem sits at the intersection of two skills that separate junior engineers from senior ones: recognizing when a brute-force recursive solution is secretly repeating work, and finding the right state representation that collapses a two-sided problem into a one-sided one. Once you've internalized the trick here — tracking a difference instead of two separate totals — you'll start spotting the same pattern in a whole family of adversarial and interval-based DP problems.

Problem Overview

You're given an array of numbers. Two players take turns removing a number from either end of the array — never from the middle — and each number removed is added to that player's running score. Player 1 always moves first. Both players play optimally, meaning at every turn they choose whichever end maximizes their own final score, assuming the other player will do the same.

The question isn't "what's the final score" — it's simpler than that. You just need to return true if Player 1 can end the game with a score greater than or equal to Player 2's, and false otherwise. A tie counts as a win for Player 1.

Example

Take nums = [1, 5, 2].

If Player 1 grabs the 2 (the rightmost number, trying to bank a decent value early), the array left is [1, 5]. Player 2 then optimally takes the 5, leaving Player 1 with only the 1. Final scores: Player 1 has 2 + 1 = 3, Player 2 has 5. Player 1 loses, despite making a choice that looked reasonable in the moment.

That's the core trap of this problem: grabbing the bigger number right now doesn't guarantee the better outcome, because it changes what your opponent gets to choose from next.

Intuition

Imagine splitting a shared resource with someone who wants the biggest share exactly as badly as you do. Every choice you make reshapes their options, and every choice they make reshapes yours. This kind of two-sided, alternating-advantage fight is called minimax, and it underlies this entire problem.

The naive way to model it is to track two scores — Player 1's total and Player 2's total — and simulate every possible sequence of picks. That works, but it's clumsy: you're carrying twice as much state as you need.

Here's the insight that unlocks the problem: instead of tracking two scores, track a single number — the current mover's score minus the opponent's score, from the perspective of whoever is about to move.

Take [1, 5]. Whoever moves first takes the 5 (the better option), leaving the other player the 1. From the mover's perspective, their advantage is 5 - 1 = 4. That one number tells you everything: it's positive, so the mover comes out ahead.

The key mechanic: when the turn passes to the other player, what was "my gain" becomes "their loss" — the sign flips. This lets a single recurrence represent both players at once, because the same formula, applied from alternating perspectives, always tells you who's ahead.

For the full array, the rule is simple: if the final difference is zero or more, Player 1 wins.

Brute Force Solution

Idea: At every turn, try taking the left number and try taking the right number. Recurse into both branches, following the game all the way to the end, and see which starting choice leads to a win.

Algorithm: 1. Define a recursive function over the range [i, j] representing the numbers still in play. 2. At each call, the current player picks nums[i] or nums[j]. 3. Recurse into the smaller subrange with the turn passed to the other player. 4. At the base case (i == j or the range is empty), compare final scores.

Advantages: Simple to reason about, directly mirrors the problem statement, easy to verify correctness on small inputs.

Disadvantages: Every turn branches into two more calls, and many of those calls solve the exact same subrange redundantly. The recursion tree grows exponentially.

Complexity: Time is O(2ⁿ) in the worst case, space is O(n) for the recursion stack. For an array of just 20 numbers, that's already over a million paths — impractical for anything realistic.

Optimal Solution

The brute-force recursion has a giveaway sign of wasted work: diff(i, j) gets called from multiple different branches of the recursion tree, but the answer only depends on the range [i, j] — not on how you got there. That's the signal to memoize: save each answer the first time you compute it.

Define diff(i, j) as the best score advantage the current player can force, using only the numbers between index i and j.

Recurrence: - If the player takes nums[i]: they gain nums[i], but the opponent then plays optimally on [i+1, j], and whatever advantage the opponent forces there works against the current player. So this branch is worth nums[i] - diff(i+1, j). - If the player takes nums[j]: symmetric logic gives nums[j] - diff(i, j-1). - The player picks whichever branch is larger, since they play optimally:

diff(i, j) = max(nums[i] - diff(i+1, j), nums[j] - diff(i, j-1))

Base case: when i == j, there's only one number and no choice — diff(i, i) = nums[i].

Rather than computing this top-down with memoization, we can build it bottom-up as a table, filling by subarray length:

Step What happens
1 Fill every dp[i][i] — single-element subarrays, trivially nums[i]
2 Grow the window to length 2, then 3, then more
3 Each dp[i][j] reuses two smaller, already-computed cells
4 dp[0][n-1] holds the answer for the entire array

Growing the window this way guarantees that by the time you compute dp[i][j], both dp[i+1][j] and dp[i][j-1] already exist in the table.

Python Code

from typing import List


def predict_the_winner(nums: List[int]) -> bool:
    n = len(nums)
    if n <= 1:
        return True

    # dp[i][j] = best score advantage the current player can force
    # using only nums[i..j]
    dp = [[0] * n for _ in range(n)]

    # Base case: single-element subarrays
    for i in range(n):
        dp[i][i] = nums[i]

    # Grow the window length from 2 up to n
    for length in range(2, n + 1):
        for i in range(n - length + 1):
            j = i + length - 1
            take_left = nums[i] - dp[i + 1][j]
            take_right = nums[j] - dp[i][j - 1]
            dp[i][j] = max(take_left, take_right)

    return dp[0][n - 1] >= 0

Code Walkthrough

  • dp = [[0] * n for _ in range(n)] builds an n x n grid of zeros using a list comprehension per row — this avoids the classic bug of using [[0] * n] * n, which would make every row the same list object.
  • The base-case loop fills the diagonal: with a single number, there's no decision to make, so the advantage is just that number.
  • The outer length loop controls how wide the subarray window is, growing it one step at a time so smaller answers are always ready before they're needed.
  • The inner i loop slides that window across the array; j is derived from i and length rather than tracked separately.
  • take_left and take_right are exactly the two branches of the recurrence — take a number, then subtract whatever advantage the opponent can force on what's left.
  • dp[0][n - 1] >= 0 reads the final answer: if Player 1's forced advantage over the whole array is zero or positive, they win or tie, which counts as a win.

Dry Run

Using nums = [1, 5, 233, 7]:

Diagonal (length 1): dp[0][0]=1, dp[1][1]=5, dp[2][2]=233, dp[3][3]=7.

Length 2: - dp[2][3]: take 233 → 233 - dp[3][3] = 233 - 7 = 226. Take 7 → 7 - dp[2][2] = 7 - 233 = -226. Max is 226. - Similarly, every adjacent pair gets filled the same way.

Length 3, then length 4 repeat the pattern, each cell reusing two already-computed smaller cells, until dp[0][3] is reached.

The final value at dp[0][3] comes out to +222. Since that's ≥ 0, the function returns True — Player 1 wins.

As a sanity check on the tie rule: for nums = [2, 2], both players end up with equal scores, and the same recurrence correctly returns True, because a tie counts as a win for Player 1.

Complexity Analysis

Time: O(n²) — the table has n² cells, and each cell is computed in O(1) using two already-filled neighbors.

Space: O(n²) for the table itself. This can be reduced to O(n) with a rolling 1D array if only the final answer is needed, since each length only depends on the previous length's row.

These bounds are correct because every cell is computed exactly once (no repeated recursive calls, unlike brute force), and each computation does constant work.

Alternative Solutions

Top-down memoization: Keep the original recursive function, but cache each (i, j) result the first time it's computed using a dictionary or a 2D memo array. This reads closer to the plain-English recurrence and is often easier to write under interview pressure, since you don't have to reason about fill order — you just let the recursion "figure it out" and skip recomputation.

from functools import lru_cache
from typing import List


def predict_the_winner_memo(nums: List[int]) -> bool:
    n = len(nums)

    @lru_cache(maxsize=None)
    def diff(i: int, j: int) -> int:
        if i == j:
            return nums[i]
        take_left = nums[i] - diff(i + 1, j)
        take_right = nums[j] - diff(i, j - 1)
        return max(take_left, take_right)

    return diff(0, n - 1) >= 0

Both approaches cost the same asymptotically: O(n²) time and O(n²) space. The bottom-up version avoids recursion overhead and stack depth limits; the top-down version is often faster to write and reason about correctness for.

Edge Cases

  • Single-element array: Player 1 takes the only number and automatically wins. The code handles this with the early if n <= 1: return True check.
  • All zeros: Every diff value comes out to zero, which is still a tie — still a win for Player 1.
  • Two equal elements ([2, 2]): both players end up with identical scores; the recurrence correctly treats this as a win via the >= 0 check.
  • Large values: Python integers grow arbitrarily large, so even array values up to the problem's stated bound (10,000,000) never cause overflow.
  • Strictly increasing or decreasing arrays: these don't need special-casing — the general recurrence handles them the same as any other input.

Common Mistakes

  1. Checking > 0 instead of >= 0. A tie counts as a win for Player 1; using strict inequality silently produces wrong answers on tied games.
  2. Greedy end-picking. Choosing whichever end looks numerically larger right now, without accounting for what that choice hands the opponent, is not the same as optimal play — see the [1, 5, 2] example above.
  3. Swapping which smaller diff gets subtracted. Mixing up diff(i+1, j) and diff(i, j-1) quietly flips whose turn is being modeled, producing subtly wrong results that are easy to miss in testing.
  4. Filling the DP table in the wrong order. If you don't grow by subarray length, you'll reference dp[i+1][j] or dp[i][j-1] before they're computed.
  5. Using [[0] * n] * n to build the grid. This creates n references to the same row list, so writing to one row corrupts all of them.

Interview Questions

  • Can you first write the brute-force recursive solution before optimizing it?
  • What's the base case, and why does it need no decision logic?
  • Why does tracking a difference work instead of tracking two scores separately?
  • Can you convert your bottom-up solution to top-down memoization, or vice versa?
  • Can you reduce the space complexity from O(n²) to O(n)?
  • How would the solution change if players could only pick from one end, not both?

Key Takeaways

The [1, 5, 2] example is the whole lesson in miniature: grabbing the bigger number right now can still lose you the game once you account for what your opponent does with what's left. The score-difference trick handles this automatically, because it always folds in the opponent's optimal response. Two separate scoreboards collapse into a single recurrence, filled bottom-up, cell by cell, in O(n²) time — and once you've seen this pattern, you'll recognize it every time an adversarial two-player problem shows up in interval form.

Pattern for 'Predict the Winner' - what's the tell?

Two-player turn-based array game, optimal play both sides → game-theory recursion (minimax), not simple greedy.

Time complexity of the brute-force recursive solution?

O(2^n) without memoization; O(n^2) with memoization (n*n states, O(1) work each).

Space complexity with memoization?

O(n^2) for the memo table plus O(n) recursion stack depth.

Common bug when picking the greedy 'take the bigger end' shortcut?

Greedy fails — taking the locally bigger number can leave the opponent a better future split; must simulate both choices.

Why doesn't picking max(left, right) each turn always win?

It ignores what's left for future turns; a smaller pick now can force a worse remaining split for the opponent later.
