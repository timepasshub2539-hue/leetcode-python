Lesson 2: 10 Seconds vs 10 Minutes — Every Way to Install n8n

General

Introduction

Every automation tool has a moment where a single setup decision quietly shapes everything that comes after it, and for n8n, that moment is installation. It looks like a formality — pick a path, click a few buttons, get to the canvas — but the choice you make here determines whether your workflows are backed up automatically, whether you're responsible for patching a server, and whether your work survives a restart.

This matters for developers specifically because n8n sits at the intersection of infrastructure and application logic. Unlike a SaaS tool where hosting is invisible, n8n gives you the option to run it yourself, which means you inherit real ops decisions: where data lives, how containers persist state, and what happens when a process restarts. If you've worked with Docker before, none of this will surprise you. If you haven't, this is a low-stakes place to learn habits that apply far beyond n8n — volume mounts, environment-variable configuration, and the container-as-ephemeral-storage mental model show up constantly in backend and DevOps work.

Getting this right the first time also saves you from the single most common beginner mistake with self-hosted n8n: building out real workflows in a container, restarting it, and watching everything disappear. That's not a hypothetical — it's exactly what happens when you skip one flag.

Problem Overview

n8n gives you three practical ways to get an instance running:

  1. n8n Cloud — a fully managed instance you don't administer at all.
  2. npx n8n — a zero-install way to run n8n locally using Node's package runner.
  3. Docker — a containerized instance you run yourself, ideally with persistent storage attached.

The "problem" to solve isn't technical difficulty — none of these are hard to start. The real problem is picking the right one for your situation and understanding the one operational detail (data persistence) that determines whether your work is safe. Get this wrong, and you don't get a friendly error message. You get an empty canvas where your workflows used to be.

Example

Here's what each path actually looks like in practice.

Cloud:

Sign up → n8n provisions an instance → you land on the owner-account screen

No terminal, no server, no config files. Output: a working instance in seconds.

npx (local, ephemeral):

npx n8n

Output: n8n downloads (first run only), starts a local server, and opens on localhost:5678. Close the terminal or reset your machine, and depending on your setup, you may need to re-fetch state — there's no dedicated persistent volume unless you configure one.

Docker (local, persistent):

docker run -it --rm \
  --name n8n \
  -p 5678:5678 \
  -v n8n_data:/home/node/.n8n \
  docker.n8n.io/n8nio/n8n

Output: same local instance as npx, but the -v n8n_data:/home/node/.n8n flag maps n8n's internal data directory to a Docker volume that lives outside the container. Restart, rebuild, or even delete the container, and n8n_data still holds your workflows, credentials, and owner account.

Remove that -v flag, and the exact same command becomes a trap: everything works perfectly until you stop the container, at which point all of it is gone.

Intuition

Before touching any command, it helps to think about where state lives in each option, because that's the only variable that actually matters here.

With Cloud, the provider owns the storage layer entirely. You're not choosing where data lives — that decision was made for you, and it's designed to persist by default. This is why Cloud has no "gotcha": persistence isn't a step you can forget, it's baked into the product.

With self-hosting, you take on that responsibility. And containers, by design, are meant to be disposable — that's the entire point of the technology. A container is supposed to be identical every time you start it, which means anything written inside it during runtime is, by default, temporary. Docker only remembers what you explicitly tell it to remember, via a volume — a storage location that exists independently of any one container's lifecycle.

Once you see it that way, the mental model simplifies: Docker isn't "riskier" than Cloud, it's just explicit about a tradeoff that Cloud hides from you. The engineer's job is to notice that tradeoff exists and configure around it, rather than to avoid self-hosting altogether. That's the whole intuition — a volume isn't an optional nice-to-have, it's the mechanism that turns "container" into "server."

Brute Force Solution

If we're borrowing the "brute force vs optimal" framing from algorithm problems, the brute-force approach to installing n8n is: run Docker without thinking about storage.

Idea: docker run the n8n image, get it working, start building workflows.

Algorithm: 1. Pull and run the n8n Docker image. 2. Open the browser, create the owner account, build workflows. 3. Stop the container at some point (intentionally or via a crash, reboot, or docker system prune).

Advantages: - Fastest possible command to type — nothing extra to configure. - Works flawlessly for the entire session, so the flaw isn't visible until it's too late.

Disadvantages: - Total data loss on container removal. Your owner account, credentials, and every workflow you built live only inside the container's writable layer. - No way to upgrade the n8n image without losing everything, since upgrading typically means recreating the container. - No backup path — there's nothing to back up, because nothing was ever written outside the container.

Complexity (in setup-and-recovery terms): - Time to get running: O(1) — one command. - Time to recover after data loss: undefined — the data doesn't exist anymore. There is no recovery.

This is the classic brute-force pattern: it looks correct because it produces the right output initially, and the failure only shows up on a case you didn't test — namely, restarting the container.

Optimal Solution

The optimal setup is the same Docker command with one addition: a volume mount that redirects n8n's data directory to persistent storage.

Layer Brute force (no -v) Optimal (with -v)
Owner account Stored in container Stored in volume
Credentials & encryption key Stored in container Stored in volume
Workflows Stored in container Stored in volume
Survives docker rm? No Yes
Survives image upgrade? No Yes

The fix costs nothing extra in complexity — it's the same command, plus one flag — which is what makes skipping it such an unforced error. n8n stores everything it needs (owner account, credentials, encryption key, workflow definitions) under /home/node/.n8n inside the container. Point a named volume at that path, and Docker keeps that directory alive independently of the container's lifecycle. You can stop the container, delete it, pull a new image version, and start a fresh container against the same volume — your data reattaches as if nothing happened.

If you choose Cloud instead, none of this applies — the provider's storage layer already does the equivalent of "always mount a volume," so there's no decision to make.

Python Code

The video and lesson are Docker/CLI-focused rather than Python-focused, but here's a small, genuinely useful utility: a script that checks whether a running n8n Docker container has a volume mounted, so you can catch the missing--v mistake before you lose anything.

"""Warn if a running n8n Docker container has no persistent volume mounted."""
import json
import subprocess
import sys

N8N_DATA_PATH = "/home/node/.n8n"


def get_container_mounts(container_name: str) -> list[dict]:
    """Return the Mounts section from `docker inspect` for a container."""
    result = subprocess.run(
        ["docker", "inspect", container_name],
        capture_output=True,
        text=True,
        check=True,
    )
    data = json.loads(result.stdout)
    return data[0]["Mounts"]


def has_persistent_data_volume(mounts: list[dict]) -> bool:
    """Check whether n8n's data directory is backed by a named volume."""
    return any(
        mount["Destination"] == N8N_DATA_PATH and mount["Type"] == "volume"
        for mount in mounts
    )


def main(container_name: str = "n8n") -> None:
    mounts = get_container_mounts(container_name)
    if has_persistent_data_volume(mounts):
        print(f"OK: '{container_name}' has a persistent volume at {N8N_DATA_PATH}")
    else:
        print(
            f"WARNING: '{container_name}' has no volume mounted at {N8N_DATA_PATH}. "
            "Restarting or removing this container will erase all workflows."
        )
        sys.exit(1)


if __name__ == "__main__":
    container = sys.argv[1] if len(sys.argv) > 1 else "n8n"
    main(container)

Code Walkthrough

  • get_container_mounts shells out to docker inspect, which returns a JSON document describing the container, including a Mounts array — every filesystem mapping between host/volume and container.
  • has_persistent_data_volume scans that array for an entry where the container-side path (Destination) matches n8n's known data directory and the mount Type is "volume" (as opposed to a temporary, container-local path).
  • main prints a clear pass/fail message and exits with a non-zero status on failure, so this can be dropped into a CI check or a pre-deploy script without extra glue code.
  • The container name defaults to "n8n" but is overridable via a CLI argument, matching the --name n8n used in the Docker run command above.

Dry Run

Run the check against the brute-force container (no -v flag):

$ python check_n8n_volume.py n8n

docker inspect n8n returns a Mounts array that's empty or contains no entry for /home/node/.n8n. has_persistent_data_volume returns False. Output:

WARNING: 'n8n' has no volume mounted at /home/node/.n8n. Restarting or removing this container will erase all workflows.

Exit code 1.

Now run it against the optimal container (-v n8n_data:/home/node/.n8n):

Mounts contains {"Type": "volume", "Name": "n8n_data", "Destination": "/home/node/.n8n", ...}. The check finds a match, returns True. Output:

OK: 'n8n' has a persistent volume at /home/node/.n8n

Exit code 0.

Complexity Analysis

  • Time: O(m), where m is the number of mounts on the container — typically single digits, so effectively constant time in practice. Docker's inspect call itself is the dominant cost, and it's a single API round-trip.
  • Space: O(m) to hold the parsed mounts list; negligible for any realistic container configuration.
  • This is correct because a container's mount list is fixed at creation time and fully described by docker inspect — there's no partial or lazy state to account for.

Alternative Solutions

  • docker-compose with a named volume in docker-compose.yml — functionally identical to the -v flag, but declarative and reproducible. Preferable once you're managing more than a single container, since the volume configuration lives in version control instead of a one-off shell command.
  • Bind mount to a host directory (-v /home/user/n8n-data:/home/node/.n8n) instead of a named Docker volume — gives you direct filesystem access to inspect or back up the data manually, at the cost of being less portable across machines.
  • n8n Cloud — sidesteps the entire persistence question by design, at the cost of losing infrastructure control and, depending on your plan, some configurability.

Edge Cases

  • Running Docker without any volume flag at all — the primary failure mode covered above; total data loss on container removal.
  • Mounting the wrong path (e.g., /root/.n8n instead of /home/node/.n8n) — the volume exists and looks correctly configured, but n8n never writes to it, so data loss still occurs silently.
  • Losing the owner account credentials — since the account isn't recoverable via any cloud-based "forgot password" flow on self-hosted instances, losing them alongside a wiped volume means starting over completely.
  • Running multiple npx n8n sessions expecting shared state — each invocation is independent unless you've explicitly configured shared storage; don't assume continuity across terminal sessions.
  • Switching Docker image versions without checking the volume schema — rare, but worth confirming compatibility notes before major version jumps if you're maintaining a long-lived instance.

Common Mistakes

  1. Running Docker without the -v flag, assuming Docker persists data by default (it doesn't).
  2. Confusing npx n8n's convenience with Docker's persistence — they solve different problems.
  3. Treating the owner account as recoverable, when it's tied entirely to the instance's local data.
  4. Not knowing which environment variables control port and encryption key, then troubleshooting blind when something doesn't start.
  5. Choosing Cloud or Docker based on habit rather than actual need for control, then fighting the platform's constraints later.
  6. Mounting a volume to the wrong container path, giving a false sense of security.
  7. Deleting a container with docker rm without first checking whether a volume was attached.

Similar Problems

  • Configuring environment-based settings in a Node.js or Python app — the pattern of reading config from env vars instead of a UI settings panel is common across backend tooling.
  • Comparing managed vs. self-hosted database services (RDS vs. self-managed Postgres) — the same control-vs-convenience tradeoff shows up at the infrastructure level.

Key Takeaways

  • Cloud trades control for convenience; self-hosting trades convenience for control — neither is universally correct.
  • npx n8n is for quick, disposable exploration, not for anything you intend to keep.
  • Docker is the right self-hosted choice, but only with a volume mount — without it, you're one restart away from losing everything.
  • n8n's configuration lives in environment variables, not a hidden settings menu — know the key ones (port, encryption key) before you need them.
  • The owner account is created once, locally, and isn't recoverable through any cloud mechanism — treat it and its underlying data with the same care as a database credential.

npm vs Docker for self-hosting: main tradeoff?

Data (workflows, credentials) vanishes on restart unless you mount a persistent volume for n8n's data folder.

Where does n8n read its runtime settings from?

Environment variables (and a local config/user folder) — not a GUI settings page, so misconfigured env vars silently change behavior.

To create the owner account (admin login) before landing on the workflow editor.
