3105. Longest Strictly Increasing or Strictly Decreasing Subarray

General ✓ Runtime tested

8. Introduction

Every interview loop eventually hands you a problem that looks almost too simple to be a real question — scan an array, track a run, return a length. LeetCode 3105, Longest Strictly Increasing or Strictly Decreasing Subarray, is exactly that kind of problem, and that's precisely why it shows up so often as a warm-up or filter question. It doesn't test whether you know a famous algorithm by name. It tests something more basic and, honestly, more revealing: can you look at a sequence, reason about what state needs to be carried forward from one element to the next, and resist the urge to over-engineer a solution with nested loops or extra arrays?

This is a problem that rewards clean thinking over clever tricks. Interviewers like it because the "obvious" first instinct — restart your scan every time a streak breaks — is technically correct but wasteful, and the gap between that instinct and the optimal one-pass solution is small enough to walk through live in an interview, yet large enough to show whether a candidate notices redundant work. If you're prepping for interviews or just building your instincts for array problems, this is a great one to internalize, because the pattern underneath it — a single pass with a couple of counters that grow or reset based on a comparison — reappears constantly in problems about runs, streaks, and consecutive sequences.

9. Problem Overview

You're given an array of integers. You need to find the length of the longest contiguous slice of that array where the values are either strictly increasing the entire way through, or strictly decreasing the entire way through — whichever of the two turns out to be longer. Return that length as a single integer.

The word "strictly" is doing a lot of work here. It means every adjacent pair in the run has to actually go up, or actually go down — no ties allowed. If two consecutive numbers are equal, that breaks both an increasing run and a decreasing run at that point. A single number on its own always counts as a valid run of length one, since there's no neighbor to violate the rule.

The constraints are intentionally small: the array has at most 50 elements, each between 1 and 50. That's a strong signal. It means a brute-force approach would technically pass within any reasonable time limit, but the problem isn't really asking "can you make this pass" — it's asking "can you recognize when a single pass is enough, and prove to yourself why."

10. Example

Take the array [1, 4, 3, 3, 2].

  • 1 → 4: increasing. Current increasing streak length: 2.
  • 4 → 3: decreasing. The increasing streak breaks; current decreasing streak length: 2.
  • 3 → 3: equal. Neither streak can continue — this resets both back to a baseline of 1.
  • 3 → 2: decreasing. New decreasing streak length: 2.

Across the whole walk, the longest streak we ever see, in either direction, is 2. That's the answer.

Notice what's happening under the hood: we never found a streak longer than 2 in this array, but we found two different streaks of length 2 — one increasing (1,4), one decreasing (4,3 and separately 3,2). The answer only cares about the maximum across all of them, not which direction "won."

11. Intuition

The naive instinct, especially under interview pressure, is to think of this as a search problem: pick a starting index, extend the run for as long as possible, then move to the next starting index and repeat. That instinct isn't wrong — it would produce a correct answer — but it's worth pausing on why it's wasteful before building it.

If you start at index 0 and walk forward until the streak breaks, you've already compared every adjacent pair up to the break point. Starting over from index 1 and re-walking forward means you're re-comparing pairs you already looked at. The information about whether nums[i] is bigger or smaller than nums[i-1] doesn't change depending on where your "run" started — it's a fixed fact about those two positions. So restarting from every index is really just checking every pair in the array multiple times, dressed up as a sliding window.

The insight that unlocks the one-pass solution is this: at any given index, there are really only two things you need to know to decide what happens next — how long is my current increasing streak, and how long is my current decreasing streak. You don't need to know anything about streaks further back, because a streak is only ever extended or broken by its immediate neighbor. That means you can carry both numbers forward as you walk the array exactly once, updating them based on a single comparison at each step, and checking after every step whether either one has become your new best.

The subtle part — and the part most people get wrong on a first attempt — is handling ties correctly. If you're tempted to use >= or <= instead of strict > and <, it feels harmless, but it silently breaks on inputs like [3, 3, 3, 3], where every streak should collapse back to length 1 at every step, not keep growing. Strict comparison, and resetting both counters on a tie, is what keeps the logic honest.

12. Brute Force Solution

Idea: For every starting index, extend a run forward as long as it keeps increasing, and separately as long as it keeps decreasing, tracking the best length seen.

Algorithm: 1. For each index i from 0 to n-1: - Extend forward while the sequence strictly increases; record the length. - Extend forward while the sequence strictly decreases; record the length. 2. Return the maximum length found across all starting points and both directions.

Advantages: Easy to write, easy to reason about correctness directly from the problem statement, no risk of subtle state-tracking bugs.

Disadvantages: Re-examines the same adjacent pairs from multiple starting indices. Conceptually doing redundant work even though the array is small enough that it doesn't matter here.

Complexity: Time O(n²) in the worst case (every starting index re-walks much of the array). Space O(1) beyond the input.

13. Optimal Solution

Walk the array exactly once, carrying three numbers forward:

Variable Meaning
inc length of the current strictly increasing streak ending at this position
dec length of the current strictly decreasing streak ending at this position
best the longest streak (either direction) seen so far

All three start at 1, because any single element is trivially a streak of length one.

Then, starting from the second element, compare it to the one before it:

  • Bigger → the increasing streak continues, so inc += 1. The decreasing streak is broken, so dec resets to 1.
  • Smaller → the decreasing streak continues, so dec += 1. The increasing streak is broken, so inc resets to 1.
  • Equal → neither streak survives a tie, so both inc and dec reset to 1.

After every step, update best = max(best, inc, dec).

The key proof point is that inc and dec never need to "remember" anything beyond their current value — each step's decision depends only on the immediate neighbor comparison, which is why a single pass is sufficient. There's no case where you'd need to look back further than one position.

14. Python Code

class Solution:
    def longestMonotonicSubarray(self, nums: list[int]) -> int:
        inc = dec = best = 1

        for i in range(1, len(nums)):
            if nums[i] > nums[i - 1]:
                inc += 1
                dec = 1
            elif nums[i] < nums[i - 1]:
                dec += 1
                inc = 1
            else:
                inc = dec = 1

            best = max(best, inc, dec)

        return best

15. Code Walkthrough

  • inc = dec = best = 1: Every array has at least one element, and a single element is always a valid streak of length one in both directions — this initializes all three trackers to that baseline.
  • for i in range(1, len(nums)): We only need to start comparing from the second element, since each comparison looks at nums[i] against nums[i - 1].
  • if nums[i] > nums[i - 1]): The increasing streak is still alive, so it grows by one. The decreasing streak just broke, so it falls back to the baseline of one.
  • elif nums[i] < nums[i - 1]: Mirror case — the decreasing streak grows, the increasing streak resets.
  • else: The values are equal. Neither direction counts a tie as part of a streak, so both reset to one.
  • best = max(best, inc, dec): Checked after every single step, this is what guarantees we catch the longest streak regardless of which direction it comes from or when it occurs.
  • return best: Once the loop finishes, best holds the answer.

16. Dry Run

Array: [1, 4, 3, 3, 2]

i nums[i-1] nums[i] Comparison inc dec best
start - - - 1 1 1
1 1 4 greater 2 1 2
2 4 3 less 1 2 2
3 3 3 equal 1 1 2
4 3 2 less 1 2 2

Final best = 2, matching the expected answer.

17. Complexity Analysis

Time: O(n). Each element is visited exactly once, and the work done per element — one comparison, a couple of assignments, one max call — is constant. There's no nested loop and no re-visiting of earlier elements, so the total work scales linearly with the array length.

Space: O(1). Only three integer variables (inc, dec, best) are maintained regardless of input size. No auxiliary array, no recursion stack, no extra data structure.

Given the constraint of at most 50 elements, even the O(n²) brute force would run instantly — but the one-pass solution isn't harder to write, so there's no real tradeoff being made by choosing it. In a timed test run on a 50-element input, the brute force took roughly 48 microseconds versus roughly 16 microseconds for the optimal version — about a 3x difference even at this tiny scale, and the gap only widens as n grows.

18. Alternative Solutions

A reasonable variant is to compute the increasing and decreasing streaks as two completely separate passes — one loop dedicated to tracking increasing runs, a second loop dedicated to tracking decreasing runs, then taking the max of the two results. This is still O(n) time and O(1) space, so asymptotically it's identical to the single-pass version. The only real difference is style: two simpler, more narrowly-focused loops versus one loop juggling two counters. The combined single-pass version is slightly more elegant and touches each element only once in wall-clock terms, but both are valid, interview-acceptable answers — pick whichever reads more clearly to you under pressure.

19. Edge Cases

  • Empty array: Not valid per constraints (the array always has at least one element), so no special handling is needed, but if it arose, the loop would simply never execute and best would remain at its initial value.
  • Single element: best stays at 1, which is correct — a lone number is a streak of length one.
  • All elements equal, e.g. [3, 3, 3, 3]: Every comparison hits the else branch, so inc and dec reset at every step and best never exceeds 1.
  • Strictly increasing entire array, e.g. [1, 2, 3, 4]: inc grows every step and ends up equal to n, so best equals the full array length.
  • Strictly decreasing entire array: Mirror of the above, with dec growing to the full length.
  • Minimum and maximum values (1 and 50 per constraints): The logic only depends on relative comparisons between neighbors, so the actual magnitude of the values never affects correctness.
  • Zigzag pattern, e.g. [1, 5, 2, 6, 3]: Every step flips direction, so neither inc nor dec ever grows past 2, and best caps at 2.

20. Common Mistakes

  1. Using >= or <= instead of strict > and <. This silently allows ties to extend a streak, which is wrong by the problem's own definition of "strictly."
  2. Forgetting to reset the other counter when one grows. If inc grows but dec isn't reset to 1 on an increase, dec can carry stale, inflated values forward.
  3. Not resetting both counters on a tie. A tie breaks both directions, not just the one currently "winning."
  4. Initializing counters to 0 instead of 1. This undercounts every streak by one, since a single element is already a valid run of length one.
  5. Checking best only after the loop instead of after every step. This misses cases where the peak streak length occurs partway through the array rather than at the very end.
  6. Restarting the scan from every index (brute force) without realizing the redundant comparisons, which works but wastes time proportional to n² for no benefit when a one-pass version is just as easy to write.

21. Interview Questions

  • How would this change if the array could contain duplicates representing "non-strict" monotonic runs as well — would you track four counters instead of two?
  • Can you modify this to return the actual subarray (start and end indices), not just its length?
  • What if you needed the longest strictly increasing run specifically, ignoring decreasing runs entirely — how does the solution simplify?
  • How would you adapt this logic to a 2D grid, finding the longest monotonic run along rows or columns?
  • Could this be solved with a single counter instead of two, using some clever sign-tracking trick? What are the tradeoffs?

23. Key Takeaways

The core lesson here isn't really about this specific problem — it's about a pattern. Any time you're asked for the longest run, streak, or consecutive block in an array, ask yourself: can I describe the state I need at position i using only information from position i-1? If yes, you almost never need more than a single pass and a couple of counters. The equal-case handling is the detail that separates a solution that looks right from one that's actually correct — always trace through a worst-case tie input like [3, 3, 3, 3] before trusting your logic.
