11. Container With Most Water | LeetCode Daily Python Solution (the trick nobody sees)

General ✓ Runtime tested

Introduction

Container With Most Water shows up constantly in interview prep lists, and for good reason — it's one of the cleanest examples of a pattern you'll reuse for the rest of your career: the two-pointer squeeze. Companies like Amazon and Google favor it because it isn't really testing whether you know a trick. It's testing whether you can look at an O(n²) brute force, notice that most of the work is wasted, and prove that a smarter approach won't miss the right answer.

That last part is the real skill. Plenty of engineers can write the two-pointer code once they've seen it before. Far fewer can explain, from scratch, why moving the shorter wall is always safe. That's what we're building here — not just the code, but the reasoning that lets you rediscover this pattern the next time it shows up in a different disguise.

Problem Overview

You're given an array of non-negative integers, where each value represents the height of a vertical line standing at that index. Pick any two of these lines. Together with the x-axis between them, they form a container that can hold water.

The amount of water that container holds depends on two things:

  • Width — the horizontal distance between the two chosen lines (the difference in their indices).
  • Height — capped by whichever of the two lines is shorter, since water spills over the shorter side.

Your task: find the two lines that maximize the area of water trapped, and return that maximum area. The container can't be tilted — the water surface is always flat, so the shorter wall sets the limit no matter how tall the other one is.

Example

Take heights = [1, 8, 6, 2, 5, 4, 8, 3, 7].

If you pick index 1 (height 8) and index 6 (height 8), the width is 6 - 1 = 5 and the height is min(8, 8) = 8, giving an area of 40.

But if you pick index 1 (height 8) and index 8 (height 7), the width is 8 - 1 = 7 and the height is min(8, 7) = 7, giving an area of 49 — the actual best answer for this array.

Notice something important: the pair with the tallest matching walls (40) isn't the winner. The pair with slightly more width and a "good enough" short wall (49) beats it. That's the whole tension in this problem — height and width trade off against each other, and greedily chasing the tallest wall is a trap.

Intuition

Start by picturing the brute-force instinct: check every pair of walls, compute the area, keep the best. That works, but it means checking every possible width from smallest to largest — a lot of pairs that obviously can't win.

Instead, think about the two most extreme choices you could make: the very first wall and the very last wall. That pairing gives you the maximum possible width. Any other pair you pick will have equal or smaller width. So this is a reasonable place to start — not because it's the answer, but because it's the widest, and width is expensive to give up.

Now ask: from here, is there ever a reason to move the taller of the two walls inward?

No. The taller wall isn't the bottleneck — the shorter wall is capping the water level. If you move the taller wall inward, you only lose width, and the height is still capped by the same short wall as before. You cannot do better. That move can be ruled out entirely, no computation needed.

But moving the shorter wall inward has potential. You lose the same one unit of width, but you might discover a new wall that's taller than the one you just abandoned — and if the new shorter-side height goes up enough, it can outweigh the width you gave up.

This is the whole insight: only moving the shorter wall can possibly produce a better answer. So you start wide, and repeatedly discard the shorter wall, sliding it inward — because every wall you skip past was already proven incapable of beating what you've seen.

Brute Force Solution

Idea: Check every pair (i, j) where i < j, compute min(height[i], height[j]) * (j - i), and track the maximum.

Algorithm: 1. Loop i from 0 to n-1. 2. Loop j from i+1 to n-1. 3. Compute the area for (i, j) and update the max if it's larger.

Advantages: Trivial to reason about, guaranteed correct, no edge cases to worry about.

Disadvantages: Recomputes areas for pairs that can be provably ruled out. For large inputs, this becomes unusable.

Time complexity: O(n²) — every pair is checked. Space complexity: O(1) — just a running maximum.

Optimal Solution

The two-pointer squeeze works like two judges walking in from opposite ends of the array:

Step Left Right Shorter wall Width Area Action
1 index 0 (h=1) index 8 (h=7) left 8 8 move left
2 index 1 (h=8) index 8 (h=7) right 7 49 move right
... ... ... ... ... ... continue until pointers meet

Each step, you: 1. Compute the area for the current left/right pair. 2. Update the best area seen so far. 3. Move whichever pointer points at the shorter wall inward.

You stop when left and right meet. Every step discards exactly one wall from consideration — and the proof above guarantees nothing better was hiding behind it.

Python Code

def max_area(heights: list[int]) -> int:
    """Return the maximum water area trappable between two walls."""
    left, right = 0, len(heights) - 1
    best_area = 0

    while left < right:
        width = right - left
        h = min(heights[left], heights[right])
        best_area = max(best_area, h * width)

        # The shorter wall is the bottleneck, so it's the only side
        # that can ever produce a better result — move it inward.
        if heights[left] < heights[right]:
            left += 1
        else:
            right -= 1

    return best_area

Code Walkthrough

  • left, right = 0, len(heights) - 1 — start with the widest possible container.
  • best_area = 0 — tracks the best result found so far; safe starting value since area is never negative.
  • while left < right — stop once the pointers meet; there's no container left to measure.
  • width = right - left — horizontal distance between the two walls.
  • h = min(heights[left], heights[right]) — the shorter wall caps the water level.
  • best_area = max(best_area, h * width) — update the running maximum.
  • if heights[left] < heights[right]: left += 1 else: right -= 1 — always move the shorter wall inward. On a tie, moving either side is safe; the code picks right.

Dry Run

Using heights = [1, 8, 6, 2, 5, 4, 8, 3, 7]:

  1. left=0 (1), right=8 (7) → width 8, h=1, area=8. best_area=8. Left is shorter → left=1.
  2. left=1 (8), right=8 (7) → width 7, h=7, area=49. best_area=49. Right is shorter → right=7.
  3. Pointers keep sliding inward as right walks from index 7 down toward left, but no pair beats an area of 49 for this array.
  4. Loop ends when left == right. Return best_area = 49.

Complexity Analysis

Time: O(n) — each pointer moves inward exactly once over the course of the algorithm, never backward, so the total number of steps is bounded by n.

Space: O(1) — only a constant number of variables (left, right, best_area) regardless of input size.

These bounds are correct because the proof in the Intuition section guarantees no pair is ever skipped that could have produced a better answer — the algorithm doesn't just run faster, it's provably not missing anything.

Alternative Solutions

You could precompute a "max height to the right" array or similar structures, borrowing ideas from Trapping Rain Water — but that problem asks for a fundamentally different quantity (total trapped water across the whole array, not the best single pair), so those structures add complexity here without adding correctness. For this specific problem, the two-pointer squeeze is already optimal in both time and space, so there's no meaningfully faster or leaner alternative.

Edge Cases

  • Fewer than 2 walls: Not a valid input per constraints, but if encountered, the loop simply never executes and returns 0.
  • All walls the same height: h is just that shared height every iteration; correctness holds.
  • Two walls total: The loop runs exactly once, computing the only possible area.
  • Walls of height 0: Contribute 0 to any area they're part of, but don't break the logic.
  • Duplicate heights scattered through the array: No special handling needed — min() and the comparison logic work identically regardless of duplicates.

Common Mistakes

  1. Moving the taller wall instead of the shorter one. This is the single most common bug — it feels intuitive ("taller must be better") but it can never improve the answer and wastes the search.
  2. Forgetting the water level is capped by the shorter wall, and mistakenly using max() instead of min() when computing height.
  3. Off-by-one errors in width calculation — width is right - left, not right - left + 1 (indices, not counts).
  4. Not updating best_area before moving a pointer, which silently drops the correct answer on the final relevant iteration.
  5. Assuming brute force and two-pointer explore the same pairs — they don't; the two-pointer approach explicitly skips pairs it has proven can't win, so trying to "verify" it against a partial brute-force trace can be misleading if you don't track which pairs were skipped and why.

Interview Questions

  • Why is it safe to move only the shorter pointer, and never the taller one?
  • Can you prove that this greedy approach never misses the optimal pair?
  • How would you modify this solution if the container could be tilted?
  • What's the difference between this problem and Trapping Rain Water?
  • Can you solve this without extra space beyond two pointers?

Key Takeaways

The two-pointer squeeze pattern applies whenever you're searching for a best pair between two ends of an array, and you can prove that moving one particular side is always safe to discard. Start wide, then shrink from the side that's actually limiting your result — never the side that isn't. Container With Most Water is the cleanest possible introduction to this idea, which is exactly why it keeps showing up in interviews.

📇 Flashcards

Two-pointer squeeze: when does this pattern apply?

Array/string + need best pair from two ends, shrinking search space by moving one side inward each step.

Time complexity of the two-pointer solution?

O(n) — single pass, each pointer moves at most n times total.

Space complexity of the two-pointer solution?

O(1) — just two index variables and a running max, no extra structures.

Why move the shorter wall, not the taller one?

Width always shrinks; keeping the taller wall preserves the only chance at a bigger height, so moving it can only lose area.

Brute force vs two-pointer here — what's skipped safely?

Brute force checks all O(n^2) pairs; two-pointer proves moving the short wall inward skips only pairs that can't beat the current best.

Follow-up: does the two-pointer proof still hold with duplicate heights?

Yes — ties can move either pointer; area only depends on min height and shrinking width, duplicates don't break the invariant.
