11. Container With Most Water | LeetCode Daily Python Solution (the trick nobody sees)

General ✓ Runtime tested

Introduction

Container With Most Water shows up constantly in coding interview prep lists, and there's a good reason for that: it looks simple on the surface, but it quietly tests whether you can spot a greedy insight that isn't obvious from the problem statement alone. Anyone can write the brute-force version in a few minutes — loop over every pair, compute the area, keep the max. It works. It also passes every tiny test case an interviewer throws at you early on.

The real signal comes from what happens next. When the interviewer asks "can you do better than O(n²)?", this is the moment where a lot of candidates stall. The two-pointer trick that solves this problem isn't a memorized formula — it's a reasoning pattern that reappears in Trapping Rain Water, 3Sum, and a whole family of array problems where you're searching for an optimal pair or triplet under a monotonic constraint. Once you internalize why moving the shorter wall is the only move worth making, you'll recognize the same shape of argument the next time it shows up in a different disguise.

This walkthrough builds the intuition from scratch, not just the final code, so you can reconstruct the solution on a whiteboard without having seen this exact problem before.

Problem Overview

You're given an array of non-negative integers, where each number represents the height of a vertical line drawn at that index on the x-axis. Pick any two of these lines. Together with the x-axis between them, they form a container capable of holding water.

The catch: the container's walls are rigid and vertical, so water can never rise above the shorter of the two chosen lines — the taller line's extra height above the shorter one is just wasted, it doesn't hold anything back that would otherwise spill.

The amount of water held is:

area = width × height
width = distance between the two chosen indices
height = the shorter of the two line heights

Your task is to choose the pair of lines that maximizes this area and return that maximum value.

Example

Take the array:

heights = [1, 8, 6, 2, 5, 4, 8, 3, 7]
indices =  0  1  2  3  4  5  6  7  8

The best pair here is index 1 (height 8) and index 8 (height 7).

  • Width = 8 - 1 = 7
  • Height = min(8, 7) = 7
  • Area = 7 × 7 = 49

Notice that index 6 also has height 8 — taller than index 8's height of 7 — but pairing index 1 with index 6 gives width 5, so area 5 × 8 = 40, which is smaller. A taller wall isn't automatically better; width matters just as much as height, and the winning pair balances both.

Intuition

Don't start by thinking about code. Start by thinking about what makes a container big: it needs to be either wide, tall, or both. Since height is capped by whichever wall is shorter, tall alone isn't enough — you need the shorter of your two chosen walls to still be reasonably tall while the walls are also far apart.

Here's the key move an experienced engineer makes: start with the widest possible container, the one formed by the very first and very last line. This container has the maximum width you could ever get, though its height might not be great.

Now ask: from here, is there any way moving the taller wall inward could help? No — moving it inward only shrinks the width, and since the shorter wall was already the limiting height, moving the taller wall doesn't change that cap at all. It can only make things worse or, at best, equal. So it's never worth trying.

But moving the shorter wall inward might help. You lose a bit of width, but you have a chance at finding a taller line that raises the water cap enough to make up for it. That's the only move that could possibly reveal something better — so that's the move you always make.

This single observation is what collapses an O(n²) search into an O(n) pass: at every step, you eliminate the shorter wall from ever being useful again in combination with anything to its inside, because any container using that wall and a line further in is strictly narrower with the same or lower height cap.

Brute Force Solution

Idea: Try every possible pair of lines, compute the area for each, and track the maximum.

Algorithm: 1. For each index i from 0 to n-1. 2. For each index j from i+1 to n-1. 3. Compute width = j - i, height = min(heights[i], heights[j]), area = width * height. 4. Update the running maximum.

Advantages: Trivial to write, easy to reason about, guaranteed correct.

Disadvantages: Checks every pair even though most of them are provably worse than pairs you've already checked. Doesn't scale.

Complexity: - Time: O(n²) — nested loop over every pair. - Space: O(1) — no extra data structures.

With 10 lines, that's roughly 45 comparisons — nothing. With 100,000 lines, that's about 10 billion comparisons, which will time out on any real judge or interview constraint.

Optimal Solution

Set two pointers: left at index 0, right at index n-1. Track max_area = 0.

Loop while left < right:

Step Action
1 Compute width = right - left
2 Compute height = min(heights[left], heights[right])
3 Compute area = width * height, update max_area if larger
4 Move the pointer at the shorter wall inward by one

Repeat until left meets right. Return max_area.

Each iteration eliminates exactly one line from ever being the limiting wall again, and each line is visited at most once, which is what gives you the linear time bound.

Python Code

from typing import List


def max_area(heights: List[int]) -> int:
    left, right = 0, len(heights) - 1
    best = 0

    while left < right:
        width = right - left
        height = min(heights[left], heights[right])
        best = max(best, width * height)

        # The taller wall can never raise the cap by moving inward,
        # so only the shorter wall's side is worth advancing.
        if heights[left] < heights[right]:
            left += 1
        else:
            right -= 1

    return best

Code Walkthrough

  • left, right = 0, len(heights) - 1 — start with the widest possible container.
  • best = 0 — nothing has been measured yet, so the running maximum starts at zero.
  • while left < right — stop once the pointers meet; a single line can't form a container by itself.
  • width = right - left — the horizontal distance between the two chosen walls.
  • height = min(heights[left], heights[right]) — water can never rise above the shorter wall.
  • best = max(best, width * height) — keep the largest area seen so far.
  • if heights[left] < heights[right]: left += 1 else: right -= 1 — always advance the pointer on the shorter side, since that's the only move that could possibly find a taller cap.

Dry Run

1 (8) 8 (7) 7 7 49 49 right--
1 (8) 7 (3) 6 3 18 49 right--
1 (8) 6 (8) 5 8 40 49 right--

1 (8) 4 (5) 3 5 15 49 right--
1 (8) 3 (2) 2 2 4 49 right--
1 (8) 2 (6) 1 6 6 49 right--

left and right meet — loop ends. Return 49, matching the winning pair from the example.

Complexity Analysis

  • Time: O(n) — each iteration moves exactly one pointer, and each pointer can move at most n times total across the whole run, so the loop body executes at most n times.
  • Space: O(1) — only a handful of scalar variables are used, regardless of input size.

Both bounds are tight: you can't do better than O(n) here because in the worst case you must inspect every line at least once to know it isn't part of the answer (consider an array that's strictly increasing then strictly decreasing — every value could plausibly matter until checked).

Alternative Solutions

A monotonic-stack approach is sometimes suggested, but it doesn't actually fit this problem well — that pattern shines in Trapping Rain Water, where you're accumulating water contributed by every bar, not searching for a single best pair. For Container With Most Water, two pointers is both the simplest and the asymptotically optimal approach; there's no meaningfully different algorithm worth comparing it against here.

Edge Cases

  • Fewer than two lines: with 0 or 1 elements, no container can be formed — the loop never executes, best stays 0.
  • All heights equal: e.g., [4, 4, 4, 4] — height never changes, so the widest pair automatically wins; the algorithm still finds it correctly since width shrinks monotonically as pointers close in.
  • Two lines only: [1, 1] — width 1, height min(1, 1) = 1, area 1. The loop runs exactly once.
  • Very tall wall far from a short one: e.g., [1, 1000] — height is still capped by the shorter wall (1), so the algorithm correctly returns a small area instead of being fooled by the tall bar.
  • Duplicate maximum heights: ties are handled naturally since min() doesn't care which side is "first" — either branch of the if still makes progress.

Common Mistakes

  1. Moving the taller pointer instead of the shorter one. This throws away containers that could still beat the current best — the taller side was never the limiting factor.
  2. Sorting the array first. Sorting destroys the original indices, and width depends entirely on original positions, not on relative height order.
  3. Using <= instead of < in the while condition, or forgetting the loop condition entirely, causing an off-by-one or infinite loop.
  4. Forgetting to update best before moving a pointer. If you move first and compute area second, you'll skip evaluating the current pair entirely.
  5. Assuming height is max() instead of min(). Water spills over the shorter wall, not the taller one — this single flipped function call silently breaks every test case involving unequal heights.

Key Takeaways

Start from the widest possible container and always release the shorter wall — that single greedy rule is provably safe because the taller wall could never have raised the cap anyway. This turns an O(n²) brute-force scan into a single O(n) pass with no extra space. The pattern generalizes: whenever you're searching for an optimal pair under a "the weaker element decides the outcome" constraint, check whether narrowing from both ends while discarding the weaker side is safe — it often is.
