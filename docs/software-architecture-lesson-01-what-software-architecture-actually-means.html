Software-Architecture Lesson 1: Software Architecture Lesson 1: The One Change That Breaks Everythin

General

Introduction

Every developer hits this wall eventually. The first feature you build in a new codebase takes an hour. A few months later, a feature of the exact same size takes three days — sometimes longer. Nothing about your skill changed. Nothing about the difficulty of the feature changed. So what did?

This is one of those questions that separates engineers who've only ever worked solo on small projects from engineers who've kept a large system alive for years. It shows up constantly in system design interviews, in "tell me about a time you dealt with technical debt" behavioral questions, and in the day-to-day frustration of every team that's ever said "we need to refactor this before we can ship anything else."

The answer isn't about writing cleaner code line by line. It's about architecture — a word that gets thrown around so loosely that most developers can't actually define it, let alone tell you how it's different from "design" or "clean code." Understanding that distinction is what lets you diagnose why a codebase is slow to work in, and more importantly, prevent it from happening in the first place.

Problem Overview

Here's the scenario, stripped down to its core: a developer builds a login form on day one of a project. It takes an hour. Months later, that same codebase has grown, and a feature of comparable size — not more complex, just comparable — takes multiple days to ship.

The natural instinct is to blame something concrete: the code got messier, the team got slower, maybe morale dropped. But swap in a brand-new, highly competent developer who's never touched the codebase before, and the same slowdown happens to them too. That rules out a skill or motivation problem. Something about the structure of the system itself is generating the slowdown, independent of who's working in it.

The core confusion is that three separate concerns get flattened into one vague phrase: "how the code is built."

  • Implementation is the literal line of code you're writing right now.
  • Design is how a single piece is shaped internally — its functions, its classes, its internal logic.
  • Architecture is a narrower and different question entirely: which parts of the codebase are allowed to import which other parts. It's not about how a function works. It's about whether that function is even reachable from where you're standing.

When people say "this code needs better architecture," they often mean "this function is ugly" — which is a design problem, not an architecture problem. Fixing the wrong layer wastes time and doesn't solve the actual issue.

Example

Imagine a small e-commerce codebase with two areas: a User module (signup, login, profile data) and a Billing module (subscriptions, invoices, payment methods).

Scenario A — Design problem: The function that calculates a user's subscription total is 200 lines long, deeply nested, and hard to read. That's a design issue. You can rewrite that one function in isolation and nothing outside it needs to know.

Scenario B — Architecture problem: Somewhere in the User module, someone wrote from billing.internal import get_payment_token to grab one helper function. It works. Six months later, a developer refactors Billing to change how payment tokens are stored — a completely reasonable, self-contained change from Billing's point of view — and the User module breaks in production, because it was quietly depending on an internal detail nobody documented.

Scenario B is the one that costs three days instead of one hour. The bug isn't in any single function — it's in an undocumented dependency between two parts of the system that nobody decided should exist.

Intuition

Here's how an experienced engineer thinks about this, and it starts with a question most people don't ask: who is allowed to know about whom?

For a weekend project — one file, a handful of functions — this question doesn't matter. Every function can see every other function, and there's nothing to get lost in. One file is sufficient architecture for that scale. Adding boundaries there would be pure overhead.

But growth changes the math. Ten files. Fifty. Three hundred. At some point — and this point differs per team, but it always arrives — no single person can hold the entire system in their head anymore. Past that line, every change you make risks breaking something you cannot see, because you don't know what's silently depending on the thing you're touching.

Without explicit boundaries, any part of the code can reach into any other part. That access isn't planned — it's discovered by developers under time pressure who need one small thing from another module and take the shortest path to get it. Nobody sits down and decides "let's make Billing depend on User's internals." It happens one quick import at a time, each one reasonable in isolation, until the dependency graph is an unreadable mess.

The fix isn't to eliminate connections between modules — Billing legitimately needs data from User sometimes. The fix is to make every connection a decision, not an accident. Instead of reaching directly into another module's internals, you go through a defined interface: a public function, an API, a contract that says "this is the surface area I'm exposing, and I'll keep it stable." That single shift — from silent coupling to declared coupling — is what architecture actually buys you.

Brute Force Solution

The "brute force" approach to a growing codebase is the one most teams fall into by default: no boundaries at all. Any file can import any other file directly. There's no distinction between a module's public surface and its internal implementation details.

Idea: Let developers import whatever they need, wherever they need it, whenever a feature calls for it.

Algorithm: 1. Need a function from another part of the codebase? Import it directly. 2. Ship the feature. 3. Repeat, indefinitely, across every module.

Advantages: - Zero upfront cost. No time spent designing interfaces. - Fast for the first several features, when the codebase is still small enough to reason about.

Disadvantages: - Coupling grows invisibly. Nobody can tell, just by looking at a module, who depends on it. - Refactoring becomes dangerous. Changing an "internal" detail can break a distant, unrelated feature. - Onboarding gets harder — new developers can't safely change anything without grepping the entire codebase first. - The three-day feature. This is precisely the failure mode described in the transcript.

Time and space complexity (informally): Cost per feature grows roughly linearly, then superlinearly, with codebase size — because the number of undocumented dependencies a change might collide with grows with the number of modules that have ever been allowed to import each other freely. There's no formal Big-O here, but the intuition holds: unconstrained coupling means unconstrained blast radius.

Optimal Solution

The optimal approach is to define, deliberately and in advance, which modules are allowed to depend on which — and to enforce that only public interfaces are ever imported, never internal details.

Here's the shape of it:

Module Allowed to depend on Exposes
User nothing else get_user(id), create_user(...)
Billing User (via its public interface only) charge_user(id, amount)
Notifications User, Billing (via public interfaces) send_receipt(...)

The rule: Billing can call get_user(id), because that's a declared, public contract. Billing cannot reach into User's database table directly, or import a private helper function from inside User's package. If Billing needs something User doesn't expose, that's a conversation — "should User expose this?" — not a silent workaround.

This is usually enforced with a small number of concrete techniques: - Package/module boundaries with explicit public APIs (e.g., only import from user/__init__.py, never from user/internal/db.py). - Dependency direction rules — often drawn as a simple graph — stating which layers can import which (e.g., "nothing may import from api/ except main"). - Interfaces or abstract contracts between modules, so the shape of a dependency is fixed even if the internal implementation changes freely.

None of this requires a diagram nobody reads or a review committee. It requires a small number of decisions, written down once, ideally enforced by linting or import rules so violations get caught automatically rather than discovered in production.

Python Code

Below is a minimal, runnable illustration of the difference between undisciplined coupling and a boundary-enforced design — using Python's package structure as the enforcement mechanism.

# --- billing/internal.py ---
# Treated as private: nothing outside `billing` should import this directly.

def _get_stored_token(user_id: str) -> str:
    """Simulates a low-level lookup a UI/other module should never touch."""
    return f"token-for-{user_id}"


# --- billing/api.py ---
# The ONLY module other packages are allowed to import from.

from billing.internal import _get_stored_token


def charge_user(user_id: str, amount: float) -> str:
    """Public contract: charge a user. Internals may change freely
    as long as this function's behavior stays stable."""
    token = _get_stored_token(user_id)
    return f"Charged {amount} using {token}"


# --- user/api.py ---
# User module's public surface. Does NOT import from billing.internal.

from billing.api import charge_user


def upgrade_user_plan(user_id: str, plan_price: float) -> str:
    """Depends only on billing's declared public interface."""
    return charge_user(user_id, plan_price)


# --- boundary check (lightweight enforcement) ---

import ast
import pathlib


def find_illegal_imports(package_dir: str, forbidden_module: str) -> list[str]:
    """Scans .py files for direct imports of a module marked internal."""
    violations = []
    for path in pathlib.Path(package_dir).rglob("*.py"):
        if "internal" in path.parts:
            continue  # internal files may import their own siblings
        tree = ast.parse(path.read_text())
        for node in ast.walk(tree):
            if isinstance(node, ast.ImportFrom) and node.module == forbidden_module:
                violations.append(str(path))
    return violations

Code Walkthrough

  • billing/internal.py holds implementation details. The leading underscore on _get_stored_token is a convention signaling "not part of the contract."
  • billing/api.py is the only file other modules should ever import from. charge_user is the boundary — the one function Billing promises to keep stable.
  • user/api.py imports from billing.api, never billing.internal. This is the declared dependency: User is allowed to depend on Billing's public interface.
  • find_illegal_imports is a small static-analysis check: it walks the AST of every file outside the internal folder and flags any file that imports directly from a forbidden internal module. This is a simplified version of what tools like import-linter or custom CI checks do in real codebases — turning an architectural rule into something a machine enforces, instead of a rule people have to remember.

Dry Run

Suppose billing/internal.py's _get_stored_token gets refactored to fetch from a new caching layer instead of a database — an internal implementation change.

  1. charge_user in billing/api.py still calls _get_stored_token(user_id) and gets a token back. Its signature and behavior from the outside are unchanged.
  2. user/api.py's upgrade_user_plan still calls charge_user(user_id, plan_price). It never touched _get_stored_token directly, so it's completely unaffected by the internal refactor.
  3. Running find_illegal_imports("user", "billing.internal") returns an empty list — confirming User never took a shortcut into Billing's internals.

Compare this to the brute-force version, where user/api.py might have imported _get_stored_token directly. In that world, step 1's refactor breaks user/api.py immediately, and nobody investigating the User module would think to look inside Billing for the cause.

Complexity Analysis

There's no traditional Big-O here since this isn't an algorithm on a data structure — it's a structural property of a codebase. But the analogous "complexity" is useful to name:

  • Blast radius (brute force): proportional to the total number of modules that have ever had an unrestricted import path to the changed code — effectively unbounded as the codebase grows, since any file could theoretically depend on any other.
  • Blast radius (boundaries enforced): bounded to the modules that consume a given public interface. If Billing only exposes charge_user, then only callers of charge_user are ever at risk from a Billing change — internal refactors are provably safe.

This is why the fix isn't "write better code" — it's "shrink the set of things a change can possibly affect," which is a structural, not a stylistic, improvement.

Alternative Solutions

Microservices push this idea further by making the boundary a network call instead of a package boundary — you can't accidentally import another service's internals because they're not even in the same process. This solves the coupling problem completely but adds real operational cost (network latency, deployment complexity, distributed debugging). For most teams, it's overkill until the org itself needs to scale, not just the code.

Monorepo with enforced import rules (the approach shown above) gets most of the same benefit — explicit, enforced boundaries — without the operational overhead of separate deployments. This is usually the better starting point.

Hexagonal / ports-and-adapters architecture is a more formalized version of the same idea, where every module defines "ports" (interfaces) it depends on, and concrete implementations are plugged in from outside. It's worth reaching for once a system has many external dependencies (databases, third-party APIs) that need to be swappable or mockable for testing.

All three are the same core idea at different scales: decide the dependency direction on purpose, then enforce it.

Edge Cases

  • Empty codebase / brand-new project: No boundaries needed yet. Adding them too early is its own mistake — premature architecture slows down the exact phase where speed matters most.
  • Circular dependencies: If User needs something from Billing and Billing needs something from User, that's a sign the boundary is drawn in the wrong place — usually the shared piece should be extracted into a third module both depend on.
  • One-off internal exception: A "just this once" import of an internal detail under deadline pressure. This is exactly the failure mode described in the transcript — it works today and becomes untraceable coupling later.
  • A module that's grown too large to have one clean interface: Often a sign the module itself needs to be split, not that the boundary concept has failed.
  • Legacy code with no boundaries at all: You don't need to fix everything at once — start by enforcing boundaries on new code, and only retrofit the parts of the old code that keep causing incidents.

Common Mistakes

  1. Confusing "messy function" with "bad architecture." Ugly code inside one function is a design problem — fix it locally. Don't restructure the whole system to solve a local readability issue.
  2. The "quick import." Grabbing one internal helper from another module because it's faster than asking for a public interface. This is the single most common way silent coupling is introduced.
  3. Treating architecture as a one-time diagramming exercise. A diagram nobody updates is worse than no diagram — it actively lies about the current dependency structure.
  4. Adding boundaries to a project too early. A weekend project doesn't need module boundaries. Enforcing them before the system is complex enough wastes time and adds friction for no benefit.
  5. Believing more layers automatically means better architecture. Boundaries should map to real, meaningful separations of concern — not be added for their own sake. Over-layering a small system creates its own kind of confusion.

While this isn't a LeetCode-style algorithmic problem, the underlying reasoning connects to problems that test dependency and graph thinking:

  • Course Schedule (LeetCode 207 / 210): Detecting cycles in a dependency graph — directly analogous to catching circular module dependencies.
  • Design patterns questions (Dependency Injection, Strategy Pattern): Both are concrete mechanisms for keeping a dependency direction explicit rather than hardcoded.
  • System design interview prompts (e.g., "design a URL shortener," "design an e-commerce checkout flow") almost always implicitly test whether you draw sensible service/module boundaries, even when not asked directly.

Key Takeaways

  • The slowdown from feature one to feature ten isn't a skill problem — it's a structural one.
  • Implementation, design, and architecture are three different questions. Architecture specifically asks: which parts of the code are allowed to depend on which.
  • Small projects don't need boundaries. Growth is what makes them necessary — past the point where one person can hold the whole system in their head.
  • Uncontrolled coupling isn't intentional — it accumulates one "quick import" at a time.
  • The fix isn't zero connections between modules. It's making every connection a deliberate decision instead of an accidental discovery.

📇 Flashcards

What is the primary difference between architecture, design, and implementation?

Architecture defines high-level boundaries and modules. Design details interfaces within those modules. Implementation writes specific code.

Why does 'just starting to code' cause a slowdown in larger projects?

Without defined boundaries, changes ripple unpredictably, creating hidden breakages that force extensive debugging instead of focused development.

What is the main benefit of drawing boundaries on purpose?

It limits the blast radius of changes, ensuring modifications in one area do not unexpectedly break unrelated parts of the system.

Which metric indicates a lack of architectural boundaries?

When one small change requires many calls across different modules or reveals hidden dependencies between distant parts of the codebase.
