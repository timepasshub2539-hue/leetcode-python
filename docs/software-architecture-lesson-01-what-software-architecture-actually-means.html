Why "Just Start Coding" Breaks Down

Every developer has lived this: a task that should take thirty minutes eats three days instead. Not because the feature was hard — because the codebase fought back. You touch one file and three others quietly break. You spend more time figuring out what's safe to change than actually changing it.

This isn't a skill problem. It's an architecture problem, and it's one of the most common things that separates engineers who can ship confidently in a large codebase from those who can only move fast in a small one. Interviewers test this constantly — not by asking you to define "architecture," but by watching whether the code you write in a 45-minute session would survive being touched by five other people six months from now.

This lesson isn't about diagrams or buzzwords. It's about three concrete layers of a codebase and one decision that determines whether your project stays easy to change or slowly turns into a minefield.

Problem Overview

Here's the situation in plain terms: a codebase starts small. One file, two hundred lines, one person writing it. At that size, you can hold the entire thing in your head. If you need to add a button, you just add it — call a function, wire it up, done. There's nothing to plan because there's nothing you can't see.

Now fast-forward. The same project is fifty files deep, three people are contributing, and it's been six months. Nobody holds the whole system in their head anymore. Every change is now a bet on what you can't see — and that bet is exactly where the three days went.

The core problem: code that was organized for "add a function, call it" no longer works once the system is too big to see all at once. Something has to replace your mental model of the whole codebase. That something is architecture.

Example

Say you're building a feature: a "Save Draft" button on a blog editor.

  • At 200 lines: the button's click handler directly calls save_to_db(content). One file. It works, and it's the fastest way to ship it.
  • At 50 files: that same pattern — UI code calling the database directly — is now duplicated across a dozen screens: the editor, the admin panel, the mobile sync job. Someone changes the drafts table schema to add a version column, and now six unrelated screens break, because they all reached into the database independently instead of going through one shared path.

The first version isn't wrong. It's just sized for its context. The second version is where the boundary should have existed and didn't.

Intuition

Here's how an experienced engineer thinks about this, before writing a single line of a new feature.

They separate three questions that are easy to blur together:

  1. What does this one function do? (Implementation)
  2. How do the functions in this one file cooperate? (Design)
  3. Which files are allowed to call which other files? (Architecture)

These are zoom levels on the same codebase, not different topics.

Implementation is the innermost layer — the click handler, the API call inside it. One function, one job. Change it, and only that function moves.

Design zooms out to the file that function lives in. It's how the functions inside that file cooperate — validate input, call the API, update the UI. Still one file, still one concern, but now it's about the relationships between several small pieces.

Architecture zooms out past the file entirely. It's about which parts of the codebase are allowed to depend on which other parts. The button's file can call a service. The service can hit the database. The button's file should never reach into the database directly. That's not a style preference — it's a rule about what's allowed to know about what.

The moment you skip that last layer — when UI code reaches straight into the database — you haven't made a coding mistake. You've made an architecture mistake. The code runs fine today. The cost shows up later, when two unrelated screens turn out to be secretly connected through a table they both touch directly.

Brute Force Solution ("No Boundaries")

Idea: Let any file call any other file directly. No service layer, no interfaces, no rules about what's allowed to depend on what.

Algorithm: 1. Need data? Query the database from wherever you are. 2. Need a computation? Call whatever function has it, regardless of which "layer" it's in. 3. Ship it.

Advantages: - Zero setup cost. No interfaces to write, no extra files to create. - Fastest possible path to a working feature — genuinely correct for prototypes, solo projects, or throwaway scripts.

Disadvantages: - Every file becomes a hidden dependency of every other file. Changing one table's schema can silently break screens that have nothing to do with each other. - No single place to change how data is fetched — validation, caching, and logic get copy-pasted everywhere it's needed. - The cost doesn't show up immediately, which is what makes it dangerous. It compounds silently until a routine change becomes a three-day investigation.

Time complexity (cost per change): O(1) today, but the effective cost per change grows over the life of the project as more code takes the same shortcut — closer to O(n) or worse, where n is the number of places that shortcut was taken.

Space complexity: N/A — this is a structural cost, not a memory cost, but the "space" of undocumented dependencies grows unbounded.

Optimal Solution: Enforced Boundaries

The fix isn't more code — it's a rule about which files are allowed to call which. Concretely:

UI layer  →  Service layer  →  Database layer

The UI is allowed to call the service. The service is allowed to call the database. The UI is not allowed to skip the service and touch the database directly.

Layer Responsibility Can call
UI (handler) Collect input, trigger action, render result Service layer only
Service Business logic, validation, orchestration Database layer, other services
Database Storage and retrieval Nothing above it

Why this works: when the drafts table changes shape, there's exactly one place that needs to know — the service function that talks to it. Every UI screen that calls that service keeps working unchanged. The boundary turned a schema change from "find every place that touches this table" into "update one function."

This costs something real. You now have an extra file, an extra function call, a place you have to open instead of just scrolling down in the same file. That cost is worth paying once a module's internals actually need to change without dragging the rest of the app along with it — not before.

Python Code

# db.py — database layer: knows how to talk to storage, nothing else
def fetch_draft(draft_id: str) -> dict:
    # Actual query implementation lives here.
    ...

def save_draft(draft_id: str, content: str) -> None:
    ...


# draft_service.py — service layer: business rules, the only caller of db.py
from db import fetch_draft, save_draft

MAX_LENGTH = 50_000

def save_draft_content(draft_id: str, content: str) -> None:
    if len(content) > MAX_LENGTH:
        raise ValueError("Draft exceeds maximum length")
    save_draft(draft_id, content)


# editor_handler.py — UI layer: never imports db.py directly
from draft_service import save_draft_content

def on_save_click(draft_id: str, content: str) -> None:
    save_draft_content(draft_id, content)

Code Walkthrough

  • db.py is the only file that imports a database driver. Nothing else needs to know how storage works.
  • draft_service.py imports db.py, and owns the business rule (MAX_LENGTH). This is where validation lives so it isn't duplicated across every screen that saves a draft.
  • editor_handler.py imports only draft_service.py. It has no idea a database exists. If storage moves from Postgres to something else, this file doesn't change at all.
  • The import statements are the architecture. If you can trace the boundary just by reading imports, the rule is being enforced; if editor_handler.py ever imports db.py, the boundary has already been broken.

Dry Run

A user clicks "Save Draft" with content "Hello world".

  1. on_save_click("draft-42", "Hello world") runs in editor_handler.py.
  2. It calls save_draft_content("draft-42", "Hello world") in draft_service.py.
  3. The service checks len("Hello world") > 50_000 → false, so it proceeds.
  4. It calls save_draft("draft-42", "Hello world") in db.py, which writes to storage.
  5. Control returns to the UI. No layer skipped a step; each layer only talked to the one directly below it.

Now imagine the admin panel needs to save drafts too — it calls save_draft_content, gets the same validation for free, and the database layer never had to be touched or duplicated.

Complexity Analysis

  • Time: Adding a layer adds one function call per boundary crossed — O(1) overhead per call, which is negligible at runtime.
  • Space: One extra file per layer. Fixed, small overhead, not proportional to project size.
  • Why this is correct: The real cost being optimized isn't runtime — it's change cost. Without boundaries, a schema change is O(number of callers) because every direct caller needs updating. With a service layer, it's O(1) because there's exactly one caller to fix.

Alternative Solutions

Feature-based folders instead of layer-based folders: group by feature (drafts/, comments/) rather than by layer (ui/, services/, db/). Still enforces "which file can call which" — just organizes it around features instead of technical layers. Reasonable when features rarely share logic; worse when a lot of shared business logic exists across features, since that logic has nowhere obvious to live.

Dependency injection / interfaces between layers: instead of the service importing db.py directly, it depends on an abstract interface. Useful for swapping implementations (e.g., testing with a fake database) but adds real complexity — not worth it until you actually need to swap implementations.

Edge Cases

  • Solo project, throwaway prototype: skip the boundaries entirely. The cost of architecture only pays off once more than one person or more than a few months are involved.
  • A boundary that's crossed exactly once: if only one screen ever needs direct database access, a service layer might be overkill — but be honest about whether "once" will stay true.
  • A service that needs to call another service: this is fine and common; the rule is about layers, not about a strict single path.
  • Legacy code with no boundaries at all: don't try to fix it everywhere at once — enforce the boundary only at the piece of the codebase you're currently changing.
  • A boundary you added but nothing ever needs to change independently: this is wasted cost — remove it if a module never needs to move without dragging others.

Common Mistakes

  1. Confusing "adding a function" with "having an architecture." Implementation-level changes don't require architectural decisions — the mistake is applying the same instinct at 50 files that worked at 200 lines.
  2. Treating architecture as a diagram drawn once at the start. It's an ongoing decision about what's allowed to depend on what, not a document you file away.
  3. Adding boundaries to a prototype that will be thrown away. This is premature cost with no payoff — the codebase never lives long enough to need it.
  4. Letting the UI query the database "just this once." That "once" becomes the template every future contributor copies.
  5. Discovering the boundary after the mess, instead of deciding it on purpose. Architecture problems are almost always retroactive fixes for a decision that was never made explicitly.

Interview Questions

  • How would you decide where to draw a boundary in a new service?
  • What's the difference between a design pattern and an architectural decision?
  • When is skipping a service layer the right call?
  • How do you refactor a codebase where boundaries were never enforced, without a full rewrite?
  • What signals tell you a module's internals need to change independently of the rest of the app?

Similar Problems

  • Layered Architecture / N-Tier Architecture: the general pattern this lesson demonstrates — presentation, business logic, and data layers.
  • Dependency Inversion Principle (SOLID): a stricter version of the same idea — high-level modules shouldn't depend on low-level implementation details.
  • Repository Pattern: a common way to implement the database layer shown here, abstracting storage behind a consistent interface.
  • Microservices boundary design: the same "who's allowed to call whom" question, at the scale of entire services instead of files.

Key Takeaways

  • Implementation, design, and architecture are three different zoom levels on the same codebase — not three separate topics.
  • "Just start coding" is correct at small scale and wrong at large scale — the failure isn't a skill regression, it's a missing decision about boundaries.
  • Boundaries cost real overhead. Pay that cost once a module's internals need to change independently — not before.
  • Skipping a boundary doesn't cost you today. It compounds, silently, until a small change takes days instead of minutes.
