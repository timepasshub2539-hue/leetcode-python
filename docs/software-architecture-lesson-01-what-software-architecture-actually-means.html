Software-Architecture Lesson 1: Software Architecture Lesson 1: Two Teams, Same App, Same Day, Diffe

General

Introduction

Every developer eventually hits the same wall, usually without realizing it's a wall until they've already walked into it. You're six months into a project. A feature request comes in that should take an afternoon. Instead, it takes a week, because touching one file quietly breaks three others you never meant to go near.

This isn't a skill problem. It's an architecture problem, and it's one of the most common things interviewers probe for once you're past the entry level — not "can you write a for loop," but "can you reason about how a system should be shaped before you start writing it." Junior engineers get judged on whether the code runs. Senior engineers get judged on whether the code still runs cleanly a year later, after five other people have touched it.

This lesson is about the gap between those two outcomes, and why it has almost nothing to do with talent and everything to do with a handful of decisions made — or not made — early.

Problem Overview

Picture two teams starting the exact same application on the exact same day.

Team A opens an editor and starts typing. No planning meeting, no whiteboard, just code. Team B spends their first week sketching out how the pieces of the system should relate to each other before writing a single line of business logic.

For a while, Team A looks like the clear winner. They ship features. Team B has nothing to show a stakeholder except boxes and arrows on a whiteboard.

Six months later, the picture flips. Team A is stuck — every new feature seems to require touching code in five unrelated places, and every change comes with a nagging fear of what else might break. Team B is still moving at close to their original speed.

Same language, same framework, same team size, same feature list. The only difference was whether someone deliberately decided how the pieces of the system should connect, or let that get decided by accident, one Tuesday-afternoon shortcut at a time.

Example

Let's make this concrete instead of abstract.

Say the ask is small: "Add a discount field to checkout." Same feature, dropped into two different codebases.

Codebase 1 (no boundaries): The discount logic ends up touching the checkout controller, the pricing calculator, the invoice generator, the analytics event tracker, the email receipt template, and a caching layer that assumed prices never changed mid-session. Six files. Every one of them was quietly coupled to "price," and nobody had ever drawn a line around where price-related logic was supposed to live.

Codebase 2 (clear boundaries): There's exactly one place that owns pricing logic — a PricingService that everything else calls into rather than reimplementing. Adding a discount is a five-line change inside that one file. Nothing else moves, because nothing else was ever allowed to know the internals of how price gets calculated.

Same feature. Same difficulty of the underlying logic. The only variable was whether a boundary existed before the change showed up.

Intuition

Here's how an experienced engineer actually arrives at the need for structure — it's not from reading a book on design patterns, it's from getting burned.

Think of a house instead of a codebase for a second. Laying a single brick is implementation — a function, a line of code. Deciding how one room is laid out is design — a class, a module, how a handful of pieces fit together for one purpose. Deciding how all the rooms connect into the whole house — where the load-bearing walls go, where the plumbing runs, which rooms even get to talk to each other — that's architecture.

Now ask: what's the actual cost difference between repainting a room and moving a load-bearing wall?

Repainting is contained. Worst case, you lose an afternoon. Moving a load-bearing wall is a different category of problem entirely — you're tearing out drywall, re-routing wiring, and re-checking whether the rest of the structure still holds, because everything above and beside that wall was quietly counting on it staying exactly where it was.

Code works the same way. A function is a brick — cheap to change. A class is a room — moderately expensive to change. But an architectural decision — which layer owns the database, which modules are allowed to import which — is a load-bearing wall. It's cheap to get wrong on day one and brutally expensive to fix on day two hundred, because by then, dozens of things have quietly been built on the assumption that the wall stays put.

The intuition an experienced engineer builds over time isn't "always plan everything upfront." It's much more specific: learn to recognize which decisions are bricks and which ones are walls, and spend your planning energy only on the walls.

Brute Force Solution

The "brute force" approach here is Team A's approach: start coding immediately, let structure emerge organically, deal with problems as they show up.

Idea: Write the feature that's due. Don't spend time designing for a future that might not arrive.

Algorithm: 1. Get a requirement. 2. Write the code that satisfies it, wherever seems most convenient in the moment. 3. Ship it. 4. Repeat.

Advantages: - Fastest possible short-term velocity. - Zero upfront overhead — no meetings, no diagrams, no "wasted" time. - At small scale (a handful of files), this is genuinely the correct choice. There's nothing tangled yet, so planning would just be pure overhead.

Disadvantages: - Every decision about where code lives gets made implicitly, by whoever's typing fastest that day, under deadline pressure. - Boundaries emerge by accident — usually by whoever copy-pasted the most recent similar file as a starting point. - The tangle compounds. Each new feature has to route around the mess left by the last one.

Time and space complexity (informally): Feature velocity starts high and degrades roughly with the square of codebase size, for reasons covered below. There's no fixed "space" cost in the traditional sense, but there is a growing cognitive load cost — the mental model required to safely change anything keeps expanding.

Optimal Solution

The optimal approach isn't "plan everything up front" — that's just brute force in the other direction, and it's just as wrong at small scale. The optimal approach is planning proportional to the actual cost of connections in the system, and the key insight is that this cost isn't linear.

Here's the part most people miss: connections between files don't grow with the number of files. They grow with the number of possible pairs of files — file count squared, roughly.

Files Possible connections
3 3
10 45
30 435
100 4,950

At 3 files, everything can talk to everything, and that's genuinely fine — there's nothing to manage. Adding folders, interfaces, and layers at that size is the actual mistake: you're paying a structure tax before there's any structure worth managing.

But nobody can hold 435 potential relationships in their head. Somewhere between "3 files" and "30 files," you cross a threshold where the number of things that could depend on each other exceeds what a human can track informally. That crossover — not a fixed file count, not a fixed team size — is the real point where architectural planning starts paying for itself.

The optimal strategy, then, looks like this:

  1. Below the crossover point: write code directly, skip the ceremony. Team B drawing boxes for a 3-file app would be wasting time.
  2. Approaching the crossover point: identify the load-bearing walls — the handful of decisions (who owns the database, where business rules live, what's allowed to call what) that would be catastrophically expensive to change later — and make those decisions on purpose, before the code makes them by accident.
  3. Past the crossover point: treat those boundaries as fixed constraints. New code has to fit within them, not route around them.

Python Code

Here's what the difference looks like in practice — the tangled version versus the bounded version, applied to the discount example above.

# --- Tangled version: pricing logic scattered across the app ---

class CheckoutController:
    def checkout(self, cart, user):
        price = sum(item.price * item.qty for item in cart.items)
        if user.is_premium:
            price *= 0.9  # discount logic duplicated here
        invoice = self._build_invoice(price)
        self._send_receipt_email(price, user)
        self._track_purchase_event(price)
        return invoice

    def _build_invoice(self, price):
        # another place that assumes it knows how price is computed
        return {"total": round(price, 2)}

    def _send_receipt_email(self, price, user):
        # discount logic silently duplicated again if it ever changes
        ...

    def _track_purchase_event(self, price):
        ...


# --- Bounded version: one owner for pricing logic ---

class PricingService:
    """The only place that knows how a final price is computed."""

    def calculate_total(self, cart, user) -> float:
        price = sum(item.price * item.qty for item in cart.items)
        price = self._apply_discounts(price, user)
        return round(price, 2)

    def _apply_discounts(self, price: float, user) -> float:
        if user.is_premium:
            price *= 0.9
        return price


class CheckoutController:
    def __init__(self, pricing: PricingService):
        self.pricing = pricing

    def checkout(self, cart, user):
        total = self.pricing.calculate_total(cart, user)
        invoice = {"total": total}
        self._send_receipt_email(total, user)
        self._track_purchase_event(total)
        return invoice

    def _send_receipt_email(self, total, user):
        ...

    def _track_purchase_event(self, total):
        ...

Code Walkthrough

  • Tangled version: CheckoutController owns pricing logic directly. The discount calculation is inline, which means any other file that also needs "the real price" — an invoice generator, an email template, an analytics tracker — either duplicates that logic or reaches back into the controller to get it. Both options create a hidden dependency.
  • PricingService: A single class with one job — decide what something costs. calculate_total is the only public entry point; _apply_discounts is an implementation detail nothing outside the class needs to know about.
  • CheckoutController (bounded version): Receives a PricingService instance rather than building pricing logic itself. This is the boundary in action — the controller depends on an interface (calculate_total), not on the internals of how pricing works.
  • Why this matters for the discount feature: adding a new discount rule means editing _apply_discounts — one method, in one file. Nothing else in the system needs to change, because nothing else was ever allowed to know how discounts are computed.

Dry Run

Requirement: "Give premium users a 10% discount."

Tangled version: Grep the codebase for anywhere price gets computed. Find it in the controller. Also find a second, separate price calculation in the invoice generator that was copy-pasted from an earlier version of the controller and never updated. Fix both. Ship it. Three weeks later, someone reports that receipts show the wrong total — the email template has a third copy of the pricing logic nobody remembered existed.

Bounded version: Open PricingService. Add the discount check inside _apply_discounts. Every caller — checkout, invoicing, email, analytics — automatically gets the correct total, because they all route through calculate_total. One change, one file, done.

Complexity Analysis

  • Tangled version: Each new pricing-related change has cost proportional to the number of places pricing logic has been duplicated — which tends to grow with the number of features built so far. In the worst case, this approaches O(n) places to fix for a single logical change, where n is the number of call sites, and each one is a chance to introduce a bug through inconsistency.
  • Bounded version: Each pricing-related change is O(1) relative to the size of the rest of the system — you edit one service, and correctness propagates automatically to every caller, because they all delegate rather than duplicate.
  • Why this is correct: the bounded version enforces a single source of truth. There is no path through the code that can compute a price without going through PricingService, so there's no way for the logic to drift out of sync with itself.

Alternative Solutions

A reasonable middle ground for smaller teams is lightweight modularity without full layering — group related files by feature folder (e.g., checkout/, pricing/, invoicing/) without introducing formal interfaces or dependency injection. This gets you most of the discoverability benefit of architecture with less ceremony than a fully layered system, and it's often the right call for a project that's crossed the "3 files" threshold but hasn't yet crossed the "30 files" one. The tradeoff is that boundaries are conventions rather than enforced contracts — a determined teammate can still reach across them under deadline pressure.

Edge Cases

  • A genuinely tiny script (1–3 files): Don't apply any of this. Structure here is pure overhead — you're the crossover-point exception, and the brute-force approach is optimal.
  • A prototype that everyone agrees will be thrown away: Architecture invested here is wasted investment. Bricks only, no walls.
  • A "temporary" hack that becomes permanent: The most common failure mode described in this lesson — nobody decided the database should be imported directly into every controller, it just happened once under deadline pressure and got copied. Watch for shortcuts that outlive their justification.
  • A team that over-architects a 5-file app: The inverse mistake — paying structure tax with no structure to manage yet, which slows down exactly the phase where speed should be free.
  • Legacy code with no architecture at all: Retrofitting boundaries onto an already-tangled system is expensive, but the fix isn't "rewrite everything" — it's identifying the highest-traffic load-bearing wall (usually data access) and drawing that boundary first.

Common Mistakes

  1. Applying heavy architecture to a small project. Interfaces and layers for a 3-file app is solving a problem you don't have yet.
  2. Confusing "no plan" with "no cost." Skipping the planning conversation doesn't remove the decision — it just means the decision gets made by accident, usually badly.
  3. Treating every decision as equally reversible. Not distinguishing bricks from walls means either over-planning trivial things or under-planning the ones that matter.
  4. Copying an existing file as a shortcut without checking what it silently depends on. This is exactly how "every controller imports the database directly" becomes the unspoken standard.
  5. Waiting for pain before addressing structure. By the time re-testing everything after every change feels normal, the cost of fixing the underlying boundary has already grown substantially.
  6. Mistaking a diagram for architecture. Drawing boxes on a whiteboard that nobody enforces in code isn't architecture — it's decoration. The decisions have to actually constrain what the code is allowed to do.

Interview Questions

  • How do you decide when a codebase needs more structure versus when structure would be premature?
  • What's the difference between architecture, design, and implementation, and can you give an example of each?
  • Describe a time you had to change something in a poorly structured codebase. What made it hard?
  • How would you introduce boundaries into an existing tangled codebase without a full rewrite?
  • Why does the cost of changing a system tend to grow faster than the system's size?

Similar Problems

  • Separation of Concerns principle — the general theory behind why PricingService shouldn't also send emails.
  • Dependency Inversion Principle (the "D" in SOLID) — why CheckoutController should depend on an interface, not a concrete implementation.
  • Domain-Driven Design's bounded contexts — a more formal version of "draw a boundary before code makes one by accident."
  • The "God Object" anti-pattern — what happens when nobody ever draws the boundary at all, and one class ends up owning everything.

Key Takeaways

  • "Just start coding" isn't wrong — it's correct at small scale, where there's nothing to get tangled yet.
  • The real danger point isn't a fixed file count, it's the crossover where possible connections between files exceed what a person can hold in their head — which grows roughly with the square of file count, not linearly.
  • Architecture is the set of decisions that are expensive to undo later. Made on purpose, they're an investment. Made by accident, they're a bill paid every sprint.
  • The cost of bad structure isn't the change itself — it's everything that quietly depended on the thing you just moved.

📇 Flashcards

Architecture vs. design vs. implementation — what's the difference?

Architecture = structural decisions costly to reverse; design = module-level choices; implementation = code. Architecture constrains everything below it.

Why does 'just start coding' work at first but break later?

Small apps have few structural decisions to get wrong; past a certain size, undecided structure gets decided implicitly by whoever wrote code last.

What are the 'three altitudes' of software decisions?

System-level structure, module/component design, and line-by-line implementation — each needs different judgment and changes at different costs.

What does a bad architectural wall actually cost?

Not a rewrite — ongoing tax: every feature crossing the wrong boundary needs workarounds, slowing all future work.

Same feature, two codebases — what's the point of that example?

Identical functionality can be trivial or painful to add depending on prior structural decisions, showing architecture's compounding effect.

Why is architectural cost 'not linear'?

Costs of poor structure grow disproportionately with scale/time — small early misalignments cause outsized pain later, unlike steady linear growth.
