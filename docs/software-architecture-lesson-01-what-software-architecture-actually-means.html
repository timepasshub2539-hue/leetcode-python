Software-Architecture Lesson 1: Software Architecture Lesson 1: The Codebase That Got Slow For No Re

General

Why This Problem Matters

Every engineer eventually hits the same wall: a codebase that used to be pleasant to work in becomes something you dread opening. You add one small feature and three unrelated things break. Nobody wrote worse code last month than they did six months ago — so why does it feel like the ground is shifting under you?

This is one of the most common (and most poorly explained) topics in software engineering, and it shows up constantly in system design interviews, in code review conversations, and in the day-to-day frustration of working on a growing product. Interviewers test it because it separates people who can write a function from people who can be trusted with a system. Understanding it early saves you years of cleaning up messes you didn't know you were creating.

This lesson is about building the mental model before touching a single design pattern. Patterns are just tools. Without the model, you'll misuse them.

Problem Overview

Here's the situation in plain terms: a team builds a product. At first, everything moves fast. Then, at some point — not suddenly, but gradually — every change starts costing more than it should. A one-line fix in billing somehow breaks the login page. A schema change in the database ripples into the UI. Nobody did anything obviously wrong, yet the codebase behaves like a house of cards.

The instinct is to blame code quality. Messier functions, sloppier naming, not enough tests. Sometimes that's true. But very often, the actual cause is something structural: too many parts of the system know too much about each other. Nobody decided, on purpose, which parts of the code are allowed to depend on which other parts. So, by default, everything ends up depending on everything.

That's not a implementation problem. It's an architecture problem, and the two are commonly confused.

Example

Imagine a small app with three areas: auth, billing, and ui.

  • auth/login.py handles logging a user in.
  • billing/stripe_client.py wraps calls to Stripe.
  • ui/dashboard.py renders what the user sees.

Someone working on login needs to charge a card during signup. They open billing/stripe_client.py, see a StripeClient class already sitting there, and import it directly into auth/login.py.

It works immediately. It's one line. Nobody stops to ask whether auth should know about Stripe at all.

Six months later, ten other files have done the exact same thing — importing StripeClient directly instead of going through a single billing.charge_user() function. Now the payment provider changes, or Stripe updates its SDK, and instead of editing one function, you're grepping the entire codebase for every place that touched Stripe directly. That's the tangle, made concrete.

Intuition

An experienced engineer doesn't start by asking "how do I write this function." They start by asking "who should be allowed to know about whom."

Think about it physically. In a well-run organization, not everyone can walk into the finance department and change numbers directly — there's a process, a form, a designated person. That's not bureaucracy for its own sake; it's what keeps finance stable while everything else around it changes. Software needs the same thing.

The insight is this: at small scale, relationships between parts of a system don't matter, because there's basically only one relationship — you and the whole file. At 200 lines of code, one person holds the entire thing in their head. There's nothing to "manage" because there's no complexity in the connections yet.

At 200,000 lines, nobody holds the whole thing in their head. What matters now isn't any single function — it's how the pieces talk to each other. A codebase with excellent individual functions but no rules about who can call whom will still collapse under its own weight, because the failure mode isn't inside any one piece. It's in the space between pieces.

This is the core distinction the lesson makes:

  • Implementation — the actual code inside one function or file.
  • Design — how one module is structured internally.
  • Architecture — how modules relate to each other across the whole system.

"Just start coding" optimizes implementation. Each function looks fine in isolation. But nobody decided the relationships, so relationships form anyway — just badly, driven by whatever's convenient in the moment rather than what's sustainable.

Brute Force Solution ("Just Start Coding")

Idea: Write the code that solves the immediate problem. Import whatever you need, wherever it lives. Ship the feature.

Algorithm: 1. Identify the feature needed. 2. Find the existing code that does something close to what you need. 3. Import it directly, wherever it is. 4. Ship.

Advantages: - Extremely fast in the short term. - Zero upfront planning cost. - Works fine when the codebase is small and one person understands all of it.

Disadvantages: - Every shortcut becomes a permanent, invisible dependency. - Dependencies compound — each new one makes future changes more likely to break something unrelated. - No one can predict blast radius. A "small" change might touch three systems no one thought were connected.

Time and space complexity (conceptually): Cost to add a feature ships flat early on — effectively O(1) per feature. But because nothing bounds how many modules directly depend on each other, the number of undecided relationships grows closer to O(n²) as modules increase, where each new module can potentially tangle with every existing one. Space complexity, in terms of "hidden coupling debt," grows the same way — it's not stored anywhere explicit, but it exists in every uncontrolled import.

Optimal Solution: Deciding Relationships on Purpose

The fix isn't "write better code." It's deciding, ahead of time, who is allowed to depend on whom — and enforcing that decision with a real boundary, not a convention people are supposed to remember.

A boundary means: modules on one side of the line can only interact with modules on the other side through a defined contract — a function signature, an interface, an API — never by reaching in directly.

Using the earlier example: instead of every module importing StripeClient directly, only billing is allowed to know Stripe exists. Everyone else calls billing.charge_user(user, amount). That one function is the entire contract. The database, the algorithm within billing, even the payment provider itself can change shape completely, and nothing outside billing notices — because the only thing crossing the boundary is the contract, not the implementation details behind it.

Without a boundary With a boundary
10 files import StripeClient directly 1 file (billing) owns Stripe
Provider change = grep the whole repo Provider change = edit one function
Any module can silently depend on any other Dependencies are explicit and limited
Blast radius of a change is unpredictable Blast radius is contained to the module

This is what "boundaries" actually buy you: predictability. A change inside a bounded module stays inside that module, as long as its outward-facing contract doesn't change.

But boundaries aren't free. Drawing one costs time and adds a layer of indirection. On a small project, that cost can be pure overkill — you're protecting a relationship that was never actually going to hurt you. And a boundary drawn in the wrong place creates its own kind of tangle: now you have ceremony around a relationship that didn't need protecting, while the real dangerous coupling sits somewhere else, unprotected. The actual skill isn't "always add boundaries." It's judging which relationships are worth protecting and which aren't.

Python Code

Here's the login/billing example, first without a boundary, then with one.

Without a boundary (the trap):

# auth/login.py
from billing.stripe_client import StripeClient

def signup_and_charge(user, card_token, amount):
    client = StripeClient()
    client.charge(card_token, amount)
    create_user(user)

With a boundary (a single contract):

# billing/__init__.py
from billing.stripe_client import StripeClient

def charge_user(user, card_token, amount):
    """The only entry point into billing. Nothing outside this
    module talks to Stripe directly."""
    client = StripeClient()
    return client.charge(card_token, amount)

# auth/login.py
import billing

def signup_and_charge(user, card_token, amount):
    billing.charge_user(user, card_token, amount)
    create_user(user)

Code Walkthrough

  • billing/stripe_client.py stays exactly as it was — it's an implementation detail now, not a public entry point.
  • billing/__init__.py exposes exactly one function, charge_user. This is the contract. It's the only thing other modules are allowed to call.
  • auth/login.py imports billing, not billing.stripe_client. It doesn't know or care that Stripe exists underneath.
  • If you switch payment providers tomorrow, you rewrite the inside of charge_user. auth/login.py doesn't change at all.

Dry Run

Say Stripe changes its charge API from client.charge(token, amount) to client.create_payment(amount, token).

Without the boundary: you search the codebase for every file importing StripeClient, find ten of them, and update each call site — hoping you don't miss one.

With the boundary: you open billing/__init__.py, update the single call inside charge_user, and you're done. auth/login.py, and everything else that calls billing.charge_user(), never has to change.

Complexity Analysis

Thinking of "cost to change the payment provider" as the operation being measured:

  • Without a boundary: O(k), where k is the number of files that directly imported the dependency — and k grows unpredictably over time since nothing stops new callers from importing it directly.
  • With a boundary: O(1) — exactly one function to update, regardless of how many modules use billing.charge_user().

This is correct because the boundary converts an unbounded, discoverable-only-by-searching set of dependents into a fixed, known interface. The cost doesn't scale with the number of callers anymore — it scales with the number of underlying implementations, which is one.

Alternative Solutions

A reasonable alternative to a hard module boundary is a documented convention — a style guide that says "always go through billing.charge_user()," enforced by code review rather than by code structure.

This is cheaper to set up, but it's weaker: it depends on every reviewer catching every violation, forever. A real boundary (enforced via module structure, import linting, or language-level access control) fails loudly — a direct import either doesn't exist or gets flagged by tooling. A convention fails silently — someone just imports what's convenient, exactly like in the original example, and nobody notices until the tangle is already there.

Edge Cases

  • Tiny codebase (a few hundred lines): boundaries are overhead you don't need yet. One person holds it all in their head — skip it.
  • A module with exactly one caller: a boundary here is pure ceremony. Wait until a second caller shows up before deciding it's worth protecting.
  • A boundary drawn around the wrong thing: e.g., protecting auth from ui when the real risk is billing and database. This produces indirection without the corresponding safety.
  • Rapid prototyping / spike code: enforcing boundaries mid-exploration slows down the exact phase where speed matters most. Add them once the shape of the system stabilizes.
  • A "boundary" that's just a shared folder with no enforced contract: this looks like architecture but isn't — nothing stops someone from reaching past it, so it provides none of the actual protection.

Common Mistakes

  1. Treating architecture as a synonym for "good code." Architecture is about relationships between modules, not the quality of any one module.
  2. Adding boundaries everywhere, all at once. Over-bounding a small system adds friction without adding safety.
  3. Drawing the boundary in the wrong place — protecting a relationship that was never actually risky while leaving the truly coupled parts exposed.
  4. Confusing "it's one line" with "it's safe." The StripeClient import is exactly one line — and exactly how the tangle starts.
  5. Assuming a folder structure is a boundary. Grouping files by name doesn't stop imports from crossing freely; only an enforced contract does.
  6. Waiting until the codebase is already tangled to think about this. Boundaries are far cheaper to establish before the code exists than to retrofit afterward.

Interview Questions

  • What's the difference between software architecture, design, and implementation?
  • How would you decide whether a module boundary is worth adding?
  • Describe a time coupling between modules caused a production issue. How would you prevent it?
  • How do you design a system so that a database migration doesn't require UI changes?
  • What's the tradeoff between a monolith with clear internal boundaries versus splitting into services?

Similar Problems

While this lesson isn't a LeetCode-style algorithm problem, the underlying skill — reasoning about dependency graphs and cycles — connects directly to:

  • Course Schedule (LeetCode 207/210): detecting cycles in a dependency graph, conceptually identical to detecting circular module dependencies in a codebase.
  • Clone Graph (LeetCode 133): reasoning about how nodes (modules) relate to each other, not just their internal structure.
  • Topological Sort problems generally: any problem about ordering things based on dependency constraints mirrors deciding which modules can depend on which.

Key Takeaways

  • Architecture, design, and implementation are three different concerns operating at three different scales — conflating them leads to solving the wrong problem.
  • "Just start coding" works fine at small scale because relationships between parts don't yet exist in any meaningful number.
  • Left undecided, dependencies form anyway — driven by convenience, not intention — and that's what creates the tangle.
  • A real boundary replaces "everyone can reach in" with "only a defined contract crosses this line."
  • Boundaries have a real cost. The skill is judging which relationships are worth protecting, not protecting everything.

📇 Flashcards

What actually changes as a codebase grows, if not the code quality itself?

The number of places a change ripples to — coordination cost, not typing speed, becomes the bottleneck.

Architecture vs design vs implementation — what's the key distinction?

Architecture = boundaries/structure decisions; design = how a module solves its problem; implementation = the actual code.

Why does 'just start coding' break down past a certain size?

It optimizes for speed of the first feature, not for isolating change — so every new feature touches more of the system.

What's the concrete symptom of 'everything talks to everything'?

A small change in one file forces edits in many unrelated files because no module owns its own boundary.

What is architecture, in one sentence?

The set of boundaries that decide what can change independently and what can't.

Boundaries aren't free — what's the tradeoff?

Upfront cost: more interfaces, indirection, and planning, paid back later as isolated, cheaper changes.
