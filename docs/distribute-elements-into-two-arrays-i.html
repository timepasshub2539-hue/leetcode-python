3069. Distribute Elements Into Two Arrays I | LeetCode Daily Python Solution (why sorting is a trap)

General ✓ Runtime tested

Introduction

Every so often you hit a LeetCode problem that looks like it belongs to a category it doesn't actually belong to. LeetCode 3069, Distribute Elements Into Two Arrays I, is one of those. The name alone — "distribute elements into two arrays" — nudges you toward sorting, bucketing, or some kind of partition-by-value logic. None of that is needed.

This problem is a favorite in interviews not because it's hard, but because it tests something more valuable than algorithm memorization: can you resist over-engineering a solution the moment a problem smells like a classic? Interviewers use problems like this to see whether you simulate the process described, or whether you reach for a hammer (sorting, extra data structures) out of habit. Getting comfortable with "just simulate it" as a first instinct will serve you in a lot more interviews than this one.

Problem Overview

You're given an array of distinct integers, 1-indexed conceptually, though we'll work with it as a normal 0-indexed Python list. You're going to build two new arrays, arr1 and arr2, by placing each number from the input one at a time:

  • The first number always goes into arr1.
  • The second number always goes into arr2.
  • For every number after that, you compare the last element currently in arr1 against the last element currently in arr2. The number gets appended to whichever array has the larger last element.

Once every number has been placed, the answer is arr1 followed by arr2, concatenated in that order.

That's the entire problem. No sorting, no removing elements, no re-evaluating past decisions.

Example

Let's use nums = [2, 1, 3].

  • 2 is the first number → goes to arr1. arr1 = [2]
  • 1 is the second number → goes to arr2. arr2 = [1]
  • 3 is next. Last of arr1 is 2, last of arr2 is 1. 2 > 1, so 3 joins arr1. arr1 = [2, 3]

Final result: arr1 + arr2 = [2, 3, 1].

A second example: nums = [5, 2, 8].

  • 5 → arr1 = [5]
  • 2 → arr2 = [2]
  • 8: compare 5 vs 2. 5 wins, so 8 joins arr1. arr1 = [5, 8]

Result: [5, 8, 2].

Notice in both cases we only ever looked at the last element of each array, never the whole array.

Intuition

The instinct to reach for sorting comes from the word "distribute" — a lot of distribution problems (bucket sort, counting sort, interval partitioning) genuinely do need ordering information about the whole collection. The way to catch yourself here is to ask: does the placement rule depend on more than the two most recent items?

Read the rule again: append to whichever array has the larger last element. That's it. It doesn't ask "where would this number rank if the array were sorted." It doesn't ask "how many elements are smaller than this one." It only asks about two specific numbers — the current tails of two lists. That's a signal you're looking at a simulation problem, not a sorting or ranking problem.

Think of it as dealing cards onto two piles: you only ever look at the top card of each pile, never rifle through the whole stack. Each decision is local, and once a card is placed it never moves again — there's no backtracking, no re-sorting, no fixing an earlier choice once a later number arrives. That property (a decision is final the moment it's made) is exactly what makes a single left-to-right pass sufficient.

The distinctness constraint matters more than it looks. Because every value in the input is unique, when you compare arr1[-1] and arr2[-1], you can never get a tie. The rule always has an unambiguous winner. If duplicates were allowed, you'd need a tie-breaking rule, and the problem would need more logic — but that's not this problem.

It's worth knowing this problem has a harder sibling, LeetCode 3072, where the placement rule is based on how many elements are less than or equal to the current number, not just the last element. That version genuinely needs a Fenwick tree (binary indexed tree) to count efficiently, because the decision depends on information about the whole array so far, not just two numbers. The fact that 3069 doesn't need that machinery is precisely because its rule is narrower — a good example of how one extra clause in a problem statement can jump the required data structure up several levels of complexity.

Brute Force Solution

There isn't really a meaningfully "slower" brute force here, because the rule is already telling you the minimal amount of information to track — the last element of each array. But if you wanted to describe a naive-but-correct implementation before optimizing anything, it would look like:

Idea: Maintain arr1 and arr2 as plain Python lists. For each new number, look up arr1[-1] and arr2[-1] directly, compare, and append.

Algorithm: 1. Seed arr1 with nums[0], arr2 with nums[1]. 2. For each remaining number, compare arr1[-1] and arr2[-1]. 3. Append to the larger one. 4. Return arr1 + arr2.

Advantages: Simple, direct translation of the problem statement, no extra data structures.

Disadvantages: None, really — this is the optimal solution. There's no slower "obvious" approach worth contrasting it against, unlike problems where brute force means checking all pairs or all subsets.

Time complexity: O(n) — one pass, one comparison and one append per element. Space complexity: O(n) — for the two output arrays.

Optimal Solution

Since the brute force is the optimal solution, let's walk through exactly why each part of it is necessary and sufficient.

Step What happens Why it's enough
Seed arr1 nums[0] → arr1 Problem statement fixes this, no comparison needed
Seed arr2 nums[1] → arr2 Same — fixed by the rules
Loop from index 2 Compare arr1[-1] vs arr2[-1] These are the only two numbers relevant to the decision
Append Larger tail's array gets the new number Distinct values guarantee no tie
Combine arr1 + arr2 Final answer, order preserved within each array

The key insight to hold onto: arr1[-1] and arr2[-1] are the only state you need to carry between iterations. You don't need the full array, a sorted copy, or any auxiliary structure. That's what keeps this at O(1) work per element instead of O(log n) or O(n) per element.

Python Code

from typing import List


class Solution:
    def resultArray(self, nums: List[int]) -> List[int]:
        # First two numbers are placed by fixed rule, not comparison
        arr1 = [nums[0]]
        arr2 = [nums[1]]

        for num in nums[2:]:
            if arr1[-1] > arr2[-1]:
                arr1.append(num)
            else:
                arr2.append(num)

        return arr1 + arr2

Code Walkthrough

  • arr1 = [nums[0]] and arr2 = [nums[1]]: the two forced moves the problem hands you directly — no logic required.
  • for num in nums[2:]: iterate over everything after the first two elements, since those are already placed.
  • if arr1[-1] > arr2[-1]: [-1] grabs the last element of each list in O(1), which is exactly the "top of the pile" comparison the problem describes.
  • arr1.append(num) / arr2.append(num): append is O(1) amortized in Python, so each iteration does constant work.
  • return arr1 + arr2: concatenates the two lists in order, preserving the sequence each array built up internally.

Dry Run

Using nums = [2, 1, 3, 5, 4]:

Step num arr1 last arr2 last Decision arr1 arr2
seed — — — — [2] [1]
1 3 2 1 2 > 1 → arr1 [2, 3] [1]
2 5 3 1 3 > 1 → arr1 [2, 3, 5] [1]
3 4 5 1 5 > 1 → arr1 [2, 3, 5, 4] [1]

Final result: [2, 3, 5, 4, 1].

Complexity Analysis

Time: O(n). Each of the n numbers is visited exactly once. Every visit does a constant amount of work: two comparisons (or fewer) and one append. There's no nested loop, no re-scanning, and no sorting step.

Space: O(n). arr1 and arr2 together hold every element from the input exactly once, so their combined size is n. No auxiliary structures beyond the two output arrays are needed.

Both bounds are tight — you must at minimum read every input element once and write every output element once, so O(n) is also the best possible complexity for this problem.

Alternative Solutions

You could implement this with collections.deque instead of a list if you only ever needed to peek at the last element and append — but Python lists already give O(1) amortized append and O(1) indexing with [-1], so a deque buys nothing here and adds import overhead for no benefit.

You could also track just the two "last values" as integers (last1, last2) instead of indexing into the lists each time, saving a tiny constant factor:

def resultArray(self, nums: List[int]) -> List[int]:
    arr1, arr2 = [nums[0]], [nums[1]]
    last1, last2 = nums[0], nums[1]

    for num in nums[2:]:
        if last1 > last2:
            arr1.append(num)
            last1 = num
        else:
            arr2.append(num)
            last2 = num

    return arr1 + arr2

This is functionally identical — same time and space complexity — but avoids repeated [-1] indexing. It's a micro-optimization, not a different algorithm, and for n in LeetCode's constraint range the difference is unmeasurable. Both are worth knowing: one reads slightly cleaner, the other shows you understand what state actually matters.

Edge Cases

  • Minimum-length input: the problem guarantees at least 2 elements (since the first two are placed unconditionally), so there's no need to guard against an empty array or single-element array.
  • Strictly increasing input (e.g. [1, 2, 3, 4]): after seeding, every subsequent number is compared against a growing arr1 tail, so watch that your logic doesn't assume arr2 ever catches up — it may end up nearly empty.
  • Strictly decreasing input (e.g. [4, 3, 2, 1]): here arr2's seed value dominates early comparisons, exercising the opposite branch repeatedly.
  • Large values / negative values: Python integers handle arbitrary magnitude and sign natively, so no overflow considerations apply, unlike in fixed-width-integer languages.
  • All comparisons landing on the same array: perfectly valid — nothing in the algorithm requires the two arrays to end up balanced in size.

Common Mistakes

  1. Comparing entire arrays instead of just the last elements — for example, using max(arr1) > max(arr2) or checking against arr1[0]. This breaks the O(n) guarantee and produces wrong placements, since only the most recent addition matters.
  2. Forgetting the fixed seeding rule — trying to run the comparison logic starting from index 0 instead of manually placing nums[0] and nums[1] first.
  3. Off-by-one errors in the loop range — iterating from nums[1:] instead of nums[2:], which re-processes the second element and corrupts the result.
  4. Assuming a tie is possible and adding tie-breaking logic — unnecessary complexity, since the distinct-integers constraint guarantees the comparison is never equal.
  5. Concatenating in the wrong order — returning arr2 + arr1 instead of arr1 + arr2, which silently produces an incorrect answer that still "looks like" a valid array.
  6. Using .pop(0) or list slicing inside the loop — some solvers instinctively remove processed elements from nums, which is unnecessary and turns an O(n) solution into O(n²) due to the cost of shifting list elements.

Interview Questions

  • How would this change if the input allowed duplicate values? (You'd need an explicit tie-breaking rule, since the "always a winner" guarantee disappears.)
  • Can you solve this in-place, using only the original array and no extra output arrays? (Discuss trade-offs — you'd need index markers to track boundaries within nums, adding complexity for a marginal space saving.)
  • What's the difference between this problem and LeetCode 3072, and why does that one need a Fenwick tree while this one doesn't?
  • How would you modify this to distribute into three arrays under a similar "compare the last elements" rule?
  • Can this be done with O(1) extra space beyond the output? (Explore whether you can build the result into a single array with pointers rather than two separate lists.)

Key Takeaways

The core lesson of LeetCode 3069 isn't the code — it's the diagnostic skill of reading a placement rule carefully enough to see that it only depends on two numbers, not the whole array. When a rule is genuinely local, a single pass beats any sorting-based approach on both time and code complexity. Keep asking "what's the minimum state this rule actually needs?" before reaching for a bigger tool, and you'll avoid over-solving problems like this one in interviews.

📇 Flashcards

Two-array partition without sorting — what's the trigger?

When each element only needs comparison against the last placed value in two running arrays, skip sort — use a single left-to-right scan with a greedy rule.

Time complexity of the greedy two-array distribution?

O(n) — one pass through the input, each element placed once via constant-time comparisons.

Space complexity of the two-array distribution approach?

O(n) — the two output arrays together hold all n elements; no extra structures needed.

Trickiest bug when comparing to 'last element' of each array?

Forgetting to update the tracked last-value after every append — stale comparisons silently misroute later elements.

Why does the problem require distinct integers?

Distinctness guarantees no tie between the two last-elements, so the greater-than rule always has one unambiguous winner.

Why is this NOT a sorting problem despite 'distribute' framing?

The rule only ever looks backward at the last placed element, never reorders past picks — a streaming decision, not a full ordering.
