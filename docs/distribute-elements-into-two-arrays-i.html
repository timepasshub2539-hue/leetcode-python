3069. Distribute Elements Into Two Arrays I | LeetCode Daily Python Solution (why sorting is a trap)

General

Introduction

LeetCode 3069, Distribute Elements Into Two Arrays I, is one of those problems that looks harmless on the surface and then quietly punishes the first instinct almost everyone has: sort it. It's tagged Easy, it involves nothing more exotic than comparing two numbers, and the constraints are tiny. None of that means it's a throwaway problem.

What makes it worth your time is the trap. Interviewers love handing candidates a problem where the "obviously correct" first move destroys the exact information the problem depends on. This one does that in a single line of reasoning, and if you fall for it, you'll write code that produces plausible-looking output that is completely wrong. Catching that trap — and explaining why it's a trap, out loud, in an interview — is worth more than knowing the final algorithm.

The actual lesson here generalizes well beyond this one problem: a lot of "process this array" problems don't need the whole array in memory. They only need the last value you placed. Once you see that pattern, you stop reaching for sorted() out of habit and start asking what state the rule actually depends on.

Problem Overview

You're given an array of n distinct integers, where n is between 3 and 50, and every value is between 1 and 100. You need to split every number in the array into one of two new arrays, arr1 and arr2, following a strict, order-dependent rule:

  • The first number in the input always goes to arr1.
  • The second number in the input always goes to arr2.
  • For every number after that, look at the last element currently in arr1 and the last element currently in arr2. Whichever one is larger, that's the array the new number gets appended to.

Because every value in the input is guaranteed distinct, those two "last elements" you're comparing are never equal to each other — so the rule never needs a tiebreaker.

Once every number has been placed, the answer is arr1 followed by arr2, concatenated into a single array.

Example

Input: nums = [5, 4, 3, 8]

Output: [5, 3, 4, 8]

Walking through it:

  1. 5 is the first element → goes to arr1. arr1 = [5]
  2. 4 is the second element → goes to arr2. arr2 = [4]
  3. 3: compare last of arr1 (5) to last of arr2 (4). 5 is bigger, so 3 joins arr1. arr1 = [5, 3]
  4. 8: compare last of arr1 (3) to last of arr2 (4). 4 is bigger, so 8 joins arr2. arr2 = [4, 8]

Concatenate: arr1 + arr2 = [5, 3, 4, 8].

Second example: nums = [2, 1, 3]

  1. 2 → arr1 = [2]
  2. 1 → arr2 = [1]
  3. 3: last of arr1 is 2, last of arr2 is 1. 2 is bigger, so 3 joins arr1. arr1 = [2, 3]

Result: [2, 3, 1].

Intuition

Here's the guess almost everyone makes on first read: "if the number is less than or equal to the current max of arr1, and arr1 isn't already too big, put it there — otherwise arr2." That reads like a sorting rule dressed up in different words, and it feels safe because sorting is the tool most people reach for whenever a problem mentions comparing numbers.

It's wrong, and tracing a small example by hand is the fastest way to see why. Take [2, 1, 3]. Sort it and you get [1, 2, 3] — but the problem never asks you to sort anything. It asks you to look at the order the numbers arrived in and which array each one landed in along the way. Those two things are exactly what sorting throws away.

The real rule only cares about one fact at each step: the last value already sitting in arr1, and the last value already sitting in arr2. Once you notice that, a second realization follows immediately — you never need to store the entire arr1 or arr2 to make the next decision. You only need their last elements. That's the difference between an algorithm that feels like it needs sorting and log-n cleverness, and one that's a single pass with two variables.

Brute Force Solution

Idea: Simulate the process literally. Keep two Python lists, arr1 and arr2. For each new number, look at arr1[-1] and arr2[-1], compare them, and append.

Algorithm: 1. Initialize arr1 = [nums[0]], arr2 = [nums[1]]. 2. For each remaining number, compare arr1[-1] and arr2[-1] and append to the larger side. 3. Return arr1 + arr2.

This is essentially the optimal solution already — the problem doesn't leave much room for a genuinely worse brute force, because the naive simulation and the efficient simulation are the same algorithm. The only place people usually go wrong is trying to be "smarter" by sorting first or by re-scanning the arrays to find a max, instead of trusting that the last element is all that matters.

Advantages: Simple, directly mirrors the problem statement, easy to verify by hand. Disadvantages: None significant at this input size — but if you rescan a whole array to find its max on every step instead of tracking the last element, you'd degrade this from O(n) to O(n²) for no reason.

Time complexity: O(n) if you track last elements correctly, O(n²) if you re-scan. Space complexity: O(n) for the two output arrays.

Optimal Solution

Since only the last element of each array ever matters, you don't need arr1[-1] and arr2[-1] — you can track two scalar variables that always hold the most recent value appended to each side, alongside the two growing lists (which you need anyway, since the final answer is those two lists).

Step Number last(arr1) last(arr2) Goes to
1 5 — — arr1 (rule)
2 4 5 — arr2 (rule)
3 3 5 4 arr1 (5 > 4)
4 8 3 4 arr2 (4 > 3)

The loop is deliberately boring: one comparison, one append, repeat. No sorting, no nested loops, no auxiliary data structures beyond the two output arrays themselves.

Python Code

from typing import List


def resultArray(nums: List[int]) -> List[int]:
    """Split nums into two arrays following the last-element comparison rule."""
    arr1 = [nums[0]]
    arr2 = [nums[1]]

    for num in nums[2:]:
        if arr1[-1] > arr2[-1]:
            arr1.append(num)
        else:
            arr2.append(num)

    return arr1 + arr2

Code Walkthrough

  • arr1 = [nums[0]] and arr2 = [nums[1]] handle the two fixed starting rules directly — no comparison needed for the first two elements, so don't write a conditional for them.
  • for num in nums[2:] iterates over every remaining number exactly once, starting from index 2.
  • arr1[-1] > arr2[-1] reads the current last element of each list. Since all values are distinct, this comparison is never a tie.
  • The if/else appends num to whichever array currently holds the larger last value — that's the entire rule, applied once per number.
  • return arr1 + arr2 concatenates the two lists in the order the problem requires: arr1 first, then arr2.

Dry Run

nums = [5, 4, 3, 8]

  • arr1 = [5], arr2 = [4]
  • num = 3: arr1[-1] = 5, arr2[-1] = 4. 5 > 4 → append to arr1. arr1 = [5, 3]
  • num = 8: arr1[-1] = 3, arr2[-1] = 4. 3 > 4 is False → append to arr2. arr2 = [4, 8]
  • Return [5, 3] + [4, 8] = [5, 3, 4, 8] ✔

Complexity Analysis

Time: O(n). Every number in nums is visited exactly once, and each visit does a constant-time comparison and append.

Space: O(n) to hold arr1 and arr2, which together contain every element of the input exactly once. If you don't count the output as extra space (a common convention for problems where the output is the transformed input), the auxiliary space is O(1) beyond the two last-element values.

Alternative Solutions

You could track last1 and last2 as separate integer variables instead of reading arr1[-1] / arr2[-1] each time. It saves a couple of list-index lookups but doesn't change the asymptotic complexity — for n ≤ 50, it's not worth the extra variables. Sorting-based approaches don't apply here at all, since sorting discards the arrival order the rule depends on; that's not a slower alternative, it's an incorrect one.

Edge Cases

  • Minimum length (n = 3): Only one comparison happens after the two seed elements — make sure your loop still runs correctly when there's just one number left to place.
  • Strictly increasing input (e.g., [1, 2, 3, 4]): the "which side is bigger" comparison flips in a predictable pattern — good for verifying your trace by hand.
  • Strictly decreasing input (e.g., [4, 3, 2, 1]): stresses the opposite pattern.
  • Values at the boundaries (1 and 100): confirm your comparison logic doesn't assume any particular range.
  • All comparisons resolving to the same array repeatedly: since values are distinct, this can happen if one array's last element stays consistently larger — make sure you're not accidentally capping how many elements one array can hold.

Common Mistakes

  1. Sorting the array first. This destroys the order information the rule depends on and produces a completely different — and wrong — result.
  2. Comparing the max of each array instead of the last element. The rule is specifically about the last placed value, not the largest value ever placed.
  3. Forgetting the fixed seed rule for the first two elements and running them through the general comparison loop instead.
  4. Re-scanning the whole array to find the "current max" on every iteration, turning an O(n) solution into O(n²) for no benefit.
  5. Assuming ties are possible and writing tie-breaking logic — the distinct-values constraint guarantees the comparison never ties, so that code path never executes but adds unnecessary complexity if included.

Key Takeaways

The rule in this problem depends only on the last element of each array, not the whole array, not the max, and definitely not the sorted order. Recognizing what state a rule actually depends on — before writing any code — is what separates a fast, correct O(n) pass from a slower or outright incorrect solution. When you see "process elements one at a time based on what came before," check whether you need the entire history or just the most recent piece of it.

Pattern tell: threshold/frequency split without needing order?

Frequency-driven partitioning, not sorting — when the rule depends on 'seen before' or a running count, think hash-set/counter tracking, not sort.

Time complexity for this distribute-by-appearance-count problem?

O(n), one linear pass with O(1) hash-set lookups per element.

Space complexity for this problem?

O(n) for the two output arrays plus O(n) for the tracking hash sets.

Trickiest edge case when tracing 2, 1, 3?

The very first two elements are fixed by rule (arr1 gets first, arr2 gets second) before the greater-count logic even applies — forgetting this seeds the wrong array.

Why does sorting the input not help here?

The split depends on each element's relative position and prior appearances in the *original* order, which sorting destroys.

Interview follow-up: what if the rule compared counts of elements less-than instead of greater-than?

Same O(n) approach still works — just flip the comparison when deciding which array gets the next element.
