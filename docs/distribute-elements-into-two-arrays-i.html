3069. Distribute Elements Into Two Arrays I | LeetCode Daily Python Solution (why sorting is a trap)

General ✓ Runtime tested

Introduction

Some LeetCode problems test whether you know an algorithm. Others test whether you can resist the urge to reach for one. LeetCode 3069, "Distribute Elements Into Two Arrays I," belongs firmly in the second category.

At first glance, splitting numbers between two arrays smells like a sorting problem — maybe even a classic partition problem where you separate small values from large ones. It isn't. The moment you sort the input, you throw away the exact information the problem depends on: the order elements arrived in and where they landed.

Interviewers love problems like this because they reveal something sorting-happy candidates miss — the ability to read a rule literally instead of pattern-matching it to a familiar algorithm you've memorized. This one also rewards a habit worth building for any array simulation problem: noticing that you often only need the last value of a growing structure, not the whole structure itself. That single observation turns an O(n) space, multi-list simulation into a clean, two-variable, one-pass solution.

Problem Overview

You're given an array of n distinct integers, indexed from 0. You'll distribute every element into one of two arrays — call them arr1 and arr2 — following these steps:

  1. The first element (nums[0]) always goes into arr1.
  2. The second element (nums[1]) always goes into arr2.
  3. For every element after that, compare it to the last element currently in arr1 and the last element currently in arr2: - If the last element of arr1 is greater, the new element goes into arr1. - Otherwise, it goes into arr2.

Since all values in nums are distinct, the two last elements you're comparing are never equal — there's no tie-breaking to worry about.

At the end, concatenate arr1 followed by arr2 and return the result.

The constraints are small and forgiving: 3 to 50 elements, values from 1 to 100, all distinct. This isn't a problem that needs a clever data structure — it needs a clean read of the rule.

Example

Take nums = [2, 1, 3].

  • 2 is the first element → goes to arr1. arr1 = [2]
  • 1 is the second element → goes to arr2. arr2 = [1]
  • 3 is next. Compare arr1's last element (2) to arr2's last element (1). 2 > 1, so 3 joins arr1. arr1 = [2, 3]

Final result: arr1 + arr2 = [2, 3, 1].

A second example makes the loop clearer: nums = [5, 4, 3, 8].

  • 5 → arr1 = [5]
  • 4 → arr2 = [4]
  • 3: last of arr1 is 5, last of arr2 is 4. 5 > 4, so 3 joins arr1. arr1 = [5, 3]
  • 8: last of arr1 is now 3, last of arr2 is 4. 4 > 3, so 8 joins arr2. arr2 = [4, 8]

Result: [5, 3] + [4, 8] = [5, 3, 4, 8].

Intuition

The instinct that trips people up is pattern-matching. "Two arrays, splitting numbers, some size comparison" reads like the setup for a sorted-partition problem, so the reflex is to sort nums and slice it in half or interleave by parity. That reflex is wrong here, and it's worth understanding precisely why.

The rule isn't about the relative rank of a number within the whole array. It's about a running comparison against whatever happens to be sitting at the end of each array right now, based on the order elements were processed. Sort the array first, and you've permanently erased the sequence the rule depends on — there's no way to recover which value was "last placed" once the arrival order is gone.

Once you accept that this is a simulation problem, not a sorting problem, the next realization is what makes the solution fast: at any point in the process, you never need to look at anything in arr1 or arr2 except the most recently appended element. Nothing earlier in either array ever gets compared to anything again. That means you don't need to store the arrays — you can track two scalar variables, last1 and last2, and only materialize the full lists at the point where you actually need to return them (or track everything as lists from the start and just read [-1] when comparing).

This is a pattern worth internalizing beyond this one problem: whenever a rule only reaches back to "the most recent thing," a full history is dead weight. Keep just what the rule actually reads.

Brute Force Solution

There isn't really a slower "brute force" here in the traditional sense — the naive simulation is the optimal simulation, because the rule is already local (it only depends on the last elements). The only naive mistake is over-thinking it into a sort-based or nested-loop approach.

A genuinely worse version would be: after placing each element, re-scan the entirety of arr1 and arr2 to find their max, instead of noting the max is trivially the last element appended. That's unnecessary but illustrates the trap—the max of each array happens to always be its last element, since every new value added is compared to the current end and appended in a way that never later gets beaten by something requiring a re-scan for correctness. So there's no real O(n²) brute force worth writing — the "brute force" and "optimal" solutions are the same shape, and the only inefficiency to avoid is reaching for sorting or unnecessary re-scans.

  • Time: O(n) even in the "naive" version, since the rule is inherently local.
  • Space: O(n) to store the output arrays.

Optimal Solution

Walk through it step by step:

  1. Seed arr1 with nums[0] and arr2 with nums[1]. No comparison needed for these two — the rule hard-codes their placement.
  2. For every remaining element (from index 2 onward), compare the last element of arr1 to the last element of arr2.
  3. If arr1's last element is bigger, append the current number to arr1. Otherwise, append it to arr2.
  4. After the loop, return arr1 + arr2.
Step Element Last(arr1) Last(arr2) Goes to
1 5 — — arr1 (seed)
2 4 — — arr2 (seed)
3 3 5 4 arr1 (5 > 4)
4 8 3 4 arr2 (4 > 3)

No sorting, no nested loops, no auxiliary data structures — just a single pass with two arrays growing in lockstep.

Python Code

from typing import List


class Solution:
    def resultArray(self, nums: List[int]) -> List[int]:
        arr1 = [nums[0]]
        arr2 = [nums[1]]

        for num in nums[2:]:
            if arr1[-1] > arr2[-1]:
                arr1.append(num)
            else:
                arr2.append(num)

        return arr1 + arr2

Code Walkthrough

  • arr1 = [nums[0]] and arr2 = [nums[1]] handle the two hard-coded first placements from the rule directly — no comparison logic needed for them.
  • for num in nums[2:] iterates over every element from the third onward, which is exactly where the comparison rule kicks in.
  • arr1[-1] and arr2[-1] read the last element of each list in O(1), which is what makes this efficient — Python lists support constant-time access to the last element.
  • The if/else implements the rule exactly as specified: arr1 wins ties toward itself only in the sense that it's checked first, though the problem guarantees no actual ties occur since all values are distinct.
  • arr1 + arr2 concatenates the two lists into the final answer, matching the "arr1 followed by arr2" requirement.

Dry Run

nums = [2, 1, 3]

  • arr1 = [2], arr2 = [1]
  • Loop starts at nums[2:] = [3]
  • num = 3: arr1[-1] = 2, arr2[-1] = 1. 2 > 1 → append to arr1. arr1 = [2, 3]
  • Loop ends.
  • Return arr1 + arr2 = [2, 3] + [1] = [2, 3, 1]

Matches the expected output.

Complexity Analysis

  • Time: O(n). Every element is visited exactly once, and each comparison/append is O(1).
  • Space: O(n). The two output arrays together hold every input element exactly once; no extra structures scale with input size.

Both bounds are tight — you can't produce the output without touching every element at least once, and you can't avoid storing the output arrays since the problem asks you to return them.

Alternative Solutions

You could track last1 and last2 as plain integers instead of indexing into lists, and only build arr1/arr2 as you go — functionally identical, just marginally more explicit about what the algorithm actually reads. There's no asymptotic improvement available; O(n) time and O(n) space are both required minimums for this problem, since you must read every input and produce output containing every input.

Worth knowing: the harder follow-up, "Distribute Elements Into Two Arrays II," changes the rule from "which last element is bigger" to "which array has more elements greater than the current number." That's no longer a simple last-value comparison — it requires counting how many elements exceed a threshold efficiently, which typically means a Fenwick tree (binary indexed tree) or similar order-statistics structure to keep each query at O(log n) instead of a linear scan.

Edge Cases

  • Minimum size (n = 3): Only one comparison happens after seeding. Handled naturally by the loop running once.
  • All values already "sorted" in some direction: The rule doesn't care about global order, so an ascending or descending input still just follows the local last-element comparison — no special casing needed.
  • Values near the constraint boundaries (1 and 100): No effect on logic since comparisons are purely relative.
  • Empty input: Not possible per constraints (n >= 3), so no defensive check is needed.
  • Duplicate values: Explicitly excluded by the problem (nums are distinct), which is why the comparison never needs a tie-breaker.

Common Mistakes

  1. Sorting the array first. This destroys the arrival order the rule depends on and produces a completely different (wrong) result.
  2. Comparing against the max of the whole array instead of the last element. They coincide here, but reasoning about "max" instead of "last" can lead you astray on similar problems where they diverge.
  3. Forgetting the special-cased first two elements. Trying to run the comparison rule from index 0 will crash or misplace the first two numbers.
  4. Re-scanning entire arrays each iteration instead of just checking the last element. Wasteful and unnecessary — O(1) last-element access is sufficient.
  5. Assuming ties need handling. Because the problem guarantees distinct values, code that adds tie-breaking logic is solving a problem that doesn't exist here — and may misbehave on the truly-tied edge case that can't occur.

Key Takeaways

The core lesson isn't really about this specific problem — it's about resisting premature pattern-matching. A problem that looks like sorting, searching, or a familiar template deserves a literal read of its actual rule before you commit to an approach. Once you trust the rule instead of your instinct, the implementation often turns out to need far less machinery than you assumed: here, two variables and one pass instead of an entire sort.

Pattern tell: threshold/frequency split without needing order?

Frequency-driven partitioning, not sorting — when the rule depends on 'seen before' or a running count, think hash-set/counter tracking, not sort.

Time complexity for this distribute-by-appearance-count problem?

O(n), one linear pass with O(1) hash-set lookups per element.

Space complexity for this problem?

O(n) for the two output arrays plus O(n) for the tracking hash sets.

Trickiest edge case when tracing 2, 1, 3?

The very first two elements are fixed by rule (arr1 gets first, arr2 gets second) before the greater-count logic even applies — forgetting this seeds the wrong array.

Why does sorting the input not help here?

The split depends on each element's relative position and prior appearances in the *original* order, which sorting destroys.

Interview follow-up: what if the rule compared counts of elements less-than instead of greater-than?

Same O(n) approach still works — just flip the comparison when deciding which array gets the next element.
