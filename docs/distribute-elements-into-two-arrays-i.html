3069. Distribute Elements Into Two Arrays I | LeetCode Daily Python Solution (the last-element trap)

General ✓ Runtime tested

Introduction

Every so often LeetCode throws a problem that looks trivial on the surface and quietly tests something deeper: can you resist the obvious wrong pattern and instead build a rule from first principles? LeetCode 3069, Distribute Elements Into Two Arrays I, is exactly that kind of problem.

At a glance it looks like a simple "split the list" exercise. But the moment you try to shortcut it — say, by alternating elements between two arrays — you get the wrong answer. That's the real value of this problem for interview prep: it forces you to read the rule carefully, simulate it by hand before writing a single line of code, and only then translate it into Python. Interviewers love problems like this because they separate candidates who pattern-match from candidates who actually reason about the mechanics.

It's also a great entry point into a broader family of problems. LeetCode has a "Part II" version of this exact setup that swaps a simple comparison for a Fenwick tree, and understanding why Part I doesn't need that extra machinery tells you a lot about when simple greedy logic is enough — and when it isn't.

Problem Overview

You're given a list of n distinct integers, numbered nums[1] through nums[n] in the problem's one-indexed description. You need to distribute every number into one of two arrays, arr1 and arr2, following these rules:

  1. The first number in nums always goes to arr1.
  2. The second number in nums always goes to arr2.
  3. For every number after that (starting from the third), compare the last element currently in arr1 with the last element currently in arr2. If arr1's last element is greater, the new number is appended to arr1. Otherwise, it's appended to arr2.

Once every number has been placed, the result is arr1 concatenated with arr2, in that order.

The values are guaranteed to be distinct, which turns out to matter more than it looks — more on that in a moment.

Example

Let's trace nums = [2, 1, 3]:

  • 2 is first → goes to arr1. arr1 = [2]
  • 1 is second → goes to arr2. arr2 = [1]
  • 3 is third → compare last elements: arr1's last is 2, arr2's last is 1. Since 2 > 1, 3 goes to arr1. arr1 = [2, 3]

Final result: arr1 + arr2 = [2, 3, 1].

Now a slightly longer one, nums = [5, 4, 3, 8]:

  • 5 → arr1 = [5]
  • 4 → arr2 = [4]
  • Compare: 5 > 4, so 3 → arr1. arr1 = [5, 3]
  • Compare: arr1's last is 3, arr2's last is 4. Now arr2 wins, so 8 → arr2. arr2 = [4, 8]

Final result: [5, 3, 4, 8].

Notice how the "lead" switched trays between rounds. That's the whole game: the comparison resets every single time based only on what's currently on top of each pile.

Intuition

The natural first instinct when you see "split into two arrays" is to alternate — odd-indexed numbers into arr1, even-indexed into arr2. It's a tempting shortcut because a lot of "distribute" problems really do work that way.

Test that instinct against nums = [1, 2, 3, 4, 5]. Alternating by position would predict arr1 = [1, 3, 5] and arr2 = [2, 4]. But walk through the actual rule: after seeding 1 into arr1 and 2 into arr2, every subsequent comparison favors arr2, because arr2's last element keeps climbing higher than arr1's frozen 1. You end up with arr1 = [1] and arr2 = [2, 3, 4, 5] — nothing like the alternating guess.

This is what makes the problem greedy in the true sense: each decision is made using only the current state of the two piles — the last card placed on each — and never looks ahead or back further than that. Once you internalize "compare last elements, append to the bigger one, repeat," the rest is direct translation into code.

Brute Force Solution

There isn't really a meaningfully different "brute force" here — the rule itself is already the algorithm. The only thing you could call brute force is checking membership in each array with in, which does a linear scan.

  • Idea: Follow the rule exactly, but use plain Python lists and in for any existence checks.
  • Algorithm: Same as above — seed both arrays, loop through the rest, compare last elements, append.
  • Advantages: Simple, no extra data structures.
  • Disadvantages: If you ever need to check "does this array already contain X" (as you do in some variants), using in on a list is O(n) per check, which degrades the whole solution to O(n²) in the worst case.
  • Time complexity: O(n²) if using list membership checks; O(n) if not needed at all for this specific problem.
  • Space complexity: O(n) for the two output arrays.

For 3069 specifically, no membership check is actually required — the rule only ever looks at the last element of each array, not whether a value has been seen before. So the "brute force" and "optimal" solutions here converge to almost the same thing, which is unusual and worth noticing.

Optimal Solution

Here's the full breakdown:

Step Action
1 Seed arr1 with nums[0]
2 Seed arr2 with nums[1]
3 Loop from nums[2] to the end
4 Compare arr1[-1] and arr2[-1]
5 Append to whichever array has the bigger last element
6 Return arr1 + arr2

The one-indexed trap deserves its own callout. The problem statement talks about nums[1], nums[2], and so on, because LeetCode problems are often written in one-indexed math notation. If you copy that numbering directly into Python — treating nums[1] as "the first element" — you'll seed arr1 and arr2 with the wrong numbers from the very first step. In Python, the first element is nums[0], the second is nums[1], and everything shifts down by one. This single off-by-one mistake is common enough that it's worth writing a comment in your code reminding yourself of the shift.

The other detail worth internalizing: the distinct-values guarantee is what makes the comparison well-defined. If arr1[-1] could ever equal arr2[-1], the rule "append to the bigger one" would have no answer for a tie. Because the problem guarantees distinct values, that comparison always has a clear winner, and you never need tie-breaking logic.

Python Code

from typing import List


def distribute_elements(nums: List[int]) -> List[int]:
    """Distribute nums into two arrays by comparing last-placed elements."""
    arr1 = [nums[0]]
    arr2 = [nums[1]]

    for num in nums[2:]:
        if arr1[-1] > arr2[-1]:
            arr1.append(num)
        else:
            arr2.append(num)

    return arr1 + arr2

Code Walkthrough

  • arr1 = [nums[0]] and arr2 = [nums[1]]: seed each array with its forced first card. No comparison needed yet, per the rule.
  • for num in nums[2:]: iterate over every remaining number, starting from the third element (index 2), since the first two are already placed.
  • if arr1[-1] > arr2[-1]: arr1[-1] is Python's shorthand for "the last item in arr1," which is exactly the "last card on the tray" the rule refers to.
  • arr1.append(num) / arr2.append(num): place the new number on whichever tray currently has the bigger last card.
  • return arr1 + arr2: once every number is placed, concatenate the two arrays in order — arr1 first, then arr2.

Dry Run

Trace nums = [3, 1, 5, 1, 3]:

Step Number Action arr1 arr2
1 3 seed arr1 [3] []
2 1 seed arr2 [3] [1]
3 5 3 > 1 → arr1 [3, 5] [1]
4 1 5 > 1 → arr1 [3, 5, 1] [1]
5 3 1 > 1 is False → arr2 [3, 5, 1] [1, 3]

Final result: [3, 5, 1, 1, 3]. Notice the second 1 (step 4) can't go to arr1 even though 1 is already sitting at the end of arr2 — the rule only cares about comparing last elements, not about avoiding duplicates within a tray, since duplicates across arrays are allowed by the problem statement.

Complexity Analysis

  • Time complexity: O(n). We walk through nums exactly once. Each iteration does one comparison and one append, both O(1) operations. No nested loops, no repeated scans.
  • Space complexity: O(n). We store every input number across arr1 and arr2, plus the final concatenated result. There's no auxiliary structure beyond the two output arrays.

Both bounds are tight — you can't do better than O(n) since you must at least look at every number once, and you can't use less than O(n) space since the output itself must contain every number.

Alternative Solutions

You could use a deque instead of a list for arr1/arr2, but since we only ever append to the end and read the last element (both O(1) on a plain Python list), a deque buys nothing here — it's suited for cases needing fast operations at both ends.

Another alternative is tracking just last1 and last2 as scalar variables instead of indexing into the lists each time (arr1[-1]). This is a micro-optimization that avoids repeated list indexing, but Python's list[-1] is already O(1), so the gain is negligible. It's worth knowing about for interview conversations on micro-optimization, but not worth complicating the code for.

Edge Cases

  • Minimum input size: The problem guarantees at least 2 elements, so nums[0] and nums[1] are always safe to access.
  • Exactly two elements: arr1 = [nums[0]], arr2 = [nums[1]], loop never runs, result is [nums[0], nums[1]].
  • Strictly increasing sequence: arr2 will almost always win comparisons after the first few steps since its last value keeps growing.
  • Strictly decreasing sequence: arr1 tends to dominate for the same reason, in reverse.
  • Large input (up to 10^5 elements): The O(n) approach handles this comfortably; an O(n²) approach (from unnecessary membership checks) would not.

Common Mistakes

  1. Off-by-one from one-indexed problem statement: treating nums[1] as the first element instead of nums[0].
  2. Alternating elements by position instead of comparing last elements — this only coincidentally matches the correct answer for some inputs.
  3. Comparing the first elements of each array instead of the last — the rule explicitly cares about the most recently placed card, not the original seed.
  4. Forgetting to seed both arrays before the loop, causing an index error or a wrong result on arr2[-1] when arr2 is empty.
  5. Using < instead of > (or vice versa) in the comparison, which silently flips the entire distribution and produces a plausible-looking but wrong array.
  6. Adding unnecessary membership checks with in, which turns a clean O(n) solution into O(n²) for no benefit on this specific problem.

Key Takeaways

  • Read the exact rule before reaching for a familiar pattern — alternating looked plausible here but was wrong.
  • Greedy problems like this hinge on a clearly defined, tie-free comparison; the distinct-values guarantee is what makes that possible.
  • Python's one-indexed problem statements are a common source of off-by-one bugs — always translate carefully to zero-indexed code.
  • A single pass with O(1) work per element is often all you need — resist the urge to add data structures the problem doesn't require.

📇 Flashcards

What pattern solves 'Distribute Elements Into Two Arrays I'?

Greedy simulation: seed two arrays with first two elements, then route each new element by comparing the two arrays' current last values.

Time complexity of the distribute-into-two-arrays greedy walk?

O(n) — one pass over nums, each element appended in constant time via a comparison.

Space complexity, excluding the output arrays themselves?

O(1) extra — you only track two running last-values; the output arrays are the required result, not overhead.

Trickiest bug when implementing this from the 1-indexed statement?

Off-by-one: nums[1] and nums[2] seed the trays, so the loop must start scanning from the third element, index 2 in 0-indexed code.

What breaks the greedy rule if values aren't distinct?

Nothing breaks — ties still route deterministically (arr1 wins only on strict >), so equal last-values always fall through to arr2.

Interview follow-up: why is this greedy and not DP?

Each element's destination depends only on the two current tail values, not on future choices, so a local rule is always optimal — no backtracking needed.
