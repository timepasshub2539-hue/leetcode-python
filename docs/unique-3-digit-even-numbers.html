3483. Unique 3-Digit Even Numbers | LeetCode Python Solution (why 5×9×8 is wrong)

General ✓ Runtime tested

Introduction

Some LeetCode problems test whether you know a data structure. Others test whether you can think. LeetCode 3483, "Unique 3-Digit Even Numbers," belongs firmly in the second camp. On the surface it looks like a five-second combinatorics warm-up — pick digits, multiply, done. That's exactly the trap.

This problem matters because it's a miniature version of a mistake that shows up constantly in real interviews and real code: applying one formula uniformly across positions that don't actually behave the same way. Interviewers love this problem precisely because the "obvious" answer is wrong, and watching how a candidate reacts when their quick math doesn't match the brute-force check tells them a lot about how that candidate debugs.

If you learn one thing from this problem, learn this: whenever a position in a sequence has a special rule (can't be zero, can't be a symbol, can't repeat a previous choice), stop and ask whether that rule interacts with your other choices before you multiply anything together.

Problem Overview

You're given a list of digits — somewhere between 3 and 10 of them, each between 0 and 9, and duplicates are allowed (the same digit can appear more than once in the list). Your job is to count how many distinct 3-digit even numbers you can build from these digits, following two rules:

  1. Each entry in the list can only be used once per number you build, but if a digit appears twice in the list, you're allowed to use two copies of it in the same number.
  2. The number can never start with a zero — because a number like "042" isn't really a 3-digit number, it's just 42.

You're counting distinct final numbers, not distinct arrangements — so if two different physical copies of the digit "2" in your list produce the same 3-digit number, that only counts once.

Example

Take digits [1, 2, 3, 4]. Since every digit appears exactly once, there's no duplicate-copy issue to worry about — we just need arrangements where the last digit is even (2 or 4) and the first digit isn't zero (automatically true here, since there's no zero in the list at all).

Some valid numbers: 124, 132, 214, 234, 312, 342, 412, 431... walk through it and you'll find exactly 12 valid 3-digit even numbers. Nothing repeats, because nothing in the input repeats.

Now change the input to [0, 2, 2, 4]. Suddenly zero is in play, and there are two copies of 2. This is where the real problem lives — you now have to worry about leading zeros and about two different 2's producing the same final number.

Intuition

Here's the instinct almost everyone has on first read: "last digit must be even, so 5 choices (0, 2, 4, 6, 8); first digit can't be zero, so 9 remaining choices; middle digit is whatever's left, so 8 choices." Multiply them: 5 × 9 × 8 = 360.

It feels airtight. It isn't.

The flaw is subtle: the phrase "9 remaining choices for the first digit" assumes that after removing the last digit, there are always 9 digits left that could validly go first. But that assumption quietly depends on what the last digit was.

  • If the last digit was 0, then zero is already spent — every other digit (1 through 9, that's 9 of them) is fair game for the front. No conflict.
  • If the last digit was 2, 4, 6, or 8, zero is still sitting in the pool, unused — and it still can't go in front. So the front position doesn't actually get 9 free choices; it gets 8 (nine digits total minus zero, since zero is excluded and the last digit is also excluded).

That's the whole bug. One formula assumed a uniform "9 choices" for the first digit regardless of which even digit got used last — but zero being used up versus zero being merely unavailable are two different situations with two different counts. This is a case-based problem wearing a single-formula disguise.

Brute Force Solution

Idea: Skip the hand math entirely. Generate every permutation of three digits from the input, filter out the ones that start with zero or end in an odd digit, and count what's left. Drop results into a set to avoid double-counting identical numbers built from different digit copies.

Algorithm: 1. Generate all permutations of length 3 from the digit list. 2. For each permutation (a, b, c), keep it if a != 0 and c is even. 3. Combine the three digits into a number and add it to a set. 4. Return the size of the set.

Advantages: Dead simple to write, impossible to get wrong once you trust itertools, and naturally handles duplicate-copy limits (since permutations are built from list positions, a digit that appears once can't be used twice).

Disadvantages: Doesn't scale — but that's fine here, because the input has at most 10 digits.

Time complexity: O(n³) in the worst case for generating permutations of a length-n list restricted to 3 positions, which is really O(n × (n-1) × (n-2)) — at most about 720 permutations for n=10.

Space complexity: O(n³) for storing the intermediate permutations plus O(1) extra for the result set, since at most a few hundred entries ever exist.

Optimal Solution

The "optimal" solution here isn't a different algorithm — it's the correct formula, applied by splitting on the one variable that actually changes the count: what the last digit is.

Case Last digit choices First digit choices Middle digit choices Subtotal
A: last digit is 0 1 (just 0) 9 (any nonzero digit) 8 (whatever's left) 1 × 9 × 8 = 72
B: last digit is 2, 4, 6, or 8 4 8 (can't be 0, can't repeat last digit) 8 (whatever's left) 4 × 8 × 8 = 256

Add the two subtotals: 72 + 256 = 328 — not 360.

The key visual: in Case A, zero disappears from the pool entirely (it's been used), so the first digit has a full 9 options. In Case B, zero is still sitting there unused and still forbidden from the front, so the first digit effectively loses one option compared to Case A. That single difference is where the missing 32 went (360 − 328 = 32).

For the actual LeetCode problem — with a real list of digits instead of the abstract range 0-9, and possible duplicates — the brute-force permutation approach is simpler to implement correctly than re-deriving this formula for arbitrary digit multisets, and since the input is capped at 10 digits, there's no performance reason not to use it.

Python Code

from itertools import permutations


class Solution:
    def totalNumbers(self, digits: list[int]) -> int:
        seen = set()

        for a, b, c in permutations(digits, 3):
            if a != 0 and c % 2 == 0:
                seen.add(a * 100 + b * 10 + c)

        return len(seen)

Code Walkthrough

  • from itertools import permutations — pulls in the standard-library tool that generates every ordered arrangement of a given length from a list, without us hand-rolling recursion.
  • seen = set() — holds the distinct valid numbers we've built so far; using a set (not a list) means duplicate numbers from duplicate digit copies collapse automatically.
  • for a, b, c in permutations(digits, 3): — iterates every ordered triple of positions from digits. Because permutations operate on positions, not values, a digit that only appears once in the input can never be used twice in one triple — the copy limit is enforced for free.
  • if a != 0 and c % 2 == 0: — the two rules from the problem: no leading zero, last digit must be even.
  • seen.add(a * 100 + b * 10 + c) — reconstructs the actual 3-digit number from its digits and stores it.
  • return len(seen) — the count of distinct valid numbers.

Dry Run

Input: digits = [0, 2, 2, 4]

Permutations of length 3 include things like (0, 2, 2), (2, 0, 2), (2, 2, 0), (2, 4, 0), (4, 2, 2), (2, 2, 4), and many more.

  • (0, 2, 2) → a == 0, rejected (leading zero).
  • (2, 0, 2) → a = 2 (fine), c = 2 (even) → number = 202, added to seen.
  • (2, 2, 0) → a = 2, c = 0 (even) → number = 220, added.
  • (2, 4, 0) → a = 2, c = 0 → number = 240, added.
  • (4, 2, 2) → a = 4, c = 2 → number = 422, added.
  • (2, 2, 4) → a = 2, c = 4 → number = 224, added.

Notice that (2, 0, 2) using the first copy of 2 as a and (2, 0, 2) using the second copy both produce 202 — but since we store the integer 202 in a set, it only counts once, even though two different permutation tuples generated it.

After all permutations are processed, seen contains the full list of distinct valid numbers, and len(seen) is the answer.

Complexity Analysis

Time: O(n³) where n is the number of digits (at most 10), since permutations(digits, 3) produces at most n × (n-1) × (n-2) tuples, and each is processed in constant time. In practice, that's at most 720 iterations — this is correct because we're bounding a brute-force enumeration by a small, fixed input size, not because n³ is generally fast.

Space: O(n³) in the worst case for the set (bounded by the number of distinct 3-digit numbers, which is at most 900, and also bounded by the permutation count), plus O(1) auxiliary space per iteration. This is correct because the set can never hold more entries than there are permutations feeding it.

Alternative Solutions

The two-case formula from the "Optimal Solution" section generalizes to the range 0-9 with no duplicates, and computing it directly is O(1) time and space — strictly faster than brute force. The catch: the moment your input has arbitrary duplicate digits and isn't guaranteed to contain every digit 0-9, you'd need to carefully count how many digits are available in each category (zero vs. nonzero-even vs. nonzero-odd, and how many copies of each), which turns a one-line formula into a small case-counting routine of its own. For an input capped at 10 digits, that added complexity doesn't buy you anything the brute-force version doesn't already give you for free — this is a case where the "clever" solution is worse engineering than the "dumb" one.

Edge Cases

  • All digits identical, e.g. [2, 2, 2]: Only one distinct number is possible (222), and only if it satisfies both rules — here it does, but if the repeated digit were odd, the answer would be 0.
  • No zero in the list: The leading-zero rule never triggers, and the two-case split (Case A / Case B) collapses to just Case B's logic.
  • Only one even digit available, e.g. [1, 3, 5, 7, 8]: Every valid number must end in that one digit — count drops sharply since there's no choice for the last position.
  • Minimum-length input (3 digits): If those 3 digits don't include an even digit or the only valid arrangement starts with zero, the answer can be 0.
  • Maximum-length input (10 digits) with heavy duplication: Tests whether your solution actually deduplicates — without the set, this case would overcount badly.

Common Mistakes

  1. Using the single formula "choices for last × choices for first × choices for middle" without splitting on whether the last digit is zero — this is the exact 360-vs-328 trap.
  2. Forgetting that zero, once used as the last digit, is no longer available for the first digit's exclusion check — leading to double-penalizing the first digit's choices.
  3. Building numbers from permutations of range(10) instead of the actual input digits list — this ignores the constraint that a digit can only be used as many times as it appears.
  4. Forgetting to deduplicate with a set, so numbers built from two different physical copies of the same digit get counted twice.
  5. Checking c % 2 == 0 before checking a != 0, then short-circuiting incorrectly, or checking oddness/evenness against the wrong variable (a common typo when swapping between reading digits as strings vs. integers).

Key Takeaways

The lesson isn't really about digits — it's about spotting when a shared multiplier formula silently assumes something that isn't actually constant across cases. Any time the first slot in a sequence has a rule the other slots don't (can't be zero, can't be a special character, can't repeat), check whether that rule's effect changes depending on what happened elsewhere before you multiply. When in doubt, brute-force it and compare — it's the fastest way to catch a formula that's subtly wrong instead of visibly broken.

📇 Flashcards

How many unique 3-digit even numbers from digits 1,2,3,4 (no repeats)?

Split by last digit: last=2 or 4 gives 2×2=4 each; count both cases, sum them.

Why can't the leading digit be 0 in this digit-arrangement problem?

3-digit numbers can't start with 0, so first-position choices exclude 0 even if 0 is in the digit set.

Why split into 'last digit zero' vs 'last digit nonzero even' cases?

When last digit is 0, first digit has full remaining choices; when nonzero even, first digit loses one option (can't be 0).

Time complexity of counting unique 3-digit even numbers from n digits?

O(1) with combinatorics (permutation formula); O(n^3) if brute-force enumerating all digit triples.

Common bug when counting these numbers by brute force?

Forgetting to exclude leading zero, silently including invalid numbers like 024 as valid 3-digit numbers.

Combinatorics case-split vs brute-force enumeration — when to prefer which?

Use case-split math for large digit sets (fast, exact); brute force fine for small fixed sets like 4 digits, easier to verify.
