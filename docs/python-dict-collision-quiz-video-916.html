Why Do Two Different Keys Land in the Same Dict Slot? #shorts

General

Introduction

Most developers use Python dictionaries hundreds of times a day without ever asking how they actually work under the hood. We're taught that dict lookups are O(1), and we leave it at that. But interviewers love this topic precisely because "just O(1)" is an assumption, not an understanding — and a single line of code can expose the gap.

Consider this: what happens when you insert a value under the key 1, and then insert another value under the key True? Most people guess you'd end up with two separate entries. You don't. This kind of question shows up in interviews not because anyone expects you to memorize Python trivia, but because it tests whether you actually understand what a dictionary key is — a hash plus an equality check, not just a piece of data sitting in a slot. Once you understand that, a whole category of "why is my dict behaving weirdly" bugs stops being mysterious.

Problem Overview

Here's the scenario, stripped down to its essence:

  1. Create an empty dictionary.
  2. Set the value at key 1 to "one".
  3. Set the value at key True to "yes".
  4. Print the dictionary.

The question: does the dictionary end up with one entry or two? And if one, which key survives, and which value wins?

This isn't a syntax trick — it's a direct test of how Python decides whether two keys are "the same" for the purposes of a dictionary.

Example

d = {}
d[1] = "one"
d[True] = "yes"
print(d)

Output:

{1: 'one'}

Notice two things happening at once: - There's only one entry, not two. - The value is "yes" (from the second assignment), but the key displayed is still 1 (from the first assignment).

If you only skimmed this, you might expect {1: 'one', True: 'yes'}. That's the wrong mental model, and figuring out why it's wrong is the whole point.

Intuition

An experienced engineer doesn't start by memorizing "Python dicts do X with booleans." They start by asking: what does a dictionary actually need from a key?

A Python dict is a hash table. To store or retrieve a value, it needs two things from the key:

  1. A hash value (hash(key)) — used to find which bucket to look in.
  2. An equality check (key1 == key2) — used to confirm two keys that landed in the same bucket are actually the same key, not just a hash collision.

Now recall a fact about Python's type system: bool is a subclass of int. True behaves like 1, and False behaves like 0, in every arithmetic and equality context:

True == 1        # True
hash(True) == hash(1)   # True
True + True       # 2

Since hash(True) == hash(1) and True == 1, the dictionary has no way — and no reason — to treat them as different keys. As far as the dict's internal machinery is concerned, d[True] = "yes" is not a new insertion. It's an update to the existing entry for 1.

That single insight — dict identity is governed by hash + equality, not by type or spelling — is the seed of the entire solution. Once you see it, the "which key survives" behavior falls out naturally: Python's dict implementation only overwrites the value on a match; it leaves the original key object in place. That's a CPython implementation detail worth knowing, not just a quirk — it's consistent, documented behavior.

Brute Force Solution

There isn't really a "brute force" algorithm to write here — this is a conceptual problem, not a computational one. But it's still worth walking through the naive (wrong) mental model, because articulating why it fails is instructive.

Naive assumption: "Different literals mean different keys." Under this assumption, you'd expect the dict to grow to two entries, since 1 and True are typed and spelled differently.

Why it's wrong: This assumption treats keys as raw syntax rather than as objects with __hash__ and __eq__. It ignores that Python's equality model is based on value semantics for these types, not identity or literal representation.

  • Advantages: None — it's simply an incorrect model, useful only as a strawman to correct.
  • Disadvantages: Leads to bugs any time your dict keys can include bool-and-int pairs, or more generally, any two objects that are __eq__-equal but look different (e.g., 1 and 1.0, or custom objects with overridden equality).
  • Complexity: N/A — this is a reasoning error, not an algorithm.

Optimal Solution

The "optimal solution" here is really the correct mental model, applied step by step to the actual dict machinery:

Step 1 — Insert 1. Python computes hash(1), finds (or creates) the bucket for that hash, and stores the key-value pair (1, "one") there.

Step 2 — Insert True. Python computes hash(True). Since hash(True) == hash(1), it lands in the same bucket.

Step 3 — Collision resolution. Landing in the same bucket doesn't automatically mean "same key" — hash collisions between genuinely different objects happen too. So Python runs the equality check: True == 1 → True. Since both the hash and the equality check confirm a match, Python treats this as an update to the existing entry, not a new one.

Step 4 — Value overwrite, key preserved. CPython's dict implementation updates the value stored at that slot to "yes", but it does not replace the stored key object. The original key 1 stays put. This is why print(d) shows {1: 'one'}... wait — let's be precise with the actual value:

{1: 'yes'}

The key remains 1 (the object originally inserted), but the value has been overwritten to "yes".

Step Action Bucket (via hash) Equality check Result
1 d[1] = "one" bucket for hash(1) — New entry: 1 → "one"
2 d[True] = "yes" same bucket (hash(True) == hash(1)) True == 1 → True Existing entry updated: 1 → "yes"

This table is the entire mechanism. No magic, no special-casing of bool — just the general rule for how any two keys interact in a Python dict, applied to a pair that happens to look surprising at first glance.

Python Code

def demonstrate_dict_collision() -> dict:
    """Show how True and 1 collide as dictionary keys."""
    d = {}
    d[1] = "one"
    d[True] = "yes"
    return d


if __name__ == "__main__":
    result = demonstrate_dict_collision()
    print(result)                    # {1: 'yes'}
    print(len(result))               # 1
    print(1 in result, True in result)  # True True

Code Walkthrough

  • d = {} creates an empty dict, which internally allocates a small hash table.
  • d[1] = "one" computes hash(1), places 1 in the corresponding bucket, and associates it with "one".
  • d[True] = "yes" computes hash(True). Because bool inherits int's hashing behavior, hash(True) == hash(1) == 1. Python probes the same bucket, finds the existing key 1, checks True == 1 (which is True), concludes it's the same key, and overwrites the value with "yes".
  • return d returns a dict with exactly one entry: {1: 'yes'}.
  • The len(result) == 1 check confirms no second entry was created.
  • 1 in result and True in result both return True because membership testing uses the same hash + equality logic as insertion.

Dry Run

Starting state: d = {}

  1. d[1] = "one" → d = {1: 'one'}
  2. d[True] = "yes": - hash(True) → 1 - Probe bucket for hash 1 → finds existing key 1 - True == 1 → True → same key confirmed - Overwrite value: d = {1: 'yes'}
  3. print(d) → {1: 'yes'}

Final dict has one key (1), one value ("yes").

Complexity Analysis

  • Time: O(1) average per insertion, same as any dict write — computing a hash and probing a bucket doesn't change because the keys happen to collide by value. The collision here is a correctness detail (same key, not two keys), not a performance one (Python dicts already expect and handle hash collisions between genuinely different keys via open addressing).
  • Space: O(1) additional space — since no new entry is created, the dict doesn't grow at all for the second assignment.
  • Why these are correct: The collision-handling path (hash match → equality check) is already part of every dict write in CPython; this example doesn't invoke a special code path, it just happens to trigger the "same key" branch instead of the "different key, same bucket" branch.

Alternative Solutions

There's no alternative algorithm here since this is a language-semantics question, but it's worth knowing the related cases that test the same underlying concept:

  • 1 vs 1.0: hash(1) == hash(1.0) and 1 == 1.0, so they also collide as dict keys. {1: 'a', 1.0: 'b'} produces {1: 'b'}.
  • Custom objects with overridden __eq__ and __hash__: Any two objects where you've made __eq__ return True and __hash__ return the same value will collide the same way, regardless of type.
  • Frozensets/tuples as keys: Different container objects with equal contents also collide, by the same hash+equality rule ({(1, 2): 'x', (1, 2): 'y'} → {(1, 2): 'y'}).

The common thread: dict key identity is a two-part contract (__hash__ and __eq__), not a type check.

Edge Cases

  • Empty dict: No collision possible; behavior is trivially defined.
  • Reversed insertion order: d[True] = "yes"; d[1] = "one" produces {True: 'one'} — same collision, but now True is the key that's preserved, since it was inserted first.
  • False and 0: Same collision pattern — hash(False) == hash(0) and False == 0.
  • Mixing 1, True, and 1.0 in sequence: All three collide into a single entry; whichever is inserted first determines the surviving key object.
  • Non-hashable keys (lists, dicts): Not applicable to this collision pattern — those raise TypeError before hashing even matters.

Common Mistakes

  1. Assuming type determines dict key identity. Type is irrelevant; hash and equality are what matter.
  2. Expecting len(d) to grow with every assignment. An assignment to an existing key updates in place; it doesn't add a new entry.
  3. Assuming the second assignment replaces the key object, not just the value. CPython keeps the original key object on a match — this is subtle and easy to get backwards.
  4. Ignoring bool's relationship to int. Forgetting that bool is a subclass of int leads to surprising bugs in any code that uses 0/1 and True/False interchangeably as dict keys or set members.
  5. Confusing hash collisions between different keys (a performance concern handled internally) with equal keys (a correctness/identity concern) — these are two different situations that happen to use the same lookup path.

Key Takeaways

  • Python dictionaries key entries by hash plus equality, not by type or literal spelling.
  • bool is a subclass of int, so True/1 and False/0 hash identically and compare equal — they collide as dict keys.
  • On a collision between equal keys, Python updates the value but keeps the original key object.
  • This isn't a bug or an edge case to work around — it's the same general mechanism that makes dict lookups fast and consistent for every key type.
  • Understanding this turns "why did my dict do that" moments into predictable, reasoned-through behavior.

📇 Flashcards

Dict lookup slow with many collisions — what's the tell?

Poor/duplicate hash values clustering keys into same buckets; think hash function quality, not dict itself.

Average time complexity of dict get/set despite collisions?

O(1) amortized — CPython uses open addressing with probing to resolve collisions.

Space complexity of a Python dict with n entries?

O(n), but overallocated (load factor ~2/3) so actual memory is larger than n slots.

Tricky bug: two unequal objects with same hash() value?

Legal collision — dict still works via __eq__ check per bucket, but custom __hash__ without __eq__ can break lookups.

Open addressing vs separate chaining for collisions?

CPython dicts use open addressing (probe sequence in same array); many other languages chain via linked lists per bucket.

Interview follow-up: why must equal objects have equal hashes?

Dict/set lookup finds bucket by hash then confirms via __eq__; mismatched hash breaks that invariant, causing missed lookups.
