Can You Predict a Python Dict Collision? #shorts

General

Introduction

Every Python developer uses dictionaries daily, but very few can explain what actually happens when two different-looking keys collide. This isn't a corner case you'll only meet in a systems course — it's something that quietly changes program behavior in real code, and it's a favorite subject for technical interviewers because it tests whether you understand a data structure or just know its syntax.

The specific scenario here — setting d[1] = "one" and then d[True] = "yes" — looks like it should produce a dictionary with two entries. It doesn't. Understanding why forces you to actually learn how Python decides two keys are "the same," which is a much deeper and more useful skill than memorizing dict syntax. It also sets up a foundation for understanding hash tables in general, which show up constantly in coding interviews: two-sum, grouping anagrams, caching, deduplication — all of it rests on the same mechanics you're about to see.

Problem Overview

You're given the following sequence of operations on an empty dictionary:

  1. Create an empty dictionary.
  2. Set the key 1 to the value "one".
  3. Set the key True to the value "yes".
  4. Print the dictionary.

The question: what gets printed? Most people instinctively expect two separate entries, one for 1 and one for True, because they look like different types — an integer and a boolean. The actual output has only one entry, and figuring out why requires understanding two separate mechanisms: how Python decides two objects are equal, and how it decides where an object lives inside a dictionary's internal hash table.

Example

d = {}
d[1] = "one"
d[True] = "yes"
print(d)

Output:

{1: 'yes'}

Only one key-value pair survives. The key stays 1 — the original key inserted — but the value has been overwritten to "yes". Nothing about True appears in the printed dictionary at all, even though it was the last thing written.

Intuition

The instinct to reach for is: "bool is a subtype of int in Python." That's true, but it only tells you that something odd might happen — it doesn't tell you why the dictionary treats them as the same key.

The real answer sits inside two dunder methods every object has: __eq__ and __hash__. A dictionary is a hash table. When you do d[key] = value, Python doesn't scan every existing key one by one. Instead it:

  1. Computes hash(key).
  2. Uses that hash to find a bucket (a slot) in the underlying table.
  3. If something is already in that bucket, it checks equality (==) against the existing key to decide whether this is the same key being updated, or a different key that happens to hash the same (a genuine collision requiring extra probing).

So the question "are 1 and True the same dictionary key?" comes down to two smaller questions:

  • Does hash(1) == hash(True)?
  • Does 1 == True?

In Python, both are true. bool is implemented as a subclass of int, where False behaves as 0 and True behaves as 1. Because of that design choice, hash(True) == hash(1) and True == 1 both evaluate to True. As far as the dictionary is concerned, they are indistinguishable as keys — even though they print differently and type(True) is not type(1).

Once you see hashing and equality as the two gatekeepers, the surprising behavior stops being surprising. It's not a quirk of dictionaries — it's a direct, logical consequence of how booleans are built on top of integers.

Brute Force Solution

There isn't really a "brute force algorithm" here since this is a language-behavior question rather than a computational problem, but it's worth walking through the naive mental model people use before they understand hashing — a linear scan.

Idea: Imagine a dictionary implemented as a plain list of (key, value) pairs. To set a key, you'd loop through the list checking existing_key == new_key for every entry.

class NaiveDict:
    def __init__(self):
        self.items = []

    def __setitem__(self, key, value):
        for i, (k, v) in enumerate(self.items):
            if k == key:
                self.items[i] = (k, value)  # overwrite, keep original key
                return
        self.items.append((key, value))

Advantages: Easy to reason about, and it actually reproduces the exact same "same key" behavior, because it also relies purely on ==.

Disadvantages: Every insertion is O(n) because it scans the whole list. This is exactly the cost that hash tables were invented to avoid.

Time complexity: O(n) per insertion, O(n²) for n insertions. Space complexity: O(n).

This version is useful only to prove a point: even without hashing at all, 1 and True would still collide, because 1 == True regardless of hashing. Hashing is what makes it fast; equality is what makes it collide.

Optimal Solution

Python's real dictionary implementation uses open addressing with a hash table. Here's the flow when you run d[True] = "yes" after d[1] = "one" already exists:

Step Operation Result
1 hash(True) Same integer as hash(1)
2 Locate bucket using that hash Same bucket as the one holding key 1
3 Compare True == 1 at that bucket True (equal)
4 Decide action Update value in place, keep the original key object

The critical, often-missed detail: the dictionary keeps the original key object (1), not the new one (True), even though True was the key used in the assignment. Python's dict only replaces the key if none existed there before; if a matching key is found, only the value is updated. This is documented CPython behavior, not an accident.

Before:              After d[True] = "yes":
┌─────────────┐      ┌─────────────┐
│ bucket(1) →  │      │ bucket(1) →  │
│  key: 1      │      │  key: 1      │   <- key unchanged
│  val: "one"  │      │  val: "yes"  │   <- value overwritten
└─────────────┘      └─────────────┘

Python Code

def demonstrate_dict_collision() -> dict:
    """Show that True and 1 collide as dictionary keys."""
    d = {}
    d[1] = "one"
    d[True] = "yes"
    return d


if __name__ == "__main__":
    result = demonstrate_dict_collision()
    print(result)                       # {1: 'yes'}
    assert result == {1: "yes"}
    assert list(result.keys()) == [1]   # key stayed 1, not True
    assert hash(1) == hash(True)
    assert 1 == True

Code Walkthrough

  • d = {} creates an empty hash table with no buckets in use.
  • d[1] = "one" computes hash(1), places 1 in the corresponding bucket, and stores "one" as its value.
  • d[True] = "yes" computes hash(True), which equals hash(1), so Python looks in the same bucket. It finds 1 already there and checks 1 == True, which is True. Since a matching key exists, Python overwrites the value only — the key object in the table remains 1.
  • print(result) shows the dictionary has exactly one entry: {1: 'yes'}.
  • The assertions at the bottom double as a lightweight self-check: they confirm the final dict, the surviving key, and the underlying hash/equality facts that caused the behavior.

Dry Run

Starting state: d = {}

  1. d[1] = "one" → table: {1: "one"}
  2. d[True] = "yes": - hash(True) → same as hash(1) - bucket lookup finds key 1 - 1 == True → True, so this is treated as an update, not a new entry - value at that bucket becomes "yes"
  3. Final table: {1: "yes"}
  4. print(d) → {1: 'yes'}

Complexity Analysis

  • Time: O(1) average per dictionary operation (get/set), because hash table lookups don't scan every element — they jump straight to a bucket via the hash value. Worst case is O(n) under pathological hash collisions, but that's irrelevant here since 1 and True intentionally hash the same by design, not by bad luck.
  • Space: O(n) for n unique keys stored. In this example, space stays O(1) because the second assignment doesn't add a new key — it overwrites an existing one.

These bounds are correct because Python's dict is a true hash table (not a list), and the True/1 case is simply the expected behavior of that table when hash() and __eq__ agree.

Alternative Solutions

If you actually wanted two separate entries for the boolean and the integer, you'd need to avoid relying on bool and int sharing identity/equality. One option: use a tuple that includes the type as part of the key.

d = {}
d[(int, 1)] = "one"
d[(bool, True)] = "yes"
print(d)  # {(int, 1): 'one', (bool, True): 'yes'}

This works because (int, 1) != (bool, True) — the tuples differ even though their second elements are "equal" under ==. It's a common pattern when you need type-sensitive keys and can't rely on default hashing behavior.

Edge Cases

  • Empty dictionary: No keys exist yet, so the first assignment always creates a new entry — no collision possible.
  • 0 and False: Same story as 1/True — hash(0) == hash(False) and 0 == False, so they collide identically.
  • Mixing int and float keys: 1 == 1.0 and hash(1) == hash(1.0), so d[1] = "a"; d[1.0] = "b" also collides, keeping key 1.
  • Reversed insertion order: If you insert True first and then 1, the surviving key is True, not 1 — the first key inserted is always the one retained.
  • Non-hashable keys: Attempting d[[1,2]] = "x" raises TypeError, since lists aren't hashable — a completely different failure mode from a collision.

Common Mistakes

  1. Assuming type() determines dictionary key uniqueness — it doesn't; __eq__ and __hash__ do.
  2. Expecting the printed dictionary to show True as a key just because it was the most recent assignment — the original key is preserved, not the new one.
  3. Believing this is a bug or Python quirk rather than intended, documented behavior rooted in bool subclassing int.
  4. Forgetting that hash(x) == hash(y) is a necessary but not sufficient condition for two objects to be treated as the same key — x == y must also hold. Two objects can share a hash and still be distinct keys if they compare unequal.
  5. Writing custom classes with a custom __eq__ but forgetting to also define __hash__, leading to unpredictable dictionary behavior — a very close cousin of this exact problem.

Interview Questions

  • Why does bool subclassing int cause this dictionary behavior?
  • What's the difference between __eq__ and __hash__, and why must objects that are equal also share a hash?
  • What happens if you override __eq__ on a class but not __hash__?
  • Can two objects have the same hash but not be equal? What does the dictionary do in that case?
  • How would you design a key type that treats 1 and True as distinct?

Key Takeaways

Dictionary key uniqueness in Python is governed entirely by hash() and __eq__, not by type. Because bool is a subclass of int with True == 1 and False == 0, boolean and integer keys that are "equal" collapse into a single dictionary entry, and the first inserted key is the one that survives, while later matching assignments only update its value. This one example teaches the exact mechanics behind every hash-based data structure you'll use in interviews and in production code.

📇 Flashcards

When you see repeated hashCode() collisions in a Python dict, think what?

Separate chaining / open addressing under the hood — dict falls back to probing, not a linked bucket list like Java.

Average-case time for dict get/set/delete despite collisions?

O(1) amortized — collisions add constant-factor probing overhead, not asymptotic cost.

Space complexity of a Python dict with n entries?

O(n), but table over-allocates (grows/shrinks in chunks) so actual memory exceeds n slots.

Trickiest bug: mutable key or bad __hash__/__eq__ pair?

Mutating a key after insertion breaks lookup silently; inconsistent __hash__/__eq__ causes duplicate-looking keys or lookup misses.

Python dict collision handling vs Java HashMap?

Python uses open addressing with pseudo-random probing; Java chains colliding entries in a list/tree per bucket.

Follow-up: why must equal objects have equal hashes?

Dict lookup hashes first then checks equality only within that bucket path; mismatched hash/eq breaks retrieval even if objects compare equal.
