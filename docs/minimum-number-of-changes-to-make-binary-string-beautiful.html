2914. Minimum Number of Changes to Make Binary String Beautiful

General ✓ Runtime tested

8. Introduction

Binary string problems show up constantly in coding interviews because they look deceptively simple and hide a trap: the instinct to reach for dynamic programming when none is needed. LeetCode 2914 — Minimum Number of Changes to Make Binary String Beautiful — is a textbook example. The moment you see "binary string" and "minimum changes," your brain wants to start tracking state across the whole string. That instinct is exactly what this problem is testing, and resisting it is the whole lesson.

Interviewers like this problem because it rewards a specific skill: recognizing when a problem decomposes into independent subproblems. That recognition is more valuable than knowing DP patterns by heart, because it tells you when not to use them. If you're prepping for interviews or building intuition for greedy-vs-DP decisions, this is a clean, fast problem to internalize that skill on.

9. Problem Overview

You're given a binary string (only 0s and 1s) whose length is always even. A string is called "beautiful" if you can split it into consecutive blocks, where:

  • every block has even length, and
  • every character inside a block is identical (all 0s or all 1s).

You're allowed to flip any character in the string (turn a 0 into a 1 or vice versa) to force this structure. The question: what's the minimum number of flips required to make the string beautiful?

Note that you don't need to decide the final block boundaries yourself — you just need there to exist some valid way to split the flipped string into these all-matching even blocks.

10. Example

Take the string 1001.

  • Flip index 1: 1 → 1101... wait, let's trace it properly. Flip index 1 (0 → 1): string becomes 1101.
  • Flip index 3 (1 → 0): string becomes 1100.

Now 1100 splits cleanly into 11 and 00 — both even length, both single repeated characters. Two flips were used, and that matches the expected answer for this input.

Why two and not fewer? Because 1001 has two mismatched adjacent pairs — 10 and 01 — and each mismatched pair costs exactly one flip to resolve. There's no way to fix a mismatched pair for free, and no overlap that lets one flip fix two pairs at once.

11. Intuition

The two constraints that matter most are:

  1. The string length is always even.
  2. The string can be up to 100,000 characters long.

The even-length guarantee is the first clue. It means you can walk through the string two characters at a time — positions (0,1), (2,3), (4,5), and so on — with no leftover character at the end. That's not incidental; it's the structural hint for the whole solution.

The length constraint (up to 100,000) is the second clue. Trying every combination of flips is exponential — for a string of length 20 alone, that's over a million possibilities. Anything that scales to 100,000 characters has to be linear: one pass, no backtracking.

So before reaching for dynamic programming, ask one question: does fixing one pair change what any other pair needs?

Look at what "beautiful" actually requires. Each pair just needs its own two characters to match. Fixing pair (0,1) doesn't touch pair (2,3)'s characters, and doesn't change whether that pair already matches or not. There's no shared state between pairs — no running total of 1s versus 0s, no carried-over imbalance, nothing that leaks from one pair into the next.

That's the entire insight: when subproblems don't affect each other, you don't need DP — you just score each one independently and sum the results.

It's worth naming the trap explicitly. Problems like "minimum swaps to group all 1s together" train you to track counts of 1s and 0s, or to think in terms of runs and windows. That's solving a different kind of problem — one where global counts matter. Here, each pair stands completely alone. Importing that pattern-matching instinct from a similar-looking problem is the most common way to overcomplicate this one.

12. Brute Force Solution

Idea: Try every possible subset of flips, check if the resulting string can be split into valid beautiful blocks, and track the minimum number of flips across all valid combinations.

Algorithm: 1. Generate every possible flip combination (2^n subsets for a string of length n). 2. For each resulting string, check whether it can be partitioned into even-length, single-character blocks. 3. Track the minimum flip count among all valid combinations.

Advantages: - Conceptually simple — no insight required, just exhaustive search. - Guaranteed correct, since it checks every possibility.

Disadvantages: - Exponential time complexity makes it unusable beyond small inputs. - Doesn't exploit the independence between pairs at all — all the structure of the problem goes to waste.

Time complexity: O(2^n · n) — 2^n flip combinations, each requiring an O(n) check. Space complexity: O(n) per generated string.

For n up to 100,000, this is not just slow — it's computationally impossible. This is the solution space the O(n) approach completely sidesteps.

13. Optimal Solution

Since each pair (2i, 2i+1) is independent, the minimum number of flips for the whole string is just the sum of the minimum flips needed for each pair.

For any single pair:

Pair contents Already matching? Flips needed
00 Yes 0
11 Yes 0
01 No 1
10 No 1

A mismatched pair always costs exactly 1 flip — change either character to match the other. There's never a case where a pair needs more than one flip, and never a case where you can avoid the flip if the characters differ.

So the algorithm reduces to: walk through the string two characters at a time, and count how many pairs don't match. That count is the answer.

Visually, for 1001:

Index:   0  1  2  3
Char:    1  0  0  1
Pairs:   (1,0)   (0,1)
Match?    No       No
Cost:      1        1

Total cost: 2 — exactly the two flips from the example.

14. Python Code

def min_changes(s: str) -> int:
    """
    Return the minimum number of flips needed to make the binary
    string `s` beautiful (splittable into even-length, single-
    character blocks).
    """
    changes = 0
    for i in range(0, len(s), 2):
        if s[i] != s[i + 1]:
            changes += 1
    return changes


def demo() -> None:
    assert min_changes("1001") == 2
    assert min_changes("10") == 1
    assert min_changes("0000") == 0
    assert min_changes("11") == 0
    assert min_changes("0011") == 0
    assert min_changes("0101") == 2
    print("All checks passed.")


if __name__ == "__main__":
    demo()

15. Code Walkthrough

  • for i in range(0, len(s), 2): strides through the string two characters at a time, landing exactly on each pair's starting index (0, 2, 4, ...). The even-length guarantee is what makes this safe — there's never a dangling single character at the end.
  • if s[i] != s[i + 1]: checks whether the two characters in the current pair already match.
  • changes += 1 adds one flip whenever they don't — this is the only cost a mismatched pair can ever incur.
  • The function returns changes once every pair has been checked — no state is carried between iterations beyond this single counter.

16. Dry Run

String: "1001"

Iteration i Pair s[i], s[i+1] Match? changes after
1 0 (0,1) 1, 0 No 1
2 2 (2,3) 0, 1 No 2

Loop ends (i would be 4, which is len(s)). Final changes = 2, which matches the expected output.

17. Complexity Analysis

Time complexity: O(n), where n is the length of the string. The loop visits each character exactly once (in pairs), doing constant work per pair. No nested loops, no re-scanning.

Space complexity: O(1). Only a single integer counter (changes) is used regardless of input size — no auxiliary arrays, no recursion stack, no memoization table.

Both bounds are tight: you cannot determine the answer without inspecting every character at least once (so O(n) time is necessary), and there's no information that needs to persist beyond the running count (so O(1) space is sufficient).

18. Alternative Solutions

A reasonable alternative is to count mismatches using Python's built-in slicing and comparison instead of an explicit index loop:

def min_changes_pythonic(s: str) -> int:
    evens = s[0::2]
    odds = s[1::2]
    return sum(a != b for a, b in zip(evens, odds))

This produces the identical result and the same O(n) time / O(n) extra space (the slices themselves copy characters), trading a small amount of memory for more idiomatic Python. For very large strings where every byte of memory matters, the index-based loop from section 14 is marginally more efficient since it avoids creating the two sliced copies. For everyday code, either is acceptable — the slicing version is arguably more readable.

19. Edge Cases

  • Minimum length string ("00" or "01"): A single pair. Returns 0 or 1 respectively — handled correctly since the loop always runs at least once for a non-empty even-length string.
  • All identical characters ("0000", "1111"): Every pair already matches, so the function correctly returns 0.
  • Maximally mismatched string ("0101", alternating): Every pair is mismatched, so the result equals half the string's length — the maximum possible flips.
  • Maximum length input (100,000 characters): The O(n) loop handles this in a single linear pass with no risk of timeout or stack issues, since there's no recursion involved.
  • String already beautiful: Returns 0 immediately — no flips are wasted checking anything beyond what's needed.

20. Common Mistakes

  1. Reaching for dynamic programming by default. Nothing here depends on prior state — adding a DP table is wasted complexity for a problem that's just a sum over independent pieces.
  2. Pairing the wrong indices, such as grouping (1,2) and (3,4) instead of (0,1) and (2,3). Only even-start pairing guarantees every block has even length as the problem requires.
  3. Importing logic from "group all 1s together" style problems — tracking running counts of 0s and 1s, or prefix sums, solves a different problem and gives the wrong answer here.
  4. Off-by-one errors in the stride, such as using range(0, len(s)) instead of range(0, len(s), 2), which double-counts or misaligns pairs.
  5. Assuming a mismatched pair could cost more than one flip — some engineers overthink this and try to validate block boundaries beyond the pair, when a single flip always suffices for a 2-character pair.
  6. Not trusting the even-length guarantee, and adding unnecessary bounds checks or padding logic for an odd leftover character that the constraints rule out entirely.

21. Interview Questions

  • Why does pairing index 0 with 1, 2 with 3, and so on work, instead of any other adjacent grouping?
  • What is the time and space complexity of this solution, and why is each bound tight?
  • How would the solution change if blocks were allowed to have odd length?
  • Can you prove that a mismatched pair never requires more than one flip?
  • How would you modify this solution if the string could contain a third character (like '?' representing a wildcard)?
  • What is the key property that lets you avoid dynamic programming here, and how do you recognize that property in other problems?

23. Key Takeaways

  • A binary string problem doesn't automatically require dynamic programming — check whether subproblems are actually dependent before reaching for a DP table.
  • The even-length constraint was the structural hint pointing directly at fixed-pair decomposition.
  • Each pair costs at most one flip, and that cost is completely local — fixing one pair never changes what another pair needs.
  • The final algorithm is a single O(n) pass with O(1) space: count the mismatched pairs, and that count is the answer.
  • The broader lesson transfers far beyond this problem: whenever a problem breaks into pieces that don't affect each other, score each piece independently and sum.

📇 Flashcards

When should you suspect a greedy-pairing trick like LC2914 Beautiful String?

String must split into equal even halves, each half uniform chars — think flip-at-boundary pairs, not brute force.

Time complexity of the optimal Beautiful String solution?

O(n) — one pass counting flips per adjacent 0-1 or 1-0 pair across the string.

Space complexity of the pair-counting approach?

O(1) — just a running counter, no extra arrays or recursion stack needed.

Trickiest bug when counting flips for Beautiful String?

Forgetting pairs must align on even indices (0-1, 2-3,...); scanning with wrong stride double-counts or skips boundaries.

Why does trying every flip combination fail here?

2^n combos explode exponentially; the structure (even-length uniform blocks) lets greedy local pair-checks replace global search.

Interview follow-up: how would you extend this to k-length uniform blocks?

Generalize pair check to compare each block of k chars against the next block, counting mismatches to flip, still O(n).
