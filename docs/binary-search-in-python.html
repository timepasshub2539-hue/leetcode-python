Lesson: How Does Binary Search Find 1 in a Million Guesses?

🎯 Binary Search

Introduction

Every developer eventually hits the moment where checking a list one item at a time just doesn't cut it anymore. Maybe it's a million user IDs, a sorted log of timestamps, or a leaderboard with a hundred thousand entries — and you need to find one value fast. That moment is exactly why binary search exists, and it's why almost every technical interview touches it in some form, directly or as a building block for harder problems.

Binary search isn't hard to memorize. Most people can type it out after seeing it once. What separates a candidate who understands it from one who recites it is whether they can explain why it works, why it needs sorted data, and why one tiny off-by-one mistake turns a fast algorithm into an infinite loop. That's the gap this lesson closes.

Problem Overview

Given a sorted list of numbers and a target value, find the index of that target — or determine that it isn't in the list at all. The list could have ten items or ten million. Your job is to do it without checking every element, using the fact that the list is already in order.

That last constraint is the whole game. A sorted list carries information: if you look at one value and it's too small, you instantly know the answer, if it exists, is somewhere to the right. Too big, and it's somewhere to the left. Every single check eliminates half of what's left.

Example

Take this sorted array:

[2, 5, 9, 14, 19, 25, 31, 37, 44, 52, 61]

We're searching for 37.

  • Step 1: low = 0, high = 10, mid = 5 → value at mid is 25. Target (37) is bigger, so we discard everything from index 0 to 5. New low = 6.
  • Step 2: low = 6, high = 10, mid = 8 → value at mid is 44. Target is smaller, so we discard everything from index 8 to 10. New high = 7.
  • Step 3: low = 6, high = 7, mid = 6 → value at mid is 31. Target is bigger, so low becomes 7.
  • Step 4: low = 7, high = 7, mid = 7 → value at mid is 37. Found it.

Four checks against an 11-element array. On a million-element array, that same doubling logic gets you there in about 20 checks, not a million.

Intuition

Picture a phone book. You don't start on page one and read every name. You flip to the middle, glance at the name there, and instantly know which half of the book to throw away. Do that a few more times and you're on the right page in seconds.

That trick only works because the names are alphabetical. If the pages were shuffled, checking the middle would tell you nothing — the name there has no relationship to where your target might be. This is the one non-negotiable requirement of binary search: the data must be sorted. Feed it an unsorted array and it won't throw an error — it will just silently hand you the wrong answer, because it's making decisions based on an ordering assumption that isn't true.

Once you accept that constraint, the algorithm falls out naturally. You need to track the boundaries of "what's left to search" — a left edge and a right edge — and a way to check the middle of that shrinking window. That's low, high, and mid. Every round: check the middle, decide which half is worthless, move a boundary inward to discard it. Repeat until the boundaries cross or you land on the target.

The reason this is fast isn't magic — it's math. Cutting a search space in half repeatedly is exponential shrinkage. Halving a million items: 500,000 → 250,000 → 125,000 → ... it takes only about 20 halvings to get down to 1. That's the entire reason binary search matters: it turns a linear problem into a logarithmic one.

Brute Force Solution

Idea: Scan the array from the front, checking each element against the target until you find it or run out of elements.

Algorithm: 1. Loop through every index from 0 to the end of the array. 2. If the current value equals the target, return that index. 3. If the loop finishes with no match, return -1.

Advantages: Works on unsorted data. Trivial to write and reason about.

Disadvantages: Gets slower in direct proportion to the size of the input. On a million-element array, the worst case checks all million values.

Time complexity: O(n) Space complexity: O(1)

Optimal Solution

The optimal approach is binary search, and the mechanics come down to three pointers doing all the work:

Pointer Meaning
low Left edge of the region still worth searching
high Right edge of the region still worth searching
mid The midpoint we check this round

Each iteration:

  1. Compute mid = (low + high) // 2.
  2. Compare array[mid] to the target.
  3. If they match, you're done.
  4. If array[mid] is too small, the target must be to the right — move low = mid + 1.
  5. If array[mid] is too big, the target must be to the left — move high = mid - 1.
  6. Keep looping while low <= high. If that condition fails, the target isn't in the array.

The critical detail — and the source of nearly every bug in this algorithm — is step 4 and 5. You must move past mid, never onto it. If you write low = mid instead of low = mid + 1, the search window never actually shrinks in certain cases, and you get an infinite loop or skip over the correct answer entirely.

Python Code

def binary_search(arr: list[int], target: int) -> int:
    """Return the index of target in a sorted arr, or -1 if not found."""
    low, high = 0, len(arr) - 1

    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1

    return -1


def binary_search_recursive(arr: list[int], target: int, low: int = 0, high: int | None = None) -> int:
    """Recursive version of binary search using the same three pointers."""
    if high is None:
        high = len(arr) - 1

    if low > high:
        return -1

    mid = (low + high) // 2
    if arr[mid] == target:
        return mid
    elif arr[mid] < target:
        return binary_search_recursive(arr, target, mid + 1, high)
    else:
        return binary_search_recursive(arr, target, low, mid - 1)

Code Walkthrough

  • low, high = 0, len(arr) - 1 — the search window starts as the entire array.
  • while low <= high — the loop continues as long as there's still a valid window to check. Once low passes high, the window is empty and the target isn't present.
  • mid = (low + high) // 2 — integer division gives the midpoint of the current window.
  • if arr[mid] == target: return mid — the success case, exits immediately.
  • elif arr[mid] < target: low = mid + 1 — the middle value is too small, so the target (if present) is strictly to the right of mid. Note the + 1: mid itself has already been ruled out.
  • else: high = mid - 1 — mirror case, the target is strictly to the left of mid.
  • return -1 — the loop exited without a match, meaning the target doesn't exist in the array.

The recursive version does exactly the same thing, but instead of updating low/high in a loop, it passes the narrowed window as arguments to the next call. The base case low > high replaces the while condition.

Dry Run

Using the array [2, 5, 9, 14, 19, 25, 31, 37, 44, 52, 61], target 37:

Step low high mid arr[mid] Action
1 0 10 5 25 25 < 37 → low = 6
2 6 10 8 44 44 > 37 → high = 7
3 6 7 6 31 31 < 37 → low = 7
4 7 7 7 37 Match → return 7

Result: index 7, found in 4 comparisons instead of scanning up to 11 elements.

Complexity Analysis

Time: O(log n). Each iteration discards half of the remaining search space. Starting from n elements, you can halve at most log2(n) times before reaching a single element. For a million elements, that's roughly 20 iterations — a dramatic improvement over a linear scan.

Space: O(1) for the iterative version. Only three integer variables (low, high, mid) are used regardless of input size.

Space: O(log n) for the recursive version, because each recursive call adds a frame to the call stack, and the recursion depth matches the number of halvings — log2(n).

Alternative Solutions

Using Python's bisect module: For production code searching a sorted list, bisect.bisect_left(arr, target) does the same binary search under the hood and is implemented in C, making it faster than a hand-rolled Python loop. It's the right choice when you just need the answer and aren't in an interview context. Hand-writing the loop is still essential for interviews, since that's exactly what's being tested.

Interpolation search: A variant that guesses mid based on the target's value relative to the range (like flipping directly near "M" in a phone book instead of always starting in the middle). It can beat O(log n) on uniformly distributed data but degrades to O(n) on skewed data, so it's rarely worth the added complexity outside specialized cases.

Edge Cases

  • Empty array: len(arr) - 1 = -1, so low (0) > high (-1) immediately, loop never runs, correctly returns -1.
  • Single element: low == high == 0. One comparison decides the outcome.
  • Target smaller than every element: high keeps decreasing until it drops below low, returns -1.
  • Target larger than every element: low keeps increasing until it exceeds high, returns -1.
  • Duplicate values: Standard binary search returns some valid index of a matching value, not necessarily the first or last. If you need the leftmost or rightmost occurrence, you need a modified version that keeps narrowing even after finding a match.
  • Unsorted input: No error is raised — the algorithm will confidently return a wrong answer or -1 for a value that's actually present.

Common Mistakes

  1. Using low = mid or high = mid instead of mid + 1 / mid - 1. This is the classic infinite-loop bug — the window never shrinks past a certain point.
  2. Running binary search on unsorted data. No crash, just silently wrong results.
  3. Using low < high instead of low <= high as the loop condition. This misses the case where the target is the last remaining single element.
  4. Integer overflow in (low + high) // 2. Not a practical issue in Python since integers are arbitrary precision, but it's a real bug in languages like Java or C++ — worth mentioning if the interviewer asks about other languages.
  5. Forgetting to handle the "not found" case. Returning None implicitly or letting the function fall through without a defined return value.
  6. Off-by-one errors in high = len(arr) - 1 vs. high = len(arr). Mixing conventions (inclusive vs. exclusive upper bound) mid-implementation is a common source of subtle bugs.

Interview Questions

  • How would you modify this to find the first or last occurrence of a duplicate value?
  • Can you binary search on a rotated sorted array?
  • How would you find the "insertion point" for a value that isn't in the array?
  • What's the difference between binary search on an array versus binary search on an answer (e.g., finding the minimum value that satisfies a condition)?
  • How does the iterative version compare to the recursive version in terms of space complexity?

Key Takeaways

Binary search only works on sorted data — that single requirement is what makes the "throw away half" logic valid. Three pointers, low, high, and mid, track the shrinking search window. Always move boundaries past mid, never onto it, or you risk an infinite loop. The payoff is enormous: O(log n) instead of O(n), the difference between 20 comparisons and a million.

📇 Flashcards

Pattern name for finding a target in a sorted list fast?

Binary search — trigger: sorted data + need to find/bound a value, think 'cut range in half.'

Time complexity of binary search?

O(log n) — each step halves the search space.

Space complexity of iterative vs recursive binary search?

O(1) iterative (three pointers); O(log n) recursive due to call stack.

Most common bug that causes infinite loops in binary search?

Forgetting to move a pointer (e.g. mid ± 1) after a comparison, so the range never shrinks.

Why use left/right/mid pointers instead of scanning linearly?

Each comparison eliminates half the remaining data — the real payoff over O(n) linear search on large sorted sets.

Linear search vs binary search — when does linear win?

Linear search wins on unsorted or small data; binary search requires sorted input and pays off only at scale.
