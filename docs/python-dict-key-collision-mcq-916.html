This Dict Holds 2 Keys But len() Says 1 #shorts

General

Introduction

Every Python developer uses dictionaries daily, but very few can explain what actually makes two keys "the same" under the hood. This matters more than it looks like it should — dictionary key collisions show up in interview questions about hashing, in bugs where data silently disappears, and in real production code that mixes booleans and integers without realizing they can collide.

The example we're breaking down today is deceptively small: three lines of code, one dictionary, one print() call. Yet it's one of those snippets that separates people who've memorized Python syntax from people who understand what's happening at the interpreter level. Interviewers love this kind of question precisely because it's short enough to ask verbally but deep enough to expose whether you understand hashable types, equality, and how CPython implements dicts internally.

By the end of this article, you'll not only know the answer — you'll be able to predict the behavior of any similar "sneaky key" scenario without running the code.

Problem Overview

Here's the setup, in plain terms: you create an empty dictionary. You assign the value "one" to the key 1. Then you assign the value "yes" to the key True. Finally, you print the dictionary.

The question is simple to state and hard to guess correctly: how many entries does the dictionary have, and what does it print?

Most people expect two separate entries — after all, 1 is an integer and True is a boolean, and they look nothing alike. But Python's dictionary implementation doesn't care how a key looks. It cares about two things only: the key's hash value and whether it's equal to an existing key. And on both counts, 1 and True are indistinguishable.

Example

d = {}
d[1] = "one"
d[True] = "yes"
print(d)
print(len(d))

Output:

{1: 'yes'}
1

Walking through what happened:

  1. d[1] = "one" creates a new entry: key 1 maps to "one".
  2. d[True] = "yes" looks up the key True in the dictionary. Python computes hash(True), finds it matches an existing bucket, then checks True == 1. Since that's True (pun intended), Python treats this as updating the same key, not creating a new one.
  3. The value "yes" overwrites "one".
  4. The dictionary ends up with a single entry, and the key displayed is whichever one was inserted first — 1 — even though the second assignment used True.

That last detail surprises people the most: even though you "set" the key as True, the printed dictionary still shows 1 as the key, because Python doesn't replace the key object on an update — only the value.

Intuition

To predict this without running code, you need to internalize one rule: a Python dictionary key is defined by its hash and its equality, not by its type or its literal spelling.

An experienced engineer doesn't think "what type is this key?" — they think "what would hash() and == say about this pair of objects?" That reframing is the whole trick.

So ask two questions about 1 and True:

  • Do they hash the same? Yes. hash(True) == hash(1) is True, because Python's bool type is implemented as a subclass of int, where True is literally 1 and False is literally 0.
  • Are they equal? Yes. True == 1 evaluates to True for the same reason — booleans are integers with a different string representation, nothing more.

Once both conditions hold, Python's dict machinery has no way to tell them apart. It's not "confused" or buggy — it's behaving exactly as designed. This is the same mechanism that lets {1: "a", 1.0: "b"} also collapse into a single key, since hash(1) == hash(1.0) and 1 == 1.0 as well.

The deeper intuition: dictionaries are built for lookups by value identity in the mathematical sense, not by how the key was written in your source code. If you remember that, this entire class of "gotcha" questions stops being tricky.

Brute Force Solution

There isn't really a "brute force vs optimal" algorithm here since this isn't a computational problem — it's a language semantics question. But it's useful to frame it the way an interview follow-up might: "How would you check, in code, whether two objects will collide as dict keys?"

Idea: Manually replicate what the dict does internally — compare hashes and equality separately.

def would_collide(key1, key2):
    return hash(key1) == hash(key2) and key1 == key2

Algorithm: 1. Compute hash() for both objects. 2. Compare hash values. 3. If hashes match, compare the objects with ==. 4. Only if both checks pass do the objects collide as the same key.

Advantages: Simple, transparent, mirrors exactly what CPython does under the hood.

Disadvantages: It's not really "brute force" in the traditional sense — there's no larger search space to reduce. This is more of a diagnostic helper than an algorithm with room for optimization.

Time complexity: O(1) for hash() and == on primitive types like int and bool. Space complexity: O(1).

Optimal Solution

Since there's no algorithmic problem to optimize, the "optimal solution" here is really about writing code that predicts and avoids this collision cleanly, rather than discovering it by accident in production.

The safest approach: never rely on Python's default hash/equality collapsing when your intent is to keep integer and boolean keys logically distinct. If you need both 1 and True as separate entries, disambiguate them explicitly — for example, by wrapping keys in a tuple that includes the type, or using a string prefix.

d = {}
d[("int", 1)] = "one"
d[("bool", True)] = "yes"
print(d)

Python Code

def demonstrate_dict_collision():
    """Show how True and 1 collapse into the same dict key."""
    d = {}
    d[1] = "one"
    d[True] = "yes"
    return d


def safe_distinct_keys():
    """Keep integer and boolean keys logically separate."""
    d = {}
    d[("int", 1)] = "one"
    d[("bool", True)] = "yes"
    return d


if __name__ == "__main__":
    collided = demonstrate_dict_collision()
    assert collided == {1: "yes"}
    assert len(collided) == 1

    distinct = safe_distinct_keys()
    assert len(distinct) == 2
    assert distinct[("int", 1)] == "one"
    assert distinct[("bool", True)] == "yes"

    print(collided)
    print(distinct)

Code Walkthrough

  • d = {} initializes an empty dictionary with no keys.
  • d[1] = "one" inserts a new key-value pair. Python computes hash(1), finds no existing entry with an equal key, and creates a fresh slot.
  • d[True] = "yes" computes hash(True), which equals hash(1). Python checks the existing entry at that hash bucket, confirms True == 1, and treats this as an update rather than an insert — the value "yes" replaces "one", but the original key object (1) stays in place.
  • demonstrate_dict_collision() returns the single-entry dict to make the behavior explicit and testable.
  • safe_distinct_keys() shows the fix: wrapping each key in a ("type", value) tuple guarantees a unique hash and unequal comparison, so both entries survive.
  • The assert statements in __main__ act as a lightweight self-check — if Python's collision behavior ever mattered differently in your environment (it won't, but it documents the expectation), this would fail loudly instead of silently.

Dry Run

2 d[1] = "one" {1: "one"} New key 1, hash computed and stored
3 hash(True) computed — Equals hash(1)
4 True == 1 checked — Evaluates to True

7 len(d) 1 Confirms single entry

Complexity Analysis

  • Time complexity: O(1) average for each dictionary insertion/update, since Python dicts are hash tables with amortized constant-time operations for hash() computation, bucket lookup, and equality comparison on primitive types.
  • Space complexity: O(1) additional space for this specific example — one entry stored regardless of how many "colliding" keys are assigned.
  • Why this is correct: Dict operations in CPython are backed by open addressing on a hash table. The number of distinct entries is bounded by the number of key values that are both hash-distinct and equality-distinct, not by the number of assignment statements executed.

Alternative Solutions

An alternative way to detect or prevent this collision is using type() checks before insertion:

def strict_insert(d, key, value):
    for existing_key in d:
        if type(existing_key) != type(key) and existing_key == key:
            raise TypeError(f"Key {key!r} collides with existing key {existing_key!r} of different type")
    d[key] = value

This trades performance (an O(n) scan per insert) for safety, catching accidental type-crossing collisions early — useful in data validation or ETL code where mixed-type keys might indicate upstream bugs, but overkill for everyday dictionary use.

Edge Cases

  • 0 and False: Same collision — hash(False) == hash(0) and False == 0.
  • Floats matching ints: {1: "a"}[1.0] returns "a" because hash(1) == hash(1.0).
  • Complex numbers: hash(1+0j) == hash(1) as well — even more surprising for most developers.
  • Custom objects with overridden __eq__/__hash__: Any two objects can be made to collide (or never collide) depending on how these dunder methods are implemented.
  • Unhashable keys: Lists or dicts as keys raise TypeError immediately — they're excluded from this discussion entirely since they can't be dict keys at all.

Common Mistakes

  1. Assuming type matters for dict keys — it doesn't; only hash() and __eq__ matter.
  2. Expecting the printed key to match the most recent assignment — the original key object is retained; only the value updates.
  3. Using booleans and integers interchangeably as keys without realizing the overlap, leading to silent data loss in real applications (e.g., a "status flag" dict where 1 and True were meant to represent different states).
  4. Forgetting that len() counts unique keys, not insertion operations — three assignments can still yield len(d) == 1.
  5. Not testing dict-based caches or memoization tables with mixed key types, which can cause cache poisoning when 1 and True are treated as the same cache entry.

Key Takeaways

  • Python dict keys are defined by hash() and __eq__, never by type or literal appearance.
  • True and 1 (and False and 0) are hash-equal and value-equal because bool subclasses int.
  • Assigning to an "equal" key updates the value but keeps the original key object.
  • When you need integer and boolean values to act as distinct keys, disambiguate them explicitly (e.g., tuple-wrap with a type tag).
  • This isn't a bug — it's a direct, predictable consequence of how Python defines hashability.

Space complexity of a Python dict with n entries?

O(n) — plus overhead for open-addressing table sizing (grows to keep load factor low).
