Top 10 Things To Check Before You Ship To Production: Why Your Green Tests Still Lied

General

Introduction

Every engineer has shipped a change that passed every test and still broke production. It's one of the more disorienting experiences in software engineering — the pipeline is green, the reviewer approved, and ninety seconds after deploy the pager goes off anyway. This isn't a story about bad luck. It's a story about what a test suite is actually built to check, and what it was never designed to check in the first place.

This matters for two overlapping reasons. First, it's the difference between a boring deploy and a 3am incident, and most teams learn this checklist the hard way — after the incident, not before. Second, this exact gap between "tests pass" and "production is safe" is a favorite theme in senior and staff-level interviews, because it separates engineers who can write correct code from engineers who understand how systems actually fail in the real world. Interviewers probe this with questions like "walk me through how you'd deploy a risky change" or "tell me about a production incident you handled" — and the strongest answers all circle back to some version of this checklist.

The goal here isn't to memorize ten bullet points. It's to build the instinct behind them, so that when you're staring at a green pipeline, you know exactly what it isn't telling you.

Problem Overview

Here's the scenario, stated plainly: you have a fully tested change. Unit tests pass, integration tests pass, maybe you even have decent coverage numbers. You deploy. Shortly after, something breaks in production that no test caught.

The underlying problem is a mismatch between the environment your tests run in and the environment your code actually runs in. Tests typically run against a database seeded moments ago, with clean, predictable data, low concurrency, and no real user traffic. Production runs against years of accumulated data — nulls that shouldn't exist, duplicate rows nobody cleaned up, edge cases that were never written into a fixture, real network conditions, and real concurrent load. Tests validate logic. They say nothing about environment, scale, configuration, or operational readiness.

The task, then, is to define a fast, repeatable set of checks that specifically targets this gap — the stuff tests structurally cannot see — and run it before every deploy.

Example

Picture two deploys of the exact same code change, one hour apart, on two different teams.

Team A merges, watches CI go green, and deploys immediately. Ninety seconds later: users can't log in, and the database is dropping writes. The root cause, once found: the production environment variable pointed at a staging database URL, left over from a config change three days earlier. No test caught it, because tests never touch real environment variables — they use a .env.test file that was correctly configured.

Team B makes the same change but runs a five-minute pre-deploy pass first. Step one is diffing prod env vars against dev/staging. They immediately spot the stale database URL, fix it, and deploy clean.

Same code. Same test suite. Same green pipeline. Completely different outcome — because the difference was never in the logic, it was in the environment surrounding it.

Intuition

Here's how an experienced engineer actually thinks about this, and it starts by rejecting a false belief: "tests passed" and "this is safe to run in production" are not the same claim, and treating them as equivalent is the single most common mistake in software delivery.

The mental model that helps: your test suite answers the question "does this code do what I intended, given the inputs I thought of?" It cannot answer "does this code survive contact with the actual world it's about to run in?" Those are different questions requiring different verification.

So instead of asking "did tests pass," an experienced engineer asks a single unifying question before every deploy: what's different between where I just tested this and where it's about to run?

That one question, applied honestly, surfaces almost everything on this list without needing to memorize it: - Different env vars? → config check. - Different data shape and volume? → migration and staging-parity check. - Different traffic level? → load check. - Different failure modes when a dependency goes down? → error-handling check. - No visibility into what's happening right now? → logging/monitoring check. - No tested way to undo this? → rollback check. - Different trust boundary (public internet vs. your laptop)? → auth/security check. - Untested safety nets (backups, rate limits)? → those aren't safety nets, they're guesses.

The list below is just that one question, broken into ten concrete, checkable items.

Brute Force Solution

The "brute force" approach to deploy safety is: write more tests, and hope coverage eventually catches everything.

Idea: if a bug slips through, add a test for that exact case. Over time, the theory goes, your test suite converges toward catching everything.

Algorithm: 1. Ship code. 2. Wait for something to break. 3. Write a regression test for it. 4. Repeat.

Advantages: - Simple to reason about — one bug, one test. - Genuinely does prevent that specific regression from recurring. - Requires no process change, no checklist discipline.

Disadvantages: - It's reactive, not preventive — you pay for every lesson with an incident first. - It doesn't scale to environmental problems. You cannot write a unit test that would have caught "someone changed a prod env var three days ago." That class of bug lives outside the code entirely. - Test suites grow large and slow without proportionally growing safer, because most production incidents aren't logic bugs — they're environment, scale, and operational bugs.

Time complexity (informally): cost grows linearly with the number of incidents you've already survived — O(incidents), which is a bad way to learn.

Space complexity: grows with test suite size, much of it low-value regression tests for one-off environmental mismatches that a checklist would have caught in five minutes.

Optimal Solution

The optimal solution isn't more tests — it's a fast, structural checklist that targets exactly the categories tests can't see. Ten checks, roughly five minutes, run every deploy.

# Check What it catches
1 Environment variables Wrong DB URL, test API keys leaking into prod
2 Migrations against real data Migration that breaks on 3 years of production rows, no rollback plan
3 Load and concurrency Race conditions, connection pool limits under real traffic
4 Graceful degradation One dependency outage taking down the whole app
5 Logging and monitoring No visibility when something breaks at 2am
6 Rollback plan No fast, tested way to undo a bad deploy
7 Security and auth Endpoints that trust anyone who asks
8 Backup restore (tested) A backup nobody has ever actually restored
9 Rate limiting (tested) A limit that's never held under real spike traffic
10 Staging parity Staging that's a smaller, friendlier lie vs. real prod shape and scale

Two of these deserve extra emphasis because they're the ones almost nobody actually tests, not just sets up: backups and rate limits. Having a backup script or a rate-limit config is not the same as knowing it works. A parachute you've never opened isn't a safety net — it's a guess. The only way to know check 8 and check 9 actually hold is to have restored from that backup and watched that rate limit survive a real spike, at least once, deliberately.

Checks 1–3 target the environment and scale gap. Checks 4–6 target failure behavior and recovery. Checks 7–9 target safety nets, tested or otherwise. Check 10 is the meta-check that keeps the other nine honest — if staging doesn't resemble prod, none of the other checks mean much when run there instead.

Python Code

None of this checklist requires new infrastructure. Here's a lightweight pre-deploy script that automates the mechanical parts — env var diffing and a rollback-readiness reminder — while the rest (load, security, staging parity) stays a human judgment call the checklist prompts you to make.

"""Pre-deploy sanity check: diffs env vars and prints the full checklist."""

import os
import sys
from pathlib import Path


def load_env_file(path: str) -> dict[str, str]:
    """Parse a simple KEY=VALUE .env file into a dict."""
    env = {}
    if not Path(path).exists():
        return env
    for line in Path(path).read_text().splitlines():
        line = line.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        key, _, value = line.partition("=")
        env[key.strip()] = value.strip()
    return env


def diff_env(dev_path: str, prod_path: str) -> None:
    """Flag env vars whose values differ or are missing between dev and prod."""
    dev_env = load_env_file(dev_path)
    prod_env = load_env_file(prod_path)

    suspicious = []
    for key in sorted(set(dev_env) | set(prod_env)):
        dev_val, prod_val = dev_env.get(key), prod_env.get(key)
        if dev_val is not None and dev_val == prod_val:
            suspicious.append(key)  # prod matches dev exactly -- likely leaked value

    if suspicious:
        print("WARNING: these prod env vars exactly match dev values:")
        for key in suspicious:
            print(f"  - {key}")
    else:
        print("Env var check: no obvious dev/prod overlap found.")


CHECKLIST = [
    "Environment variables diffed against dev/staging",
    "Migrations tested against a prod-shaped dataset, rollback verified",
    "Load/concurrency behavior checked beyond single-user testing",
    "Dependency failures degrade gracefully, don't cascade",
    "Logging/monitoring in place for this change",
    "Rollback tested, not just written",
    "Auth/permissions checked on every new or changed endpoint",
    "Backup restore actually tested recently",
    "Rate limiting actually tested under load recently",
    "Staging matches prod data shape and scale",
]


def print_checklist() -> None:
    print("\nPre-deploy checklist:")
    for i, item in enumerate(CHECKLIST, 1):
        print(f"  [{i}] {item}")


def main() -> None:
    dev_path = sys.argv[1] if len(sys.argv) > 1 else ".env.dev"
    prod_path = sys.argv[2] if len(sys.argv) > 2 else ".env.prod"
    diff_env(dev_path, prod_path)
    print_checklist()


if __name__ == "__main__":
    main()

Code Walkthrough

  • load_env_file reads a .env-style file line by line, skipping comments and blanks, and returns a plain dict. No dependency needed for this — it's a handful of lines of str parsing.
  • diff_env loads both dev and prod env files and flags any key where the prod value is identical to the dev value. An identical value in both places is exactly the "dev database URL leaked into prod" failure mode from the transcript's opening story — it's a strong signal, not proof, so it's a warning, not a hard failure.
  • CHECKLIST is a plain list of strings — no need for a class, enum, or config file for ten static strings that never change.
  • print_checklist just enumerates and prints them, giving you a physical, glanceable list to walk through by hand for the nine checks that genuinely require human judgment (load, security review, staging parity, and so on).
  • main wires it together, accepting file paths as optional CLI args so it works in any repo layout without hardcoding paths.

Dry Run

Suppose .env.dev contains:

DATABASE_URL=postgres://localhost/dev_db
API_KEY=test_key_123
DEBUG=true

And someone accidentally left this in .env.prod:

DATABASE_URL=postgres://localhost/dev_db
API_KEY=prod_key_live_456
DEBUG=false

Running python predeploy_check.py .env.dev .env.prod:

  1. load_env_file parses both files into dicts.
  2. diff_env iterates the union of keys: API_KEY, DATABASE_URL, DEBUG.
  3. For DATABASE_URL, dev and prod values are identical (postgres://localhost/dev_db) → flagged.
  4. For API_KEY and DEBUG, values differ → not flagged.
  5. Output: ``` WARNING: these prod env vars exactly match dev values:
    • DATABASE_URL ```
  6. The checklist prints below it as a reminder for the other nine checks.

That single flagged line is exactly the bug that took down Team A's deploy in the earlier example — caught in under a second, before deploy, instead of ninety seconds after.

Complexity Analysis

  • Time: load_env_file is O(n) in the number of lines per file. diff_env is O(k) where k is the number of unique keys across both files. Overall the script is linear in the size of the env files — trivially fast, since env files are small (tens of lines, not thousands).
  • Space: O(k) to hold both dicts and the union of keys in memory. Negligible for realistic env file sizes.
  • These bounds are correct because there's no nested iteration over the files — each is read once, and the diff is a single pass over a set union, not a cross-product comparison.

Alternative Solutions

A reasonable alternative to a standalone script is folding these checks into your CI/CD pipeline as an explicit gate — for example, a GitHub Actions step that runs the env diff automatically before any production deploy job, or a required checklist in your PR template for the manual checks (load, security, staging parity).

Trade-off: the standalone script is faster to write and run manually, and works even without CI access. A CI-gated version is slower to set up but removes the human "did I remember to run this" failure mode entirely, which matters more as team size grows. For a solo project or small team, the manual script is the right amount of process. For a team where deploys happen without direct oversight, wiring it into CI is worth the extra setup.

Edge Cases

  • Empty env files: load_env_file returns {} for a missing or empty file rather than raising — deploy checks should degrade to "nothing to flag" instead of crashing.
  • Duplicate keys in one file: the last occurrence wins, matching how most .env loaders behave, since dict assignment naturally overwrites.
  • Keys present in only one file: correctly skipped from the "identical value" warning, since dev_val is not None and dev_val == prod_val short-circuits when either side is missing — but worth eyeballing separately, since a prod-only key can be its own red flag (unused legacy config) and a dev-only key might mean prod is missing something it needs.
  • Values with = in them (e.g., a base64 secret): partition("=") splits on the first = only, so the rest of the value stays intact.
  • Maximum realistic scale: even a bloated env file with a few hundred variables runs through this in milliseconds — this isn't a performance-sensitive path.

Common Mistakes

  1. Treating a green test suite as proof of production safety. Tests check logic, not environment — conflating the two is the root cause of most "but it passed CI" incidents.
  2. Never actually testing the rollback. Writing a rollback plan and testing a rollback are different activities; only the second one tells you it works under pressure.
  3. Skipping the staging-parity check because staging "basically" matches prod. A smaller, cleaner staging environment hides exactly the data-shape and scale bugs prod will expose.
  4. Assuming a backup exists means a backup works. An untested backup is a guess, not a safety net — restore it before you need it, not during the incident.
  5. Not diffing environment variables before every deploy, treating it as a one-time setup step instead of a per-deploy habit — configs drift silently over weeks.
  6. Building features without graceful degradation, so one third-party outage (payment API, email service) takes the entire app down instead of just that one feature.
  7. Deploying without a way to observe what happens next — no logging or monitoring tied to the change, so if it breaks, you're debugging blind instead of reading a dashboard.

Key Takeaways

  • A passing test suite proves your logic is correct for the inputs you thought of — nothing more.
  • Most production incidents live in the gap between "tested" and "real environment": config, scale, data shape, and untested safety nets.
  • The single question that generates this entire checklist: what's different between where I just tested this and where it's about to run?
  • Untested safety nets — backups, rate limits, rollbacks — aren't safety nets. They're guesses until you've actually exercised them.
  • Five minutes of structural checking before deploy is cheaper than any incident it prevents.
