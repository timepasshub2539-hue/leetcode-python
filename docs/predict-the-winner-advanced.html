Predict the Winner — 🔴 Advanced (3/3) — LeetCode Daily Python Solution (stop tracking two scores)

General

Introduction

Predict the Winner shows up on interview lists for a reason that has nothing to do with the code being long — it's short. What it tests is whether you can look at a two-player game and realize you don't need to simulate two players at all. That's the actual skill interviewers are probing: can you find a smaller, equivalent state space than the one the problem statement seems to hand you?

This problem sits in the same family as Stone Game and a handful of other "optimal play from both ends" problems. Once you've internalized the pattern here — collapsing two competing scores into one signed difference — you'll recognize it instantly in every variant that follows. It's one of those rare DP problems where the insight, not the code, is the entire interview.

Problem Overview

You're given an array of non-negative integers. Two players take turns removing a number from either end of the array — never from the middle — and add it to their own score. Player 1 always moves first. Both players play optimally, meaning each one picks the move that maximizes their own final score, fully accounting for how the other player will respond.

The question isn't "who wins by how much." It's a yes/no question: can Player 1 end the game with a score greater than or equal to Player 2's? Ties count as a win for Player 1 — a small rule that changes a comparison operator later, so it's worth remembering.

Example

Take nums = [1, 5, 2].

The obvious instinct is "grab the 5, it's the biggest number." But Player 1 can only choose from the ends — 1 or 2 — the 5 isn't available yet.

  • Player 1 takes 2. Array left: [1, 5].
  • Player 2 takes 5 (their best move). Array left: [1].
  • Player 1 takes 1.

Final score: Player 1 has 2 + 1 = 3. Player 2 has 5. Player 1 loses, so the answer is false.

This is the counterexample worth keeping in your back pocket: greedy "take the bigger end" fails even on an array of length 3, because taking a number now can hand your opponent something bigger next turn.

Intuition

Here's how an experienced engineer approaches this without jumping to code.

First, notice the game is zero-sum with perfect information — no hidden cards, no randomness, and the total of everything on the board is fixed. Since every number eventually gets picked up by one player or the other, score1 + score2 is a constant no matter how the game plays out. It's sum(nums), always.

That single fact is the whole trick. If the total is fixed, then score1 - score2 alone tells you everything you need — you don't need both scores, just their difference. If that difference is positive, Player 1 wins the game; if it's non-negative, Player 1 at least ties, satisfying the problem's win condition.

Second, notice that at any point in the game, the only thing that matters is the current subarray — the numbers already removed are irrelevant to what happens next. That means the "state" of the game can be described entirely by a range [i, j] of the array. So define diff(i, j) as the best score difference the player whose turn it is can achieve, playing optimally on the subarray nums[i..j].

When it's your turn, you pick either end: - Take nums[i], leaving your opponent to play optimally on [i+1, j]. Their optimal outcome from their perspective is diff(i+1, j) — but from your perspective, that's working against you, so you subtract it. - Take nums[j], leaving your opponent [i, j-1], same subtraction logic.

You pick whichever end gives the larger result:

diff(i, j) = max(nums[i] - diff(i+1, j), nums[j] - diff(i, j-1))

The subtraction isn't arbitrary — it's the negation you get from switching whose perspective "the score difference" is measured from. Every turn flips who's "you," so every turn flips the sign.

Brute Force Solution

Idea: Simulate the game literally. Two accumulators, score1 and score2. At each turn, try both ends recursively, let the current player pick whichever branch maximizes their own score, and alternate whose accumulator gets updated.

Algorithm: 1. Recurse on (i, j, turn). 2. If i > j, compare score1 >= score2 and return. 3. Try taking nums[i] and nums[j], recursing into both, adding the picked value to the current player's score. 4. Return whichever branch the current player's objective favors.

Advantages: Directly mirrors the problem statement — easy to convince yourself it's correct.

Disadvantages: At every subarray of length k, there are 2 choices, and no subproblem reuse because the state includes both running scores, which vary per path. That gives branching that's exponential in n.

Complexity: Time O(2ⁿ), Space O(n) for recursion depth.

Optimal Solution

The reduction from the intuition section is what turns this into a standard interval DP. Two conditions justify using DP here:

  • Optimal substructure: diff(i, j) depends only on diff(i+1, j) and diff(i, j-1) — the best answer for a range is built purely from the best answers of two smaller ranges.
  • Overlapping subproblems: many different paths through the game revisit the same (i, j) range, so memoizing or tabulating pays off.

Fill order: dp[i][j] depends on dp[i+1][j] and dp[i][j-1], both intervals strictly shorter than [i, j]. So if you iterate by increasing subarray length — 1, then 2, then 3, and so on — every dependency is already computed before you need it.

Base case: length-1 intervals. With only one number, there's no decision — diff(i, i) = nums[i].

Table shape: an n x n grid where only the upper triangle (i <= j) is meaningful.

Walking nums = [1, 5, 233, 7] through the table by increasing length:

Interval diff value Reasoning
[0,0], [1,1], [2,2], [3,3] 1, 5, 233, 7 base case
[2,3] 226 max(233 - 7, 7 - 233) = 226
[1,2] -228 max(5 - 233, 233 - 5) = 228...
[0,3] 222 combines shorter intervals

dp[2][3] = 233 - 7 = 226 is the cell that matters most here — it's what pulls the final answer strongly positive despite the array starting with small numbers. dp[0][3] resolves to 222, and since 222 >= 0, Player 1 wins.

Python Code

def PredictTheWinner(nums: list[int]) -> bool:
    n = len(nums)
    if n <= 1:
        return True

    # dp[i][j] = best score difference the current player can achieve on nums[i..j]
    dp = [[0] * n for _ in range(n)]

    # Base case: single-element intervals
    for i in range(n):
        dp[i][i] = nums[i]

    # Fill by increasing interval length so dependencies are ready
    for length in range(2, n + 1):
        for i in range(n - length + 1):
            j = i + length - 1
            take_left = nums[i] - dp[i + 1][j]
            take_right = nums[j] - dp[i][j - 1]
            dp[i][j] = max(take_left, take_right)

    return dp[0][n - 1] >= 0

Code Walkthrough

  • if n <= 1: return True — with zero or one elements, Player 1 either has nothing to lose or takes the only number, and always ends up ahead or tied.
  • dp = [[0] * n for _ in range(n)] — a fresh 2D grid, one cell per (i, j) pair.
  • The base-case loop sets every dp[i][i] = nums[i], matching the length-1 case from the intuition.
  • The outer loop for length in range(2, n + 1) walks subarray sizes from 2 up to n, guaranteeing shorter intervals are already filled.
  • i ranges over all valid starting indices for that length; j = i + length - 1 is the matching end index.
  • take_left and take_right compute the two choices from the recurrence — take the left end or the right end, subtracting the opponent's best response on what's left.
  • dp[i][j] = max(...) — the current player always takes the better of the two options.
  • The final dp[0][n-1] >= 0 check encodes the tie-favors-Player-1 rule directly.

Dry Run

nums = [1, 5, 233, 7], indices 0–3.

Length 1: dp[0][0]=1, dp[1][1]=5, dp[2][2]=233, dp[3][3]=7.

Length 2: - dp[0][1] = max(1-5, 5-1) = 4 - dp[1][2] = max(5-233, 233-5) = 228 - dp[2][3] = max(233-7, 7-233) = 226

Length 3: - dp[0][2] = max(1 - dp[1][2], 233 - dp[0][1]) = max(1-228, 233-4) = 229 - dp[1][3] = max(5 - dp[2][3], 7 - dp[1][2]) = max(5-226, 7-228) = -221

Length 4: - dp[0][3] = max(1 - dp[1][3], 7 - dp[0][2]) = max(1-(-221), 7-229) = max(222, -222) = 222

dp[0][3] = 222 >= 0 → true. Player 1 wins, driven almost entirely by that dp[2][3] = 226 cell propagating upward.

Complexity Analysis

Time: O(n²) — there are O(n²) (i, j) pairs, and each cell does O(1) work.

Space: O(n²) for the table. This is tight for the 2D formulation as written — every cell genuinely gets read during the fill.

Why it's correct: diff(i, j) is a pure function of the range [i, j] alone — it doesn't depend on how you arrived at that range. That's exactly the property that makes memoization (and tabulation) valid rather than just convenient.

Alternative Solutions

Top-down memoization: identical recurrence, computed lazily with a cache keyed on (i, j). Useful when you don't want to fill unreachable cells, though for this problem every cell with i <= j is reachable from dp[0][n-1], so the practical savings are small. Same O(n²) time and space.

from functools import lru_cache

def PredictTheWinner(nums: list[int]) -> bool:
    n = len(nums)

    @lru_cache(maxsize=None)
    def diff(i, j):
        if i == j:
            return nums[i]
        return max(nums[i] - diff(i + 1, j), nums[j] - diff(i, j - 1))

    return diff(0, n - 1) >= 0

Space-optimized bottom-up: since dp[i][j] only ever reads from intervals one shorter, you can collapse the 2D table to a single 1D array updated in place per length, bringing space down to O(n). Worth mentioning in an interview even if you don't write it out — it signals you understand the dependency structure, not just the recurrence.

Edge Cases

  • Empty array: not valid per constraints, but n == 0 returns True trivially with the n <= 1 guard.
  • Single element: Player 1 takes it, automatically wins or ties — falls out of the n <= 1 check.
  • All equal values: every diff collapses toward 0 regardless of choices; the answer is always True since ties favor Player 1.
  • Even-length arrays: Player 1 can always secure all even-indexed or all odd-indexed elements, whichever sums larger, guaranteeing a win — no special-casing needed, the DP finds this naturally.
  • Large values: Python's arbitrary-precision integers make the stated bounds a non-issue; in a fixed-width language you'd need to check the max possible diff magnitude against overflow.

Common Mistakes

  1. Greedy "take the bigger end." Fails on inputs as small as [1, 5, 2] — see the Example section.
  2. Swapping dp[i+1][j] and dp[i][j-1] in the recurrence. Both are valid-looking indices, so it still runs without error — it just silently models the wrong player's turn and produces plausible but wrong answers on non-trivial inputs.
  3. Using > 0 instead of >= 0 in the final check. This ignores the tie-favors-Player-1 rule and will flip the answer on any input where the optimal difference is exactly zero.
  4. Filling the table in the wrong order (e.g., by row instead of by increasing length), which reads dp[i+1][j] or dp[i][j-1] before they've been computed.
  5. Tracking score1 and score2 separately in the DP formulation. It's not wrong, exactly, but it doubles the state you need to carry and obscures the actual insight the problem is testing.

Key Takeaways

Zero-sum games with two optimal players collapse into a one-player optimization when you track the score difference instead of both scores separately. The recurrence follows directly from that reduction, and the fill order for the DP table falls out of the dependency structure once you see it as interval DP. It's O(n²) time and space in the straightforward form, compressible to O(n) space with a bit more care.

📇 Flashcards

Two players pick from array ends optimally — what pattern?

Interval/game-theory DP: state = subarray range (i,j), track score difference not raw totals.

Time complexity for Predict the Winner DP?

O(n²) — one entry per (i,j) subarray, O(1) transition each.

Space complexity, and how to cut it?

O(n²) for the 2D table; reducible to O(n) with a rolling 1D array over diagonals.

Most common bug in this DP?

Forgetting the score is a *difference* (current player minus opponent), not each player's own total.

How does this differ from plain subarray sum DP?

Adds an adversarial min inside your max — opponent always leaves you the worse remaining choice.

Interview follow-up: why track difference instead of two scores?

Collapses two interacting quantities into one recurrence — both players use the same optimal-play formula, halving state.
